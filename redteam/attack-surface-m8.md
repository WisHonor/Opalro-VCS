# Milestone 8 attack surface: combine (red-team session RT19, decision 024)

Milestone 8 is the second of v0.2. It adds `opalro combine`: bringing one line's work into another. It is the first code since `goto` that rewrites the project folder, the first that makes a save with two parents, and the first that builds a new version of the project out of three others. It adds no file format: a save with two parents and a save's move notes were in format 1 already.

- **`opalro combine <target> ["message"]`.** The target is anything `goto` takes (a line, a server line, a tag, an ID). The project must be on a line. Three outcomes: nothing to combine (the line already has everything); the line only moves forward (it hadn't moved since the other left it; no save is made); or a combined save with two parents, made at once. The folder is then switched to the result as `goto` switches, as one diary step named `combine` that `undo` takes back. A combine that would leave a conflict stops, names the files (the first 100), and changes nothing.
- **Where two lines parted.** One walk over saves (`ancestry::common_starts`) finds every common starting point. None: refused. Several (two lines each combined into the other): they are combined with each other first, in ID order, each pair from its own starting points, within a budget (16 at a level, 64 inner combines in all, 256 MiB of text held).
- **Merging the project.** Entry by entry, folder by folder (`combine/tree.rs`): what one side alone changed is taken; folders are merged one level down; a file's executable mark and contents are merged apart; names one folder can't hold on Windows or macOS stop the combine.
- **Merging text.** Line by line (`combine/text.rs`), with the comparison `opalro changes` uses: changes that overlap or touch conflict; line endings are bytes; binaries, big files and files whose rule in `opalro.toml` says `conflict-markers = false` are never merged.
- **Moves.** `opalro save` now notes, in the save, each file that moved with nothing else changed. A combine follows those notes (and, where there are none, identical contents), so a change to a moved file lands where the file went. A note is believed only when it is true of its own save.
- **Saves a combine brought in.** A save is found by its ID through every parent once the line has none. `opalro history` marks a combined save and lists from any line, tag or save; `opalro show` names the other parent; every save in `--json` carries its parents.
- **Git's words.** `merge <target>` runs `combine`; `merge --abort`, `--no-ff`, `--squash` and `merge a b` are explained.

Threat list: `docs/security.md` §4. Decisions 164 to 170 in `docs/decisions/` give the rules this code follows; **read 170 first**: it corrects the six before it, and its cases (three ways a moved file's contents could have ended under another file's name; a folder left behind; where Opalro and Git differ) show where this code has been wrong already. The calls made while building are in `docs/plans/2026-11-14-milestone-8-rulings.md`. `docs/terminal.md` says what `combine` prints for people, `docs/json.md` for programs, `docs/storage-format.md` §4 what a save's move notes hold and §12 how a rule's patterns match.

## Where the code is

- `crates/opal-vcs-core/src/ancestry.rs`: `common_starts`, beside `only_in`.
- `crates/opal-vcs-core/src/combine.rs`: `combine` (the command), `merge_three` (the merge that follows moves), the errors and their words, the budget.
- `crates/opal-vcs-core/src/combine/tree.rs`, `combine/text.rs`: the two merges. `combine/tests.rs`: their tests and a model of the merge with moves.
- `crates/opal-vcs-core/src/moves.rs`: what a save notes, what a combine follows, the bounds on what either holds.
- `crates/opal-vcs-core/src/rules.rs`: which rule decides `conflict-markers` for a path.
- `crates/opal-vcs-core/src/snapshot.rs`: where `save` works out its notes. `kept.rs`: `overlay_with`, which a combine uses to put a moved file at its new place. `switch.rs`: the end of a switch, shared by `goto` and `combine`.
- `crates/opal-vcs-core/src/history.rs`: finding a save through every parent; `for_each_from`.
- `crates/opal-vcs/src/main.rs`, `combine_output.rs`, `history_output.rs`, `show_output.rs`, `git_words.rs`: the command line.
- Tests to read for how to build a hostile case: `crates/opal-vcs/tests/combine.rs`, `merge_vs_git.rs`, `model.rs`, and `tests/support` (helpers that plant saves, combined saves, tag lists and packs).

## Places worth attacking

1. **Losing or corrupting what a person saved.** A combine that goes through and silently drops one side's change, takes the wrong version of a file, merges two different files' text together, or puts one file's contents under another file's name. Decision 170 lists three such cases found and fixed in the code that follows moves; look for a fourth. Moves across both lines, chains of moves, a file moved onto a name another file left, folders moved file by file, a file that becomes a folder, names that differ only by letter case or by how an accented letter is written, an executable mark changed on one side and the contents on the other.
2. **A planted history or planted notes.** Move notes in a save are data from whoever made the repository. A note is believed only when it is true of its own save: can a save be built whose note is true of it and still sends another person's change into the wrong file? Notes with odd paths, very many notes, notes in a combined save, notes along a chain of thousands of saves. A history shaped to make the starting-point walk read everything, to give more than 16 starting points, or to make starting points that themselves need starting points, again and again (the budget of 64, and the call depth).
3. **The folder.** `combine` rewrites the folder through `goto`'s code. Unsaved work in the way, ignored files in the way, files open in another program, a file that is a link, a folder where a file should go, a combine stopped at any write (the next command must finish it or it never happened), a combine after a stopped `goto`. After a combine that goes through: does the folder equal what `goto <the combined save>` writes, folders included? After one that is refused: is anything changed, anything stored (`.opalro/packs`, `.opalro/tmp`)?
4. **Undo, redo, tidy.** `undo` after a combine and after a line that only moved forward; `redo`; `undo --to`; `tidy` inside and past the undo window, with the other line deleted: is a save freed that something still reaches through a second parent?
5. **Resources.** Many large text files both lines changed (one merged file at a time in memory); a huge reshuffle (the 64 MiB bound on following moves, and the `moves_not_followed` warning); a text file at the size and line limits; a comparison that runs out of its two seconds; a `opalro.toml` with very many rules and a deep path; a save with 1,024 parents in `history` and `show`; a missed ID on a large history (it walks every save).
6. **What a person is shown.** The refusal's list of files (paths from a hostile repository, at most 100), the target's name in the outcome line (a tag's odd name), the default message, `history`'s `[combined …]` marks (can a tag's name, a line's name or a save's message pose as one?), `show`'s `Combined` rows, hints and next-step lines (nothing from the project inside a command unless it is plain; an ID in a hint must be one the command takes).
7. **Names and IDs.** A line or tag named like the start of the ID of a save reached only through a second parent (it must be refused as meaning both); a name that is both a line and a tag as `combine`'s target; `history <from>` and `combine` reading a name by the one resolver.
8. **Git's words.** `merge` forms that run something other than what Git would mean: two targets, an option that looks like a target, `-m`, `--no-commit`, `--continue`.
9. **Rules in `opalro.toml`.** A file that a rule's author meant to keep from being merged automatically and that is merged anyway: letter case, brackets, escapes, a leading `#` or `!`, a folder pattern, a pattern with a line break, a rule changed on one of the two lines being combined (the rules that decide are the folder's own when the combine starts).
10. **Old against new.** A project used with this build and then opened by v0.1: a save with two parents and move notes must still read there. A project made by v0.1, combined here.
