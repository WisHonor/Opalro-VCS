# Milestone 7 attack surface: lines and tags (red-team session RT17, decision 024)

Milestone 7 is the first of v0.2. It adds no file format and writes nothing new to the project folder: every new command records one diary step that changes only the state (lines, where the project stands, tags).

- **Lines.** `opalro line new <name>` makes a line at the save the project is on and moves onto it. `opalro save --line <name>` now works from a line too. `opalro line rename [<old>] <new>` renames one. `opalro line delete <name> [--yes]` takes a name away, never the line the project is on, and asks first when no other line, tag or server line has the line's newest save in its history.
- **Tags.** `opalro tag` lists them; `opalro tag <name> ["message"] [--save <save>] [--yes]` makes one, or moves one that exists (asked first); `opalro tag --delete <name> [--yes]` deletes one (asked first). A tag's name is taken wherever a save is asked for (`goto`, `show`, `changes --save`, `tag --save`), after lines and server lines and before IDs. `history` and `show` name the tags at each save.
- **Whose history a save is in.** One new walk over saves, through every parent, newest first (`ancestry::only_in`): how many saves a line has that nothing else has. It decides whether `line delete` asks.
- **Names.** A new line's or tag's name follows the line-name rules and can't start with `-`. Two lines can't differ only by letter case; neither can two tags made here; a line and a tag can't share a name made here. Names that arrive another way (a Git import, a `.opalro` someone else made) can be anything the stored format allows: for a tag, any text.
- **Git's words.** `checkout -b <name>`, `switch -c <name>`, `branch -m`, `branch -d`, `branch -D` and `tag -d` run the Opalro command that means the same; other forms are explained or refused.
- **Undo.** `opalro undo` and `redo` take the new steps back and forth like any other, and say what came back without naming a save that was never made.

Threat list: `docs/security.md` §4. Decisions 157 to 160 in `docs/decisions/` give the rules this code follows, and the milestone's rulings are in `docs/plans/2026-11-14-milestone-7-rulings.md` if it exists by the time you read this. `docs/terminal.md` says what every command prints for people, `docs/json.md` what it prints for programs, `docs/storage-format.md` §9 what a diary entry and a tag list hold, and `docs/guide.md` what users are told.

Your goals:
- **Data:** lose or corrupt data: saved history, undo history, unsaved work, files outside Opalro. In particular: get saves freed that a person still needs (through `line delete`, a moved or deleted tag, then `opalro tidy`), or make undo unable to bring a line or tag back.
- **The question that wasn't asked:** make `opalro line delete` delete, without asking, a line whose saves nothing else holds; or make it say another line or tag holds them when none does.
- **The wrong save:** make a name resolve to a save other than the one a person would expect (`goto`, `show`, `changes --save`, `tag --save`), or make a save unreachable by its own ID.
- **The person at the terminal:** forge or recolour a line of output, hide text, move the cursor, or make a row that isn't Opalro's read like one (a row of the tag list, a `[tag …]` mark, a question's words, a hint), through a line's or tag's name or a tag's message. Get a raw control character into `--json`.
- **A project that arrives from someone else:** make a `.opalro` with a planted diary, tag list or history change what these commands do beyond what its data may: crash, hang, exhaust memory or disk, loop, or run past the bounds the docs state.
- **Git habits:** find a Git form that now runs an Opalro command meaning something else, or that changes anything when it should have been explained or refused.

## Where the code is

- **The walk** (decision 160): `crates/opal-vcs-core/src/ancestry.rs`: `only_in(repo, tip, others)`, with `Walk`, `Node`, `Tally`. Each save is read once, when first met; a max-heap by saver time; the answer is 0 as soon as the tip gains the others' mark; the walk goes on while a one-mark save waits, a correction waits, or the newest waiting save isn't earlier than the earliest counted one. Its promise: 0 exactly when held, whatever the saves' times; the count exact when no save is older than its parent; too high at worst otherwise, never too low.
- **Lines** (decision 158): `crates/opal-vcs-core/src/lines.rs`: `new_line`, `rename_line`, `delete_line` (its holders: every other line's newest save, every tag's save, every server line's save), `check_new_name`, `name_reason`, `step` (takes the change lock and finishes a stopped switch first), `record`. `resolve_target` is here too. `save --line` from a line: `save_goes_on` in `snapshot.rs`, with the guard against an amend that names a new line.
- **Tags** (decision 159): `crates/opal-vcs-core/src/tags.rs`: `tag`, `delete_tag`, `by_save`, its own new-name check and `record` (the tag list is stored in the same packs as the entry). The tag list is read through `Repository::tag_list` in `repo.rs`, which tells a missing, wrong-kind, undecodable or mismatched record as damage.
- **Names where a save is asked for:** `crates/opal-vcs-core/src/history.rs`: `resolve` (line, tag, change ID, fingerprint), `line_named`, `tag_named`, `others_by_id`, the errors `LineOrSave` and `TagOrSave`.
- **Undo:** `crates/opal-vcs-core/src/undo.rs` (unchanged in what it does; `undo --to` reads an entry's tag list itself before making the entry current); what it prints: `step_line` in `crates/opal-vcs/src/output.rs`.
- **The command line:** `crates/opal-vcs/src/main.rs`: `line_action`, `ask_delete_line`, `tag_list_command`, `tag_command`, `tag_delete_command`, `tag_confirm` and `ask_about_tag` (a second, read-only look at the project, opened only to word a question while the engine holds the lock), `print_step`, `unasked`, `save_named`. Words for people: `line_output.rs`, `tag_output.rs`, `history_output.rs`, `show_output.rs`. Help for a command with forms: `help.rs`.
- **Git's words:** `crates/opal-vcs/src/git_words.rs`: `translate`, `new_line`, `branch`, the `tag -d` arm, the hints.
- **Tests that already pin the basics** (go past them): the engine's `ancestry`, `lines`, `tags` and `history` test modules; `crates/opal-vcs/tests/lines.rs`, `tags.rs`, `undo.rs`, `git_words.rs`, `terminal.rs` (`project_text_is_escaped_with_colour_on`), `model.rs` (random sequences of every command against a model; it has no server lines), `import_vs_git.rs` (the walk against `git rev-list`).

## Places worth attacking

- **The walk, on a history made to mislead it.** A `.opalro` can hold any saves: saves with 1,024 parents, thousands of saves dated alike, clocks that run backwards, times at the ends of what 64 bits hold, one save listed many times among the others, the tip among the others. Try to get `only_in` to answer 0 for a line nothing else holds (then `line delete` asks nothing), to answer above 0 for a held line, to count too low, to never end, or to hold memory out of proportion to the saves stored.
- **Holders that can't be read.** `line delete` gives the walk every tag's save and every server line's save. What does one tag, or one server line, that names a save the store doesn't have do to every `line delete` in the project? And a tag that names something that isn't a save?
- **Delete, then tidy.** Find any sequence of the new commands (with `undo`, `redo`, `undo --to`, `shelf`, `goto`, `save --amend`) after which `opalro tidy` frees a save that a line, a tag, a shelf or a step inside the undo window still needs, or after which `undo` can't bring a deleted line or tag back though the window hasn't passed.
- **A tag that poses as something else.** Tags that arrive from elsewhere can have any name: the name of a line, a name that is the start of a save's change ID or fingerprint, a whole 64-digit fingerprint of another save, a name holding `@` like a server line, a name like an option (`--yes`, `-`), an empty-looking or 255-byte name. For each: what does `goto`, `show`, `changes --save` and `tag --save` do with that text, and can a person still reach the save they meant?
- **Names and messages on screen.** A tag's name and message with escape sequences, U+202E, line breaks, a carriage return, 255 bytes of control characters; a line's name at the edge of the rules. Every place they print: the tag list, `Tagged`/`Moved`/`Deleted` lines, both questions (asked at a faked terminal: build with `--all-features` and set `OPALRO_FAKE_TERMINAL=<width>`), the errors and hints, `history`'s marks, `show`'s `Tags` row, `undo`'s lines, `undo --list`. With colour on and off, at 60, 80 and 120 columns.
- **Many tags.** 100,000 tags (the stored limit), all at one save or spread; names of 255 bytes; messages of 64 KiB. `opalro tag`, `history`, `show`, `goto <tag>`, `tag new-one`, `tag --delete`: time, memory, and what the terminal is sent.
- **A planted diary.** Entries whose command is one of the new names but whose state does something else (a `line delete` that also carries a folder change; a `tag` step whose tag list is missing; a state with two lines alike, or a position on a line that isn't there): what `undo`, `redo`, `undo --list` and `undo --to` do with them.
- **The second look at the project.** While the engine holds the change lock and asks its question, the command line opens the project a second time to word it. What if the project changes under it, the store is damaged, or `.opalro` holds a link where a folder should be?
- **Two commands at once.** `line delete` or `tag` racing a `save`, a `goto`, a `tidy` or another `tag`.
- **A stopped switch.** A `goto` stopped part-way, then each new command: is the switch finished first, and told, on every path (success, refusal, a question answered no)?
- **Git's words.** Every form of `checkout -b`, `switch -c`, `branch` and `tag` you can think of: which run, and is what runs what the Git form means? Names that look like options.
- **`save --line`.** From a line, at a save, with nothing to save, with `--amend`, with paths, with a name that is a tag's.
