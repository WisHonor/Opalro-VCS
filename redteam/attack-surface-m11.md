# Milestone 11 attack surface: short names, empty folders, renames in an import (red-team session RT25, decision 024)

Milestone 11, "Loose ends", is the first of v0.3 ([decision 193](../docs/decisions/193-the-next-version-starts-with-what-v0.2-left.md)). It takes the six things the owner's review of v0.2 put first. Four change what Opalro does; one adds crash tests; one is a measurement that is not merged. The storage format did not change, but **an import now writes something it never wrote before**: move notes, which are part of a save's fingerprint. That makes the import the first thing to attack: a Git repository is the most hostile input Opalro reads.

- **The import notes the renames it is sure of** ([decision 195](../docs/decisions/195-the-import-records-the-renames-it-is-sure-of.md)). For each commit, the first parent's Git tree and the commit's are compared where their Git IDs differ. Each entry is made the way the converter makes it: the same name judgment as `read_folder`, the same kinds, contents and sizes from `blobs`, so a Git LFS file counts by what it holds. A file whose contents left exactly one path and arrived at exactly one path is noted as moved. Links, empty files and project links are never noted. A name the import leaves out, and anything below it, is in no note. A merge notes against its first parent; the first commit notes nothing. The pairing rule is the save's own (`moves::moves_by`, fed from either walk), with the save's bounds: 64 MiB to pair (`MAX_LEFT_BYTES`, counted with the fixed `HELD_PER_PLACE = 203`), then 100,000 notes and 16 MiB of paths (`first_that_fit`). In the code: `Converter::commit` calls `moves_since`, which feeds `moves::moves_by` from `compare`, a walk with an explicit stack that goes into a folder only where its Git IDs differ and merges each folder's entries by name in Opalro's order. `kept` reads a tree and keeps the names `judged` keeps (the same judgment as `read_folder`), and `entry` and `converted` give each side's entry from the converter's memos. A tree that holds one name twice (two files, or a file and a folder) is refused by `parse_tree` (`GitError::Broken`), so the import stops before any comparison meets it. **New bound:** what the comparison reads of Git's trees, cached or not, may be at most the larger of 1 GiB (`MIN_COMPARE_WORK`) and 32 times the bytes of the Git trees the converter has read (`COMPARE_WORK_PER_TREE_BYTE`, `compare_allowance`). Past it the import stops (`ImportError::Stop`), with nothing changed. On git/git the comparison reads 2.05 times what the converter read, and it is 35 to 40 % of the import's time: 0.2 imported it in 123 s and milestone 11 in 170 s, on one runner (docs/benchmarks.md §16).
- **A change ID's start counts from four letters** ([decision 194](../docs/decisions/194-a-change-ids-start-counts-from-four-letters.md)). Text of 1 to 3 letters is always a line or a tag, never a save (`history.rs`, `MIN_SHORT`, `is_change_start`). Text of 1 to 3 letters of k to z that names nothing gets the hint "A save's change ID is typed with at least 4 letters; see your saves with: opalro history". Fingerprint starts still need 8 hex digits.
- **A switch makes no folder that only conflicts standing as nothing fill** ([decision 196](../docs/decisions/196-empty-folders-in-a-switch-and-in-status.md) point 1). The switch makes a folder only if it is saved empty, or something below it is written or kept (project links, names this computer can't write), or it replaces a file (`writeout.rs`: `planned` records `held_empty` and `passed_over`; `made_on_the_way` now runs on every plan).
- **`resolve --keep` takes out a folder it empties that is gone from disk** (point 2). It asks the disk, not the read: `resolve.rs`, the `gone` check through `writeout::Folders`, passed to `kept.rs` `overlay_whole`.
- **`opalro status` shows empty folders, added and removed** (points 3 and 4). Only the innermost is named. A folder holding only ignored files shows as an added empty folder, because that is what a save records. An empty folder in the place of a file gets its own row beside the file's. Rows read `added`/`removed`, the path, then `empty folder`; the count counts folders only when no file changed; `--json` gains `empty_folders: [{"path", "change"}]` (`status.rs` `Difference::EmptyFolder`, `Status.empty_folders`; `main.rs` `status_command`; `output.rs`). `changes` and `show` are unchanged.
- **The words about older versions**: "Opalro before 0.2" where the program said "Opalro 0.1" (`setup_output.rs`, `combine.rs`).
- **The journal left after a finished switch** (flush #10) is put to every command by new crash tests (`recovery.rs`); nothing in the code changed. There are two states.
  - **State A:** the journal is back with `head` on its target, as a lost removal leaves it. Every changing command removes the journal, leaves a file the person edited untouched, warns nothing and does its own work. `undo`, `redo` and `unshelf` say they finished the stopped switch and take no step. `line delete` and `tag --delete` without `--yes` remove the journal, then refuse, since they can't ask without a terminal. Every reading command warns "just after it was done" and exits 0, and `verify` passes.
  - **State B2:** the journal is back after a later command moved `head`. Every changing command refuses with `JournalUnusable`'s words and the hint to delete the journal, and writes nothing; reading commands warn. `setup --upgrade` doesn't look at the journal: it only turns on features. On Windows the removal is written through (decision 076), so B2 can't arise there.

## Places worth attacking

Most valuable first.

1. **An import that notes a move that isn't true**, or two imports of one repository that give different saves. Craft Git repositories: a tree that holds one name twice (as a file and a folder, twice as a file with different contents); names that differ only in letter case, or in Unicode composition, on both sides of a commit; a name the import leaves out (`.opalro`, `.git`, a name that fails validation) as the source or the target of a rename; an LFS pointer and the file it points to swapping places; an LFS object that is missing; submodules (project links) renamed; a file renamed to a folder of the same name; a rename in a merge against each parent; a merge whose first parent is not the one Git's `-M` would compare; contents held twice on one side only. For each: is any note false of the save and its first parent (`moves::true_of`), and does importing twice give the same saves, byte for byte? A note that is false would send `who` and `combine` to the wrong file.
2. **The tree comparison's cost, past its allowance.** Try to make the comparison expensive while staying under the allowance, so the import takes very long without stopping. Use:
   - deep trees and very wide trees;
   - a tree ID repeated thousands of times under different names;
   - 1,000,000 renames in one commit;
   - trees whose IDs differ while their contents don't, such as two Git LFS pointers to one file, or a CRLF pointer and an LF one;
   - a history of 100,000 commits, each renaming everything;
   - work the allowance doesn't count: path strings built for every entry, `moves_by`'s second walk, `converted` lookups.

   Also try to make an honest-looking history stop. The sandbox has 4 GB. Check two things: is the walk's time bounded by what the allowance counts, and is the point where the save's own bounds cut pairing short the same on every run?
3. **Notes that send `who` or `combine` somewhere wrong** in imported history: a rename chain a→b→a, a rename and a file put back at the old name in one commit, a rename on both lines before a combine, a rename of a file that is in conflict on the other line.
4. **A short name that reaches a save it shouldn't.** Lines and tags named with 1 to 3 letters of k to z, 4 letters (where a clash is still possible), names that are also hex; `goto`, `show`, `combine`, `who --save`, `history <name>`, `undo --to`; a line named like a save's start that is then deleted. Does any 1-to-3-letter text ever reach a save, and does any hint carry text from the project?
5. **A folder made or not made so that a person's file is lost or `status` lies.** Folders that only conflicts standing as nothing fill, under folders that do hold files, under project links, under names this computer can't write; a file where such a folder goes; `goto`, `discard`, `discard <folder>`, `shelf`, `unshelf`, `undo`, `redo`, `undo --to`, `combine`, `resolve`. Try this sequence from Task 3's review: a combine leaves a folder that only conflicts fill, `mkdir` that folder, run a command that removes it, then `undo`. Does the folder come back? Does `status` ever list a folder that a save would not record, or miss one it would?
6. **`resolve --keep` taking out a folder that holds the person's work**: a folder that is on disk but can't be opened, a link where the folder was, a folder made between the read and the check, a folder in another letter case.
7. **The journal of a finished switch, made hostile.** Make a journal that names another target, a journal of 0 bytes, and a journal written back after a later command, and run every command against each. The tests pin that every changing command but `setup --upgrade` refuses a journal it can't finish, and that reading commands warn. Look for a command that writes before it looks, a refusal that leaves something half done, and `setup --upgrade` turning a feature on beside a journal it never read.
8. **What a person is shown**: an empty folder's path with escape sequences, bidi controls or a newline in `status` and in its `--json`.

## Known and not settled (do not report these as findings; prove them worse or put them to rest)

- An import gives different fingerprints than 0.2's from the first exact rename on; change IDs stay (decision 195).
- `who` doesn't follow a rename with edits in imported history (Git's own README.md, for one).
- `resolve --keep`'s check counts every error opening the folder as "gone", so a folder that can't be opened is taken out of the new save; the next save records it again (Task 3's review, Minor 2).
- Pairing near its 64 MiB bound may depend on the order the walk hands paths over: a save walks in Opalro's order, and the import's comparison merges each folder's entries in Opalro's order too (Task 5's review, Minor 1). Show whether one repository can ever be imported two ways.
- An honest history that goes back and forth between the same big folders more than about 30 times stops the import: for example, a folder of 100,000 files renamed back and forth about 57 times. 0.2 imported it, without notes. The other way would have been to keep importing and stop noting moves; that is for the owner to confirm.
- The comparison builds a path string for every entry it walks, even one it skips (Task 6's review, Minor 4), so its time is not exactly what the allowance counts.
- The journal left after a finished switch, back after a later command moved `head`, makes every changing command refuse until it is deleted (Task 7).
