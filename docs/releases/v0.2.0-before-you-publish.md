# Before you publish v0.2

This page is for you, the owner. It stays in the repository and never goes on the website. It lists what only you can do before v0.2 goes out, in the order to do it. It was written on 2026-11-16, with the version change and the release notes ([decision 187](../decisions/187-v0.2s-package.md)).

**Where things stand.** v0.2 is milestones 7 to 10: lines and tags, combining lines, conflicts kept and fixed later, and `opalro who`. It lives on the branch `v0.2`, which says version 0.2.0, while `main` still says 0.1.0. Nothing has been tagged, drafted, merged into `main` or opened as a pull request: those steps are yours. v0.1's own draft, "Opalro 0.1.0", still waits for you too ([its list](v0.1.0-before-you-publish.md)).

The short version: publishing is the one step that can't be fully taken back. Once a person has saved a project with v0.2, every later Opalro must read it. So rule on the agreement's sentence, try it, read the lists, and only then publish.

**In plain words.** Every archive carries the user agreement, and one sentence in it names the version. It was written for 0.1, and nobody but you may change what the agreement says ([decision 156](../decisions/156-the-user-agreements-blanks-filled-by-the-owner.md): you filled its blanks yourself). So it was left exactly as it is.

The sentence is in [USER-AGREEMENT.md](../../USER-AGREEMENT.md), line 51, under liability:

**What to decide:** whether it should say something else for 0.2. If 0.2 is also free, the simplest change is "nothing: Opalro is free", which no later free version needs to touch again. If you want a lawyer's view first, part 4 of [v0.1's list](v0.1.0-before-you-publish.md#4-what-a-lawyer-should-read) says what a lawyer should read.

**What to do:** tell Claude your wording, or edit line 51 yourself on the branch `v0.2`. To check it afterwards, in Git Bash: `grep -n "0.1 is free" USER-AGREEMENT.md` should print nothing if you changed it, and `grep -n "Opalro is free" USER-AGREEMENT.md` (or your own words) should print line 51. A change to the agreement makes the release workflow run on its own for any pull request that carries it, so it is checked like everything else.

## 2. Try it

Use an archive the release workflow built, not a program built on your own machine: the point is to try what people will get. Until `v0.2` is merged into `main`, the newest such archive is in the workflow's run on the branch `v0.2` (decision 187 had the workflow run there, every job but the draft). In PowerShell:

```text
gh run list --workflow release.yml --branch v0.2 -L 1 --json databaseId,conclusion
```

It prints the newest run's `conclusion` and `databaseId` (as JSON, which a terminal may spread over a few lines): `conclusion` must be `success`, and `databaseId` is the run's number. Then download the Windows archive from that run (put in the number):

```text
gh run download <the run's number> -n opalro-0.2.0-x86_64-pc-windows-msvc.zip -D $HOME\opalro-0.2-try
```

The folder `opalro-0.2-try` then holds `opalro-0.2.0-x86_64-pc-windows-msvc.zip`. Follow [the guide](../guide.md) §2 from "Put `opalro` on your PATH", exactly as a stranger would, then check:

```text
opalro --version
```

It should print `opalro 0.2.0`. If it prints `opalro 0.1.0`, your PATH finds the old program first: the guide's §2 says what to do.

**First, everything you tried for v0.1 (about 40 minutes).** Do part 1 of [v0.1's list](v0.1.0-before-you-publish.md#1-what-to-try-yourself) again with this program: a copy of a project of your own, the corners, a Git import, and a OneDrive folder. Everything there should behave as it did with 0.1.

**Then what is new (about 20 minutes).** In a new, empty folder, in PowerShell. (`Set-Content … -Encoding ascii` writes plain text in every PowerShell. In Windows PowerShell 5.1, the one Windows ships, `>` may write a kind of text Opalro reads as not text, and `-Encoding utf8` starts the file with an invisible mark that `opalro who` then shows as `\u{feff}`; PowerShell 7 writes no such mark. The steps work in both.)

What each step prints is shown below as it was printed when these steps were run on 2026-11-16, with three kinds of differences: a change ID (four letters, such as `lwnn`) and a fingerprint (twelve digits and letters) are your own, shown here as `<id>` and `<fingerprint>`; your name and the date are yours; and in a terminal Opalro adds a line or two that a script doesn't get (a `Next:` line, `Changed your mind? opalro undo`), and shows `│` where a script gets `|`. Where such a line matters, it is said.

```text
mkdir $HOME\opalro-try-lines
cd $HOME\opalro-try-lines
opalro start --preset code
Set-Content todo.txt "buy milk" -Encoding ascii
opalro save "First list"
opalro line new menu
Set-Content todo.txt "buy milk and bread" -Encoding ascii
opalro save "Bread"
opalro goto main
Set-Content todo.txt "buy milk and eggs" -Encoding ascii
opalro save "Eggs"
opalro combine menu
```

The last command prints:

```text
Combined menu into main: save <id> "Combine menu into main", with 1 place in conflict:
  todo.txt: changed on both lines, in the same place; marked in the file (1 place)

    1 file written.
```

In a terminal, then `Next: fix the marked files and pick a version for the rest, then run opalro resolve. opalro status lists what is left.` and `Changed your mind? opalro undo`.

```text
opalro status
notepad todo.txt
```

`opalro status` prints:

```text
On line main at save <id> "Combine menu into main"  (just now)

In conflict (1 place):

    todo.txt  1 marked place left to fix
```

In Notepad, the file holds both versions, and the one they started from, between marker lines:

```text
<<<<<<< main (<id>)
buy milk and eggs
||||||| where the lines parted (<id>)
buy milk
=======
buy milk and bread
>>>>>>> menu (<id>)
```

(Here `<id>` is eight letters.) Replace all seven lines with the line you want, such as `buy milk, eggs and bread`, save and close. Then:

```text
opalro resolve
opalro status
opalro history
opalro who todo.txt
```

`opalro resolve` prints `Recorded 1 fix in save <id> "Combine menu into main" on main.`, then after an empty line `    The combined save now holds it; its ID stays the same.` `opalro status` then prints its first line, then `Nothing changed since then.` `opalro history` prints:

```text
Saves on line main, newest first:

> <id>  just now  <your name>  Combine menu into main  [main]  [combined <fingerprint>]
  <id>  just now  <your name>  Eggs
  <id>  just now  <your name>  First list
  <id>  just now  <your name>  Start project
```

And `opalro who todo.txt`:

```text
Each line of todo.txt and the save it is from:

<id>  <your name>  <today's date>  1 │ buy milk, eggs and bread
```

The save it names is the combined save, since you wrote that line while fixing. Had you kept one of the two lines as it was, it would name "Bread" or "Eggs" instead.

Now a tag, and the amend that must be refused:

```text
opalro tag v1.0 "Tried v0.2"
opalro tag
opalro line new side
opalro goto main
Set-Content notes.txt "one more" -Encoding ascii
opalro save --amend
```

`opalro tag v1.0 …` prints `Tagged save <id> "Combine menu into main" as v1.0.`, and `opalro tag` prints `1 tag:`, an empty line, and `  v1.0  <fingerprint>  "Tried v0.2"`. The last command must be refused and change nothing:

```text
error: Opalro can't amend this save: line side and tag v1.0 show it too, and two saves you can see would then share one change ID.

hint: Nothing was saved. Save your changes as a new save instead: opalro save "describe your change"
```

Then `opalro save "One more"` works: `Saved <id> "One more" on main  (1 file)`.

Then take it back, one step at a time. Run `opalro undo` five times; each says what it took back:

```text
Undid save <id> "One more": main is back at <id>; its changes show as unsaved.
Undid goto: back on side at <id>.
Undid line new: line side is gone, back on main at <id>.
Undid tag: the tags changed back.
Undid resolve: main is back at <id>.
```

Undoing the fix leaves your fixed `todo.txt` in the folder, as unsaved work, and the combine wrote that file, so a sixth plain `opalro undo` stops and changes nothing:

```text
error: Your unsaved changes, or files Opalro ignores, are where the undo would write, so that step changed nothing:
  todo.txt

hint: Run opalro undo --shelve to set your changes there aside on a new shelf, as part of the same step. Saving, shelving or discarding them first won't help: each is a step of its own, which the next undo would take back. Files Opalro ignores, and unsaved links that could come back only as plain files, aren't set aside: move them somewhere else first.
```

Run what the hint says:

```text
opalro undo --shelve
```

It prints `Shelved your unsaved changes in the way on shelf 1.` and `Undid combine: main is back at <id>, 1 file written.` (in a terminal, then `Next: bring your changes back with: opalro unshelf`). `opalro history` and `opalro line` now show `main` back at "Eggs", and `menu` still there. `notes.txt`, from the undone "One more", is still in the folder as unsaved work: `opalro status` lists it as `added  notes.txt  10 B`. `opalro redo` brings the combine back, with the marked file: `Redid combine: main is at <id> again, 1 file written.` Your fix waits on shelf 1, for `opalro unshelf`.

**A project made with 0.1 (about 10 minutes).** Work on a copy, never the original: a copy of the project you tried v0.1 on, `.opalro` included, is ideal. In the copy:

```text
opalro setup
opalro setup --upgrade
```

`opalro setup` lists the project's rules and ends with `Upgrade available: conflicts (opalro setup --upgrade)` (in a terminal, a `Next:` line follows). `opalro setup --upgrade` prints:

```text
This version of Opalro can turn on 1 feature in this project:
  conflicts: a combine can keep conflicts, and you fix them when you choose.
Once it is on, Opalro 0.1 can't open this project, and opalro undo can't turn it off.
```

then asks `Turn it on? [y/N]`: answer `y`. It says `Turned on conflicts: this project can keep conflicts now.` (When these steps were run, a made-up 0.1 project stood in, and `--yes` answered the question, since a script can't be asked.) If you still have the 0.1 program, run its `status` in that copy: as decision 178 says, 0.1 says the project is newer and asks to be updated, and changes nothing. The exact words are 0.1's own and aren't quoted on any page: copy them if anything else happens.

While you try, look for: a message you don't understand, a `Next:` line that suggests the wrong thing, anything slow, and anything that changed a file you didn't expect. Copy the exact text of anything strange.

When you are done, delete the try folders. You will try once more, briefly, on the draft itself (part 7).

## 4. Rule on the speed write-up

**In plain words.** Opalro's own bar is to take at most twice Git's time. Going back to another save (`opalro goto`) was to meet it in v0.2. It doesn't on Linux in seven of the eight runs of the speed check on GitHub's machines: the release notes say so plainly, with the numbers, as v0.1's did. A `goto` waits for the disk ten times (flushes); [benchmarks.md](../benchmarks.md) §15 says what each one is for. Nothing about them was changed without you ([decision 186](../decisions/186-speed-before-v0.2.md)).

**What was measured:** timers inside the program, on GitHub's Linux machine with an AMD EPYC 7763, put the ten flushes at 3.277 ms of a 30.57 ms `goto` (10.7 %); on its Windows machine, with an Intel Xeon Platinum 8573C, 0.925 ms of 60.75 ms. That is another processor than the speed check's newest run (an AMD EPYC 9V74), so the two aren't to be added up or set against each other.

**What to read:** [benchmarks.md](../benchmarks.md) §15, "v0.2, milestone 10", and above all its part "For the owner's ruling: what each flush is for": one row per flush, what it protects, and what it costs. Its part "Where `status` and `goto` spend their time: the timers" has the measurements above, and "The gate on milestone 10's code" the newest run of the speed check.

**The question:** may anything about these flushes change?

**What to decide** (decision 186 point 4): publish v0.2 with `goto` over twice Git's time on Linux, as the notes and the guide now say it is packaged; or wait while some of the flushes are looked at, which needs its own decision. Tell Claude which; a decision record follows. If you choose to wait, the notes' first known limit and the guide's "Where Git and Git LFS still do better" change with it.

## 6. Merge `v0.2` into `main`

**In plain words.** `main` is what releases are made from, and only you put anything there. Merging brings v0.2's work, version number and documents into `main`. Do this only after milestone 10's red-team session and review are done and the milestone is merged into `v0.2` (Claude says so when it is).

In PowerShell, in the repository's folder:

```text
gh pr create --base main --head v0.2 --title "Opalro 0.2.0" --body "v0.2: milestones 7 to 10."
gh pr checks v0.2 --watch
```

`gh pr create` prints the pull request's address. `gh pr checks v0.2 --watch` waits until every check is done. Every check must pass but one: CI's (the three `test` jobs and `deny`) and the release workflow's `prepare`, the four `build`s, `sums`, the `clean-machine` checks and the `ordinary-computers` checks (the release workflow runs on this pull request because it changes `docs/releases/`). Its `release` job shows as skipped: by the workflow's own rule it runs only when started by hand from `main` (part 7). A skipped `release` is not a failure. If GitHub says the pull request has conflicts (likely if v0.1's "v0.1 published" pull request was merged first, since both change documents), ask Claude to resolve them on `v0.2`, and wait for the checks again. Then:

```text
gh pr merge v0.2 --merge
```

It should say the pull request was merged. `git fetch` then `git log origin/main --oneline -1` shows the merge.

## 7. Start the release workflow from `main`

First check that CI passed on `main`'s newest commit:

```text
gh run list --workflow ci.yml --branch main -L 1
```

It must show the run as finished and successful (a tick, or `success`). If it is still running, wait and ask again. Then start the release:

```text
gh workflow run release.yml --ref main
gh run watch
```

`gh run watch` asks which run to watch: pick the newest "Release". Every job must end with a green tick: `prepare`, the four `build`s, `sums`, the `clean-machine` checks, the `ordinary-computers` checks and `release`, which this time runs, since the run was started by hand from `main`. The run stops if CI hasn't passed on that commit, or if a release named `v0.2.0` already exists, drafts included.

When it is done, `gh release view v0.2.0` shows the draft "Opalro 0.2.0", marked as a draft, with six files: the four archives (`opalro-0.2.0-x86_64-pc-windows-msvc.zip`, `opalro-0.2.0-x86_64-unknown-linux-gnu.tar.gz`, `opalro-0.2.0-aarch64-apple-darwin.tar.gz`, `opalro-0.2.0-x86_64-apple-darwin.tar.gz`), `SHA256SUMS` and `opalro-0.2.0-website.zip`. It publishes nothing and makes no tag.

**Try the draft, briefly.** Download the Windows archive and `SHA256SUMS` from the draft (`gh release download v0.2.0 -p "*windows*" -p SHA256SUMS -D $HOME\opalro-draft`), check it as the guide's §2 says, and run `opalro --version`: `opalro 0.2.0`.

## 8. Publish the draft

1. **Check the files.** The run's log prints a SHA-256 for each file. Compare them with `SHA256SUMS` in the draft (as v0.1's list, part 7, did).
2. **Read the notes** on the draft's page: they are [v0.2.0.md](v0.2.0.md) word for word, plus one last line.
3. **Delete the "Made by" line.** The notes end with a line naming the workflow run that made the draft, as a link into the repository. It tells you which run's log to compare with (step 1). Once checked, delete it: on the draft's page choose "Edit", remove the line, and save the draft. The published page must not point into the private repository.
4. **Publish.** On the same "Edit" page, choose "Publish release". Or, in PowerShell: `gh release edit v0.2.0 --draft=false`. This creates the tag `v0.2.0` on the commit the archives were built from. `gh release view v0.2.0` then no longer says draft. From this moment, people can save projects with 0.2, and every later Opalro must read them.
