Opalro 0.2 is the first published version of Opalro, a version control system for code and large binary files together, with its own engine and storage format: it is not built on Git.

It is an early release, for one person on one computer. There is no server yet, so no sharing and no locking. Keep another copy of anything that matters.

## What it does

- **Saves and history:** `start`, `save`, `status`, `changes`, `history`, `show`, `goto`, `discard`. A save is a photo of your whole project folder; you can look at any save again, or go back to it.
- **Lines:** a line is a row of saves under a name, like `main`, to try an idea without touching your other work. `opalro line new <name>` starts one at the save you are on and moves you onto it; `opalro line` lists them, and `opalro line rename` and `opalro line delete` rename and delete one.
- **Combining lines:** `opalro combine <line>` brings that line's work into the one you are on, in one combined save. Text files that both lines changed in different places are merged line by line.
- **Conflicts kept, and fixed when you choose:** where both lines changed the same place, the combine goes through and keeps the conflict. A text file gets marker lines for you to fix in your editor; anything else stays as your line has it. `opalro status` lists what is left to fix, and `opalro resolve` records your fixes. `opalro combine --only-if-clean` stops instead, for scripts.
- **Moves recorded in saves:** when a file moves unchanged, the save notes the move, so a combine brings the other line's changes to the file where it is now.
- **Tags:** `opalro tag v1.0` gives the save you are at a name that stays with it; `opalro tag` lists them and `opalro tag --delete` deletes one.
- **`opalro who <file>`:** the save behind each line of a file, who made it and when, like Git's `blame`.
- **Shelves:** `shelf` and `unshelf` put changes aside and bring them back.
- **Undo for everything:** `opalro undo` takes back any command that changed something, and `opalro redo` brings it back. Two things it doesn't take back: `opalro tidy`, which frees space, and `opalro setup --upgrade`.
- **Fixing the last save:** `opalro save --amend` replaces your line's newest save, keeping its change ID. It is refused when another line, a tag or a server line has that save in its history, since two saves you can see would then share one change ID: it says which ones (`error: Opalro can't amend this save: line side and tag v1.0 show it too, …`), saves nothing, and suggests saving your changes as a new save instead.
- **Presets:** `opalro start` asks what kind of project it is (Game, Code or Custom); Game and Code write their rules into `opalro.toml` and `.opalroignore`, and `opalro setup` shows them and switches presets.
- **Big files:** cut into chunks, so a change to part of a file stores only the part that changed.
- **Coming from Git:** `opalro import` brings in a Git repository, Git LFS files included, and never changes the Git repository. Git's own words (`commit`, `branch`, `merge`, `blame` and more) run or explain the Opalro command that does the same.
- **Looking after a project:** `tidy` and `verify`.

What Opalro writes on disk is described in the storage format, published on https://opalro.com, and frozen from this version: every later Opalro reads what Opalro 0.2 writes.

**Speed:** measured against Git and Git LFS on GitHub's Linux and Windows machines, the losses included; the benchmarks are published on the same page. All the numbers here are from GitHub's machines (its runners). On Git's own source, Opalro's first save takes about a fifth of Git's time on Linux and a tenth to an eighth on Windows, a small save is level with Git on Linux and quicker on Windows, and saving a 10 GiB file peaked at 44 MB of memory: these were measured on 2026-11-10 and 2026-11-11, before lines and combining were built, and not measured again. The cases where Git or Git LFS came out ahead are under "Known limits" below.

## Download

From https://opalro.com: one archive per system, `opalro-0.2.0-x86_64-pc-windows-msvc.zip` for Windows, and `.tar.gz` archives for Linux (`x86_64-unknown-linux-gnu`) and macOS (`aarch64-apple-darwin` for Apple silicon, `x86_64-apple-darwin` for Intel). Each holds six files: the program, `README.md`, the user guide (`docs/guide.md`), the user agreement (`USER-AGREEMENT.md`), and the notices for the code of other people built into Opalro (`THIRD-PARTY-LICENSES.html` and `THIRD-PARTY-LICENSES-RUST.html`).

What each system needs:

- **Windows:** Windows 10 or 11, or Windows Server 2016 or later, on a 64-bit Intel or AMD processor.
- **Linux:** a 64-bit Intel or AMD processor, and glibc 2.34 or newer (Ubuntu 22.04, Debian 12, Fedora 35, RHEL, AlmaLinux and Rocky Linux 9, and later).
- **macOS:** macOS 11 or later, on Apple silicon or Intel.

Nothing else needs to be installed.

`SHA256SUMS`, on the same page, lists a SHA-256 for each archive. The guide's section 2, "Installing", has the command that checks a download on each system. A match says the file arrived whole and is the one put on the page; it doesn't say who made it, since nothing is signed.

## Not signed

The programs aren't signed. On Windows, SmartScreen may say "Windows protected your PC" when Opalro is started from Explorer (choose "More info", then "Run anyway"); started from a terminal it usually says nothing. On macOS, a program unpacked by double-clicking the archive is blocked on its first run, even from Terminal (System Settings, Privacy & Security, "Open Anyway"); unpacked with `tar` in Terminal, it isn't. The guide's "Installing" section has the steps. Signing is planned.

## Closed source

Opalro is closed source: you may use it under the user agreement, `USER-AGREEMENT.md`, in every archive.

## What it doesn't do yet

No server (so no sharing and no locking), no moving saves from one line to another (Git's `cherry-pick` and `rebase`), no guessed moves (a file moved and changed in the same save counts as one file removed and another added), and no merge programs: Opalro doesn't start one for a conflict. No repair either (`opalro verify` finds damage but can't fix it), and no export to Git. The guide's section "What v0.2 doesn't do yet" lists them all, and its section "Stopping" says how to remove Opalro, or leave a project, without losing files.

## Known limits

All the numbers here are from GitHub's machines, and are published with the benchmarks on https://opalro.com.

- **Going back to another save is slower than Opalro's own bar on Linux.** The bar is twice Git's time. In nine runs of Opalro's speed check on v0.2's code (eight as it was being built: four on milestone 7's, at `24357e1` and `26e910a`; one on milestone 8's, at `f5317d3`; two on milestone 9's last, at `a695479`; and one on milestone 10's, at `11a2bb9`, before its last change for speed; and one on the code as packaged, at `af19793`), `opalro goto` took between 1.93 and 2.74 times Git's time on Linux, and was under twice in only one; on the code as packaged it took 2.125 times; how far over depends on the runner's processor, so no single run is the answer. On Windows it was under twice where the runs printed their numbers (1.654 on the code as packaged). The speed check holds `goto` to three and a half times Git's time, and twice stays the goal.
- **`opalro status` is at its limit on Linux on some machines.** With nothing changed, it is held to twice Git's time, and the check fails past that. In the same nine runs it took 1.68 to 2.29 times Git's time on Linux, and 1.824 on the code as packaged: over twice in five, four of them on one processor type (Intel Xeon 6975P-C), where Git took 6.1 to 6.6 ms, and one on another (Intel Xeon Platinum 8573C); under it on the others. On the first of these processors the benchmarks found that Git's time decides the ratio, and that Git got quicker when GitHub changed its machines' software image. It is a matter of milliseconds (13 to 22 ms against Git's 6 to 13).
- **`opalro who` is slower than `git blame`, and doesn't follow everything Git follows.** On five files of Git's own history it took 3.0 to 5.0 times `git blame`'s time in a run on milestone 10's code at `11a2bb9`, and 3.6 to 4.9 times in a run on the code as packaged, at `af19793`. On four of them the two named the same commit for 90 to 100 % of the lines, and for two thirds of the fifth, which had been renamed. Most of the lines where they differ (871 of 930) hold text that appears more than once in the file, where which save wrote the line can't be checked without comparing versions: a looser check agreed with `who` on 821 of them, and the other 50 weren't looked at one by one. Where a line's text appears once, the save `who` named passed a check that it wrote the line in 47 cases (16 of them only because the check can't see the rename of `README.md`) and failed it in the other 10, all lines that moved; no line was found where `who` named a save that neither wrote nor moved it. In history imported from Git, `who` follows no renamed file, since the import records no moves. Where a combine took the other line's version of a file whole, `who` still names your line's save for a line both lines wrote, where `git blame` names the other line's. And `who` changes nothing in the project, but makes an empty file in `.opalro/tmp` for a moment, and removes it again, to learn how the drive compares names: where it can't, it stops with `error: Opalro couldn't make a file in <folder>: <why>`, as every command given a path does.
- **An amend can take seconds in a project with hundreds of lines,** when Opalro has no note of the save being amended: 2.84 s on Linux and 10.64 s on Windows with 300 old lines of 2,000 saves each. Right after a save, which leaves that note, the same amend took 4.35 ms on Linux (milestone 10's code at `7576db0`, one run each).
- **Where else Git or Git LFS came out ahead,** measured on 2026-11-10, before lines and combining were built, and not measured again: a switch that rewrites thousands of files takes 1.8 to 3.1 seconds against Git's 0.46 to 0.75 (3,557 files, Linux); the whole history listing 1.5 to 2 times Git's time; on a slow disk, Git LFS is quicker at the first save of big files that don't compress, and Git at going back to an old version of a big file. A long history takes more space than Git's (64.6 GB against 6.6 GB for Linux's history, 369 MB against 314 MB for Git's own), since Opalro doesn't store versions as differences yet, and importing Linux's history peaks at 3.4 GB of memory. The guide's section "Where Git and Git LFS still do better" lists every case with its numbers.
- **Some places Opalro can't work well yet:** a file another program holds open on Windows stops the commands that write it; online-only files of sync tools other than OneDrive stop `opalro save` and `opalro status`; on Windows, a project on a FAT or exFAT drive (most USB sticks and SD cards) can't be used, nor can a project be started in a folder whose path is longer than about 250 characters; on some network shares, `safe-folders` entries don't count. "Known problems", on https://opalro.com, says what to do about each.

## Problems

Write to support@opalro.com. A security problem goes to the same address, privately, with "security" in the subject.

## For scripts

Every command can print `--json`. The formats are described in the `--json` reference, published on https://opalro.com, and frozen from this version (`opalro_json` 1): within it, a field is never removed, renamed or given another meaning.

## If you used a build from before 0.2

A project made with an earlier build opens as it is. To keep conflicts, it needs `opalro setup --upgrade` once: it says what that allows and asks first, and it can't be undone. What Opalro writes is kept readable by every later Opalro from 0.2 on.
