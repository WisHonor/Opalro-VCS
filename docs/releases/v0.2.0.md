Opalro v0.2 is the second release of Opalro, a version control system for code and large binary files together, with its own engine and storage format: it is not built on Git.

It is still an early release, for one person on one computer. There is no server yet, so no sharing or locking. What is new is working with more than one line: making and naming lines, tagging saves, bringing one line's work into another, and fixing what clashes when you choose.

## What is new

- **Lines, made, renamed and deleted:** `opalro line new <name>` starts a line at the save you are on and moves you onto it; `opalro line rename` and `opalro line delete` rename and delete one. `opalro undo` takes back each.
- **Tags:** `opalro tag v1.0` gives the save you are at a name that stays with it; `opalro tag` lists them and `opalro tag --delete` deletes one.
- **Combining lines:** `opalro combine <line>` brings that line's work into the one you are on, in one combined save. Text files that both lines changed in different places are merged line by line.
- **Conflicts kept, and fixed when you choose:** where both lines changed the same place, the combine goes through and keeps the conflict. A text file gets marker lines for you to fix in your editor; anything else stays as your line has it. `opalro status` lists what is left to fix, and `opalro resolve` records your fixes. `opalro combine --only-if-clean` stops instead, for scripts.
- **Moves recorded in saves:** when a file moves unchanged, the save notes the move, so a combine brings the other line's changes to the file where it is now.
- **`opalro who <file>`:** the save behind each line of a file, who made it and when, like Git's `blame`.
- **A safer amend:** `opalro save --amend` is refused when another line, a tag or a server line has the save in its history, since two saves you can see would then share one change ID. It says which ones (`error: Opalro can't amend this save: line feature shows it too, …`), saves nothing, and suggests saving your changes as a new save instead.

## For a project made with v0.1

It opens as it is: Opalro 0.2 reads everything 0.1 wrote, and the storage format is still format 1.

To keep conflicts, such a project needs `opalro setup --upgrade`, once. It says what the new feature allows and asks first. **After it, Opalro 0.1 can't open the project,** and `opalro undo` can't turn the feature off. Until then, a combine that would leave a conflict stops and changes nothing. **A project started with 0.2 can't be opened by Opalro 0.1 either.** To keep using 0.1 on a project, copy the project folder, `.opalro` included, before you upgrade it.

## Download

From https://opalro.com: one archive per system, `opalro-0.2.0-x86_64-pc-windows-msvc.zip` for Windows, and `.tar.gz` archives for Linux (`x86_64-unknown-linux-gnu`) and macOS (`aarch64-apple-darwin` for Apple silicon, `x86_64-apple-darwin` for Intel). Each holds six files: the program, `README.md`, the user guide (`docs/guide.md`), the user agreement (`USER-AGREEMENT.md`), and the notices for the code of other people built into Opalro (`THIRD-PARTY-LICENSES.html` and `THIRD-PARTY-LICENSES-RUST.html`).

What each system needs:

- **Windows:** Windows 10 or 11, or Windows Server 2016 or later, on a 64-bit Intel or AMD processor.
- **Linux:** a 64-bit Intel or AMD processor, and glibc 2.34 or newer (Ubuntu 22.04, Debian 12, Fedora 35, RHEL, AlmaLinux and Rocky Linux 9, and later).
- **macOS:** macOS 11 or later, on Apple silicon or Intel.

Nothing else needs to be installed.

`SHA256SUMS`, on the same page, lists a SHA-256 for each archive. The guide's section 2, "Installing", has the command that checks a download on each system. A match says the file arrived whole and is the one put on the page; it doesn't say who made it, since nothing is signed.

## Not signed

The programs aren't signed. On Windows, SmartScreen may say "Windows protected your PC" when Opalro is started from Explorer (choose "More info", then "Run anyway"); started from a terminal it usually says nothing. On macOS, a program unpacked by double-clicking the archive is blocked on its first run, even from Terminal (System Settings, Privacy & Security, "Open Anyway"); unpacked with `tar` in Terminal, it isn't. The guide's "Installing" section has the steps. Signing is planned.

## Closed source

Opalro is closed source: you may use it under the user agreement, `USER-AGREEMENT.md`, in every archive.

## Still missing

No server (so no sharing and no locking), no moving saves from one line to another (Git's `cherry-pick` and `rebase`), no guessed moves (a file moved and changed in the same save counts as one file removed and another added), and no merge programs: Opalro doesn't start one for a conflict. Also still missing, as in v0.1: repair (`opalro verify` finds damage but can't fix it) and export to Git. The guide's section "What v0.2 doesn't do yet" lists them all, and its section "Stopping" says how to remove Opalro, or leave a project, without losing files.

## Known limits

All the numbers here are from GitHub's machines (its runners), and are published with the benchmarks on https://opalro.com.

- **Going back to another save is slower than Opalro's own bar on Linux.** The bar is twice Git's time. In eight runs of Opalro's speed check on v0.2's code, `opalro goto` took between 1.93 and 2.74 times Git's time on Linux, and was under twice in only one; how far over depends on the runner's processor, so no single run is the answer. On Windows it was under twice where the runs printed their numbers (1.66 in the newest that did). As in v0.1, the speed check holds `goto` to three and a half times Git's time, and twice stays the goal.
- **`opalro status` is at its limit on Linux on some machines.** With nothing changed, it is held to twice Git's time, and the check fails past that. In the same eight runs it took 1.68 to 2.29 times Git's time on Linux: over twice in five, all on runners whose processor makes Git quick; under it on the others. It is a matter of milliseconds (13 to 22 ms against Git's 6 to 13).
- **`opalro who` is slower than `git blame`, and doesn't follow everything Git follows.** On five files of Git's own history it took 3.0 to 5.0 times `git blame`'s time. On four of them the two named the same commit for 90 to 100 % of the lines, and for two thirds of the fifth, which had been renamed. Most of the lines where they differ hold text that appears more than once in the file, where either answer can be defended, and no line was found where `who` named a save that neither wrote nor moved the line. In history imported from Git, `who` follows no renamed file, since the import records no moves. Where a combine took the other line's version of a file whole, `who` still names your line's save for a line both lines wrote, where `git blame` names the other line's. And `who` changes nothing, but can't run on a project that can't be written at all.
- **An amend can take seconds in a project with hundreds of lines,** when Opalro has no note of the save being amended: 2.84 s on Linux and 10.64 s on Windows with 300 old lines of 2,000 saves each. Right after a save, which leaves that note, the same amend took 4.35 ms on Linux.
- **What v0.1's known problems said, and still holds:** a file another program holds open on Windows stops the commands that write it; online-only files of sync tools other than OneDrive stop `opalro save` and `opalro status`; on Windows, a project on a FAT or exFAT drive (most USB sticks and SD cards) can't be used, nor can a project be started in a folder whose path is longer than about 250 characters; on some network shares, `safe-folders` entries don't count. "Known problems", on https://opalro.com, says what to do about each.

## Problems

Write to support@opalro.com. A security problem goes to the same address, privately, with "security" in the subject.

## For scripts

Every command can print `--json`, and the format is still `opalro_json` 1, as in v0.1: nothing was removed, renamed or given another meaning. v0.2 adds documents for its new commands (`line new`, `line rename`, `line delete`, `tag`, `combine`, `resolve` and `who`) and new fields in some existing ones. A field whose values are a fixed list of codes, such as a change's `change`, can take a value v0.1 never gave it only in a project that keeps conflicts. The `--json` reference, published on https://opalro.com, describes every document and field.
