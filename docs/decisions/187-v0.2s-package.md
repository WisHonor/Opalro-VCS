# 187 — v0.2's package: what changes with the version, and where the work stops

- **Status:** Accepted
- **Date:** 2026-11-15
- **Agenda topic:** none (milestone 10 planning)
- **Decided by:** Claude, at the owner's request while the owner was away. The owner can reverse any part.
- **Refines:** [decision 157](157-v0.2-in-four-milestones.md) (v0.2 is packaged up to, but not including, publishing; `main` stays what v0.1 is released from); [decision 145](145-one-release-workflow-for-every-version.md) (how a release is made: the version and its notes in one commit, the workflow started from `main`, the owner publishes the draft)

## Context

**In plain words.** A release is a set of files a stranger can download and run: the program for each system, the guide, the agreement, the lists of other people's code, and a page of notes saying what is new and what is still missing. v0.1's set was made by one workflow that builds the files on GitHub's machines, tries them on machines with nothing installed, and, only when started from `main`, puts them into a draft release that the owner publishes.

v0.2 is not on `main`. It lives on the branch `v0.2`, which goes into `main` only by the owner's hand, and v0.1's own draft still waits for the owner. So the question is how far "packaged, up to publishing" can go without the owner, and what in the repository must change when the version does.

The workflow answers part of it by itself: started from any branch, it does everything except the last job, the draft. It refuses to start for a version that has no notes (`docs/releases/v<version>.md`).

## Options

- **A. Bump the version, write the notes and the documents, and run the release workflow from the branch `v0.2`.** Every job but the draft runs: the four builds, the checks that the program sends nothing, the tries on clean machines and ordinary computers. Nothing is tagged, drafted or merged. The owner gets a page that says exactly what is left.
- **B. The same, and open a pull request from `v0.2` into `main`.** The owner would find the work where they merge it. But a pull request is an invitation to merge, shown to anyone who can see the repository, for a version whose predecessor is not published yet; and the owner has said `main` is theirs.
- **C. Stop before the version changes:** leave 0.1.0 in place until the owner decides to release. Then the workflow has never built v0.2, and the first time it does is under the owner's eyes.

## Decision

**A.**

**1. The version becomes 0.2.0** in the workspace's `Cargo.toml` and `Cargo.lock`, in one commit with **`docs/releases/v0.2.0.md`** (decision 145). The program then says `opalro 0.2.0`, and new diary entries record 0.2.0. Test data that holds `0.1.0` as stored bytes (vectors, fixtures, a project "as v0.1 made it") stays as it is: it is what v0.1 wrote.

**2. The notes say what is new, what changes for a project made with v0.1, and what is still missing:**

- new: making, renaming and deleting lines; tags; combining lines; conflicts that are kept and fixed when you choose, and `opalro resolve`; moves recorded in saves; `opalro who`;
- for a project made with v0.1: it opens as it is. Keeping conflicts needs `opalro setup --upgrade`, once, and **Opalro 0.1 can't open the project afterwards**; a project started with 0.2 can't be opened by 0.1 either. What v0.1 wrote is still read: the format is still 1;
- still missing: a server (sharing, locking), moving saves between lines, guessed moves, merge programs;
- the known limits, with their numbers: going back against twice Git's time; `status` at its limit on Linux; what `who` does not follow.

**3. Every document a release carries or the website shows is brought to v0.2:** the README's first lines, the guide (the archive names, what the program prints, "what v0.2 doesn't do yet"), the download page, the welcome page, the known problems, how to report a problem. One sweep, checked by the workflow's own test that the guide names the archives of this version word for word.

**4. One text is not touched: `USER-AGREEMENT.md`.** It says what the owner agreed to say (decision 156), and one sentence in it is about the version: liability is limited to what you paid, "nothing: Opalro 0.1 is free". Whether that sentence holds for 0.2 is not a wording question. It goes at the top of the list of things only the owner can do, since every archive carries the agreement.

**5. The workflow is started from the branch `v0.2`,** by hand, on the last commit. It must pass every job it runs. Its last job, the draft, does not run there, by the workflow's own rule. **Nothing is tagged, no release is drafted, nothing is merged into `main`, no pull request is opened.**

**6. `docs/releases/v0.2.0-before-you-publish.md`** tells the owner what is left, in order: try it; go through the things to confirm from the four milestones; rule on the agreement's sentence and on the speed write-up; publish v0.1 or decide v0.2 replaces it; merge `v0.2` into `main`; start the workflow from `main`; publish the draft; put the files on the website.

## Consequences

- When the owner comes back, v0.2 is one merge and one workflow run away from a draft, and the workflow has already built and tried exactly these files from exactly this code, except for the merge commit itself.
- The branch `v0.2` says 0.2.0 while `main` says 0.1.0. If the owner publishes v0.1 first and it needs a fix release, that is made from `main` as decision 145 says and does not meet v0.2.
- The clean-room and code-audit papers that v0.1's release has (`docs/releases/v0.1.0-clean-room`, `v0.1.0-code-audit.md`) are about v0.1's code. v0.2 adds a great deal of code written the same way; whether it needs papers of its own before it is published is asked in the list for the owner, not assumed.
- A project started with the 0.2 program can't go back to 0.1. The notes and the guide say so before the download link.
