# Opalro Test Plan — Draft

> **Status:** drafted in the design phase (2026-10-31); §3 and §4 describe the tests and CI as they run after milestone 1 (2026-11-02), with milestone 2's differential tests, ignore-rule tests, hostile Git repositories and fuzz targets (2026-11-03), and milestone 3's model test, switch crash tests, hostile saves written out, memory checks and new fuzz targets (2026-11-06), and milestone 4's undo, redo, shelves and amend in the model test, its new crash tests and hostile diaries (2026-11-07), and milestone 5's big files in the model test, its crash tests of big files, hostile chunk lists, Git LFS imports, new fuzz targets, the speed gates and the benchmarks (2026-11-09), and milestone 6's presets, `opalro setup`, `opalro verify`, Git's words, the terminal design, the `--json` documents read against json.md, hostile rule files, the user guide and the release workflow (2026-11-10), and the v0.1 package's checks: that Opalro sends nothing, that nothing shipped points into the repository, the release workflow for every version and the clean-machine check (2026-11-11), and milestone 7's lines and tags in the model test, the ancestry walk against `git rev-list`, and the engine's and the command line's tests of lines, tags and the walk (2026-11-14).

**In plain words.** Opalro's first promise is "never lose or corrupt your data". Tests are how that promise survives every change to the code. Each kind of test below proves something specific, and together they run on Windows, macOS and Linux every time code is pushed.

## 1. Rules

- A task is done only when its tests pass on all three systems.
- Every on-disk format has test vectors ([storage-format.md](storage-format.md) §13) before it holds real data.
- Every bug fix comes with a test that fails without the fix.
- Speed and size claims come only from the benchmarks in §5.

## 2. Kinds of tests

| Kind | What it proves | Tools |
|---|---|---|
| Unit tests | Each small piece does what it says | Rust's built-in tests |
| Format tests | Every record encodes to exactly the bytes in the test vectors and decodes back; every invalid variant is rejected | golden files in `crates/opal-vcs-core/tests/vectors/` |
| Round-trip tests | Saving and then restoring gives byte-identical files, names, executable flags, symlinks and empty folders | `assert_fs` |
| Property tests | Random sequences of edits and commands never lose data and always match a simple model of what should happen | `proptest` |
| Crash tests | Stopping Opalro at any point while it writes leaves the repository usable, and the next command recovers | fault injection, killed processes |
| Differential tests | Importing a real Git repository gives exactly the same files, for every commit, as Git itself; Opalro's ignore rules keep the same files as Git's | `git` as the reference |
| Fuzz tests | Decoders and parsers never crash, hang or over-allocate on garbage input | `cargo-fuzz` |
| Malicious-repository corpus | Each attack in [security.md](security.md) is refused or handled safely | crafted repositories |
| Red-team sessions | A determined attacker can't break what the other tests didn't think of; once per milestone ([decision 024](decisions/024-red-team-gate.md)) | a fresh agent in a no-network Docker sandbox |
| CLI tests | Commands print what they should, both for people and as `--json` | `assert_cmd`, `insta` snapshots |
| Benchmarks | Speed and size claims are true, and stay true | ignored tests that print what they measure, `hyperfine` |

## 3. Details

**Property tests.** An in-memory model tracks what the folder and history should contain. Each random action (create, change, move or delete files; save; amend; goto; discard; undo; redo; shelf; unshelf) is applied to both Opalro and the model. After every action: `status` matches the model, every save restores byte-identically, `undo` returns to the previous state, and nothing the model says exists is missing.

The model test, `crates/opal-vcs/tests/model.rs` (`edits_saves_switches_shelves_and_undos_match_the_model`), drives the engine in the test's own process (a process per action would be too slow on Windows) through up to 30 random actions. Milestone 3 built it with these:
- write one of six files, at one of three lengths, so that files often keep their size when they change;
- write other bytes of the same length over a file;
- on Unix, turn a file's executable bit on or off;
- delete or rename a file, and make or delete one of three folders;
- save;
- `goto` a random save or line, first saving or discarding unsaved work, or keeping it;
- discard everything or one path;
- a status that reads every file.

Milestone 4 added these ([decisions 070](decisions/070-undo-and-redo-step-through-the-diary.md) to [074](decisions/074-save-amend.md)):
- `undo` and `redo` of 1 to 3 steps, with or without `--shelve`;
- `undo --to` a random diary entry: the current one, one redo or undo reaches, or any other, which is a jump;
- `shelf`, and `unshelf` of the newest shelf or of a numbered one, a number no shelf has included;
- `save --amend`, with a new message or the old one.

Milestone 5 added these ([decision 082](decisions/082-how-big-files-are-cut-into-chunks.md)):
- write a big file, 1 to 3 MiB of noise, which a save cuts into chunks;
- put 3 bytes into one of the big files at a random place, moving the rest along, or write them over its own there, so a few chunks change and the rest stay.

Milestone 6 added this ([decision 115](decisions/115-bolt-setup.md)):
- `setup --preset` with Code, Game or Custom, writing or removing `opalro.toml` and the `.opalroignore` block as one step that moves no line, always followed by an `undo` and a `redo`; switching to the preset the files already hold records nothing.

Milestone 7 added these ([decisions 158](decisions/158-making-renaming-and-deleting-lines.md) and [159](decisions/159-tags.md)), each as likely as `shelf`, with names from a pool of eight (`main`, `side`, `Side`, `wall-run`, `v1.0`, `V1.0`, `fix/a`, `-x`) shared by lines and tags, so names that are taken, alike but for letter case, the other kind's, or start with `-` come up often:
- `line new` at the save the project is on;
- `line rename` of a line, of the current one, or of a name no line has, to a name from the pool;
- `line delete` of a line or of a name no line has, answering yes or no if asked;
- `save --line`, starting a new line from a line or from a save;
- `tag` of the save the project is on, answering yes or no if the tag is at another save;
- `tag --delete` of a tag or of a name no tag has, answering yes or no.

The checks below cover big files like any other, so every switch, discard, shelf, undo and redo must write them back byte for byte, and every save must read them back through their chunk lists.

The model holds the folder's files (bytes and executable bit) and folders, every save's (its first parent, change ID and message, and whether it is a shelf's), the lines, the tags, the position and the shelves; the steps done and undone, each with its state and the whole folder before and after it; and every diary entry with its state. Its undo puts back the state from before the step and switches the folder from the "after" to the "before" by `goto`'s rule (redo the other way); a collision stops the command at that step, and `--shelve` sets the work in the way aside on a new shelf first. Shelves stay, except one the step added or removed. A jump switches from the current save to the entry's save, putting back the entry's lines, position and tags; an amend is refused at a save, when another line's history holds the save, or when a tag is at it. A new line's or tag's name is refused for the reasons above, each with the name the engine gives; `line delete` is refused for the line the project is on, and asks first exactly when the model's own walk along first parents finds that no other line's newest save and no tag's save holds the line's newest save, with the count of saves only the line has, the engine never asking otherwise; `tag` asks only before a tag moves, and `tag --delete` always. Each command that changes something makes one step, `line new`, `line rename`, `line delete` or `tag`, with no folder change; a refusal, a rename to the same name and a tag already at the save make none. After each action:
- the folder on disk holds exactly what the model holds;
- `status`, trusting the file cache, lists exactly the files added, changed, removed or changed in kind since the model's save;
- the lines, tags, position and shelves match, and so do the command's outcome, and a stop's paths and flags;
- the diary gained exactly the entries the model made, each with the right action and the model's whole state, `head` names the newest, and an entry records a folder change exactly when its command changed the folder, whose two saves differ exactly where the folder before and after the step differs;
- undo's lists, at 20 steps (the command's) and at 3 (so `more` is often true), are the model's steps: their entries, commands, whether they changed files, and their effects.

Each save holds exactly the model's files and folders in the store, checked when it is made and again at the end, with every save's message and first parent. Once per case, `opalro undo --list --json` runs as a command, and its document must be the one the model builds by [json.md](json.md)'s rules.

Each write leaves the file one of three modified times, which together cover the file cache's rules ([decision 053](decisions/053-file-state-cache.md)):
- the clock's, often within 2 s of the cache's last look, so the racy rule must make status read the file again;
- a time long past that no earlier write had, so the cache trusts the file and must notice the new time;
- the time the file had before. With the same size, that is [decision 011](decisions/011-status-and-write-out.md)'s accepted case, once the old time is more than 2 s old (1.5 s by the test's clock, for slack between clocks): status that trusts the cache may then miss the change, and a status that reads every file must see it, which also puts the cache right for the actions after. A file given an earlier time keeps that leeway when it is renamed. When the old time is newer than that, the racy rule applies and plain status must see the change.

A `goto` that keeps unsaved work is held exactly to decisions [050](decisions/050-unsaved-work-in-goto-and-discard.md) and [065](decisions/065-matching-work-doesnt-collide.md). It must stop, with nothing changed, when an unsaved change that differs from the target sits at, above or below a path where the target differs from the current save (a file, or a folder on one side only) and the folder isn't already as the target is. Otherwise it must go ahead. Work the target already agrees with, such as a file deleted that the target doesn't hold, and new files in a folder the target adds, come along. The rule came from this test: before decision 065, a deletion the target agreed with came along at a file but stopped the goto below a folder the target removes. The test also found a goto that left out a file the target adds when the user had deleted the folder it goes in; `goto.rs` keeps that case.

When it goes ahead, the folder must end as the target's own differences applied around the unsaved work, and folders made since the save stay, with the folders above them.

Names differ in more than letter case, so every drive holds them all, and a save made at a save starts a new line, as it must.

With milestone 4's actions the test found an engine bug, now fixed: a step's two saves could differ at a folder the user had made, which the step only wrote inside, so undoing a `goto`, `unshelf` or jump into it removed the folder, or stopped at it, or with `--shelve` shelved unrelated work in it, and redoing a `discard` inside it removed it. Both saves now hold such a folder ([storage-format.md](storage-format.md) §9), and its shrunk cases are tests of their own in `crates/opal-vcs-core/src/undo/tests.rs`.

The test hands the engine a cache key, so the file cache is read and written as for a user; until milestone 4 it had none, and the cache was never on in it. With the cache on, each of the cache's checks was broken in turn and the test run for 64 cases: the modified time alone not compared, or the racy rule alone taken out, passed, since the change time catches every edit either lets through; both times not compared passed too (only a same-size edit of a saved file whose entry isn't racy catches it, which the random actions rarely line up), though a 3-action sequence fails at once; both times and the racy rule broken failed within 3 cases. The racy rule needs an edit within one tick of the drive's clock after the status before it, which random actions almost never make, so the model test doesn't exercise it: the cache's own unit test `a_file_changed_within_two_seconds_of_now_is_read_again` (`filecache.rs`) pins it, entries just inside and outside the 2 seconds included.

It runs 64 cases on every push (about 21 s in a debug build on a Windows laptop with milestone 5's big files, and 89 s for 256 cases, measured 2026-11-09; with milestone 7's lines and tags, 18 s for 64 cases in a debug build and 130 s for 512 in a release build, measured 2026-11-14), and 1,024 nightly, through `PROPTEST_CASES`. A failure prints the action it failed after and the shrunk sequence. Rare paths stay rare in 64 cases (an amend refused because another line's history holds the save, a jump that stops), so the nightly run is where they are met; a tag being what holds a line's saves, so that `line delete` asks nothing, may take the nightly run's 1,024 cases to reach.

**Crash tests.** Every disk write goes through one small layer that tests can make fail (return an error, or abort the process) at the N-th operation, or fail at one named point (`OPALRO_FAULT_FAIL=start:read-back`) and let the command carry on. For each N, a test runs a command, fails it at step N, then checks that the repository opens, `opalro verify` passes, no saved data is missing, and the next command finishes or rolls back the interrupted one. Separately, a loop kills real Opalro processes at random moments.

A command can now write several packs, so milestone 2 added crash tests for the gap between two of them. A named point, `packs:rolled-over`, sits right after a full pack goes into the store.
- `a_crash_between_packs_leaves_the_repository_as_it_was` (in `crates/opal-vcs-core/src/repo.rs`) fails a command that needs three packs at every step. It checks that `state/head` still names the old entry, that the store checks out, and that running the command again works.
- `crates/opal-vcs-core/tests/import_interrupted.rs` does the same to `opalro import`, with a test-only limit of three objects a pack. After every stop there is no project yet (`.opalro/format` is missing), and running the import again gives the saves and state of a clean import. At least one stop must fall between two packs.

Merging small packs (milestone 3) adds two named points: `merge:written`, right after the new packs go into the store, and `merge:removing`, before each old pack is removed; an error there leaves that pack as a second copy. `a_merge_stopped_at_every_step_leaves_every_object_readable` (in `crates/opal-vcs-core/src/merge.rs`) fails a merge of 34 packs at every step, and checks that every object reads and the store checks out, and that merging again leaves at most two packs, and one when nothing went wrong.

Switching the folder between saves (milestone 3) adds three named points: `switch:written`, inside each file write, after the new contents are flushed in `.opalro/tmp` and before they are renamed into place; `switch:changed`, after each change to the folder; and `journal:removed`, after the journal is deleted and before its folder is flushed; the head write's own `write:before-rename` sits between the two. `a_switch_stopped_at_every_write_is_finished_by_the_next_command` (in `crates/opal-vcs-core/src/writeout/tests.rs`) stops a switch at every one of them, checks that every file is wholly old or wholly new, then runs `save`, which must finish the switch (saying so only when `head` hadn't moved yet), leave the folder exactly as the target save (checked all the way down) and remove the journal. `a_finish_stopped_in_turn_is_finished_by_the_command_after` stops a switch at a few points, then stops the `save` that finishes it at every step, and checks that the save after that finishes it.

A command has happened once `head` moves, and from then on nothing fails it ([decision 075](decisions/075-crash-recovery.md)), so milestone 4 adds two named points where an error is only a warning and the command goes on: `head:renamed`, after `state/head` is renamed into place and before `state/` is flushed (`head_not_flushed`), and `journal:removing`, before a switch's journal is deleted (`switch_unfinished`: the journal is left for the next command to remove); an error at `journal:removed` is now `head_not_flushed` too. The sweeps that make each point fail in turn count such a run as a stop after the head moved and carry on to the next point; the crash sweeps check that a crash there leaves the command done. `crates/opal-vcs/tests/recovery.rs` fails each of the three by name, and crashes `opalro undo --to` picking up a lost `head` at every point.

Milestone 4's new commands are crashed at every write in turn (`OPALRO_FAULT_AT`, a real process each time). After each stop every file must be wholly old or wholly new, and the next command that changes the project must finish the step (with `switch_finished`, unless only the journal was left) or find it not begun, and leave no journal; an amend writes no file, so its sweep checks instead that the line holds the old save or the new one:
- `an_undo_stopped_at_every_write_is_finished_by_the_next_command` and `an_undo_shelve_stopped_anywhere_is_finished_by_the_next_command` (`crates/opal-vcs/tests/undo.rs`): the undo of a `goto`, and with `--shelve` the shelf it makes, which holds the edit whenever the undo was made;
- `a_shelf_or_unshelf_stopped_at_every_write_is_finished_by_the_next_command` (`shelf.rs`);
- `an_amend_stopped_at_every_write_leaves_the_old_save_on_the_line` (`amend.rs`): an amend writes no file, so the folder never changes, the store checks out, and the line holds either the old save or the new one;
- `running_undo_again_after_a_stop_finishes_it_and_takes_no_further_step`, `undo_to_after_a_stop_finishes_it_and_takes_no_step` and `running_unshelf_again_after_a_stop_finishes_it_and_brings_back_no_other_shelf`: the command run again finishes the stopped one and goes no further ([decision 075](decisions/075-crash-recovery.md)).

`tidy` adds three named points: `tidy:marked`, once it knows what to keep; `tidy:written`, once its new packs are in the store; and `tidy:removing`, before each old pack is removed, where an error leaves that pack with a `pack_not_tidied` warning. `tidy_stopped_at_every_step_loses_nothing` (in `crates/opal-vcs-core/src/tidy/tests.rs`) fails a `tidy` at every step, and must have stopped at each of the three; after every stop each object it keeps still reads, and tidying again finishes the job. `packs_holding_nothing_to_keep_go_first_even_when_writing_fails` checks that packs holding nothing to keep are already gone when writing a new pack fails, so a full disk still gets space back.

Milestone 5 stops commands in the middle of a big file. `crates/opal-vcs/tests/chunks_stopped.rs` lowers the test-only pack limit to 16 objects, so one 3 MiB file's chunks fill several packs (the limit reaches every command in the process, so these tests keep a file of their own):
- `a_save_stopped_between_chunks_leaves_the_project_as_it_was` fails a save of the file at every step: `head` must not move, the next save must store the file, every file of every save the diary names must read back whole, the store must check out, and at least one stop must fall between two of the file's chunks;
- `a_discard_or_shelf_of_a_big_file_stopped_anywhere_loses_nothing` does the same to `discard` and to `shelf` of the file, once replaced by other bytes: after the next command it is wholly one version or the other, and both are still in a save the diary names;
- `a_crash_sweep_of_a_threaded_save_stops_at_the_same_places` stops a save of the big file and 40 small ones at each step, with one worker thread and with eight, and checks that both stop at the same place and leave the same packs, as the single writer thread promises ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)).

`tidy_stopped_at_every_step_loses_no_chunk` (in `crates/opal-vcs-core/src/tidy/tests.rs`) stops `tidy` at every step with big files in the store, and checks that every file of every kept save still reads whole, with its chunks, and so does a list stored again in a young pack.

Beside them, `crates/opal-vcs-core/tests/pack_limit.rs` is not a crash test: it checks the test-only limit itself, that it splits a command's packs until it is cleared. The limit applies to every command in the process, so that file and `import_interrupted.rs` each hold a single test.

**Differential tests against Git.** `crates/opal-vcs/tests/import_vs_git.rs` makes repositories with Git itself, runs `opalro import`, and then `assert_matches_git` (in `tests/support/`) compares the project with what Git holds, reading Git's objects through `git cat-file --batch`:

- each commit `git rev-list --all` lists has exactly one save, which rebuilds the commit's exact bytes, and commits Git writes itself rebuild from their saves' own fields, without their Git header;
- each author and committer line in Git's own form names the save's person, time and zone, so a kept Git header can't hide a wrong one;
- each Git tree, read once, is a listing with the same names after Opalro's skip rules, the kinds its modes make, and files whose Git blob IDs, computed in the test, are the entries' IDs;
- the lines, server lines and tags are the branches, server branches and tags `git for-each-ref` lists, under the names Opalro's renaming rule gives them (the everyday test also checks a few names as written, so a wrong rule can't pass on both sides), and annotated tags keep their tag objects' exact bytes.

After each of these comparisons, `assert_ancestry_matches_git` checks the ancestry walk ([decision 160](decisions/160-whether-a-save-is-in-anothers-history.md)) against Git: its tips are the lines in name order, then the server lines in name order, each standing for the commit its save records in `git-commit`, and for up to 64 ordered pairs of tips `(a, b)`, `only_in(a, [b])` must be what `git rev-list --count a ^b` prints. The pairs go round the tips, each with its next neighbour, then with the one after, and so on, so every tip comes first at least once before the cap; a pair of two tips at the same save is skipped. That holds exactly when no commit in the history of the tips compared has a committer date earlier than one of its parents' (`git log --format=%H %ct %P <tips>`; equal dates are fine). Where one does, as Git allows, the walk may count too many but never too few, so there the test asserts only that both counts are 0 together and that the walk's is never lower, and prints how many pairs still came out equal. It returns the pairs compared, which form it used and how many of the walk's counts came out higher, and each test pins all three; it prints how long the walks took. The everyday history compares 64 pairs across its merges: tips another holds, tips that hold some of their own, and tips parted at a fork. A seventh repository, a history dated backwards, has five lines and commits dated before their parents that the walks cross, so the weaker form runs on every push; in one of its 20 pairs the walk counts 2 where Git counts 1 (a merge whose second parent is read before the commit, dated earlier, that would have shown it held), which shows the weaker form is needed and not only chosen. The engine's `a_history_dated_backwards_can_count_high_never_low` pins the same four saves. Two repositories have a single tip and nothing to compare.

Git runs with nothing from the computer's set-up: no system or user config, no templates, no replace objects.

On every push, on all three systems, it compares seven repositories: everyday history (renames, deletions, an executable, links, case twins, a submodule, Unicode names, a merge and an octopus merge, every kind of branch, server branch and tag, then the same with a detached `HEAD`); unusual commits written byte by byte (signatures, a merge tag, Latin-1, a change ID, `-0000`, an odd author line, an unknown header, a parent named twice); a history dated backwards; packed and loose objects with deltas; a SHA-256 repository; Git's optional files (commit-graph, multi-pack index, bitmap, reverse index, worktree config, only packed refs); and names Windows can't hold, saved again after the import. One more test checks that a link Git wrote keeps its target when saved, on all three systems: Git for Windows writes the `/` in a link's target as `\`, and Opalro stores `/` there, as Git does ([decision 045](decisions/045-link-targets-stored-with-slashes.md)). In CI the test fails rather than skip if Git can't make the link. Before milestone 3 built this, a nightly job ran the test on GitHub's Windows runner as the evidence the decision rests on: in [run 41644016857](https://github.com/WisHonor/Bolt/actions/runs/41644016857) it failed as it should, saving `dir\target.txt` where Git stores `dir/target.txt`.

Git LFS is held to Git LFS itself (milestone 5). `an_lfs_repository_matches_what_git_lfs_checks_out` (`crates/opal-vcs/tests/import_lfs.rs`) has Git LFS track the `.bin` and `.psd` files of a three-commit history, among them a 3 MiB file edited in the middle, imports it, and checks that each commit's save holds exactly the files as they were committed, which a checkout with Git LFS gives back. `after_git_lfs_checkout_the_save_goes_through` checks out a pointer with Git LFS told to skip, and checks that the first save stops at it and goes through once `git lfs checkout` has written the file. Both run `git lfs install --local` in their own repository, never in the user's or the global config, and skip, saying so, where `git lfs` isn't found; GitHub's runners have it, so CI runs them on all three systems.

Nightly and when started by hand (§4), `a_real_repository_matches_git` imports a full clone of Git's own repository (git/git; it checks the clone isn't shallow) and compares all of it. It imports in its own process and prints how long the import took and the process's peak memory, which Linux reports as `VmHWM`, read right after the import. Its server lines give the ancestry walk tips enough, and the test fails if it compared no pairs; the walks' time it prints is the number for `docs/benchmarks.md`.

Measured on 2026-11-03 in release builds, on git/git as of 2026-11-01: 85,977 commits and 1,012 tags (Opalro leaves out the one that tags a file). Every commit, tree, file and ref matched Git; 98 commits have trees in forms Git no longer writes, and 219 keep their Git header.

- GitHub's Linux runner (`ubuntu-latest`, nightly run 41638396168): imported in 102.0 s, with a peak of 583 MiB (`VmHWM`).
- A Windows 11 laptop (AMD Ryzen 7 7730U with 8 cores, 16 GB of RAM, an NVMe SSD) with Git 2.50.1: imported in 165 s, with a peak working set of 503 MiB; the comparison took 124 s more. Windows tells a process its peak memory only through a system call, so there the test prints none: this figure is the test process's `PeakWorkingSet64`, read by PowerShell twice a second and taken as the import ended (the comparison never raised it).

Measured again on 2026-11-09, by the `Bench` workflow's `import-git` job rather than this test ([benchmarks.md](benchmarks.md) §3): git/git as of 2026-11-06 (86,059 commits and 1,022 refs), imported by `opalro` built from `main` and from milestone 5, three times each on one machine, with each import's time and peak memory from GNU `time`. On GitHub's Linux runners `main`'s took 165.0 s and milestone 5's 165.1 s on an AMD EPYC 7763, and 168.9 s and 171.2 s on an EPYC 9V74, within 1.3% of each other; an earlier run took 101.3 s with `main`'s on an EPYC 9V45, so the runner's processor matters more than the version, and nightly runs of this test on `main` have imported it in 95 to 168 s. The peak was about 573 MB (547 MiB) with `main`'s and 669–680 MB (638–649 MiB) with milestone 5's, about 100 MB more: most likely the Git reader's cache of rebuilt objects, which then stayed near its 256 MiB budget, since cut to 96 MiB ([decision 104](decisions/104-an-import-keeps-96-mib-of-rebuilt-objects.md)). The laptop wasn't measured again.

**Ignore rules against Git.** Opalro's ignore matcher is Opalro's own, written to match Git's documented and observed behaviour, and three kinds of test hold it to Git:
- Opalro's own cases, beside the matcher (`crates/opal-vcs-core/src/ignore/tests.rs`): how lines are read, which line and folder decide, `**`, bracket classes and ranges, letter case folded as Git folds it, Unicode names on drives that compose them, and lines Git can't use. Two of them show the work stays in proportion to the pattern and the path: patterns that would take a backtracking matcher years, and a bracket read of half a million `[:` that would take a reader looking ahead from each one hours.
- `crates/opal-vcs/tests/ignore_vs_git.rs` writes random rule files in random projects (as `.gitignore` for Git and `.opalroignore` for Opalro, in several folders, with names in both letter cases and in composed and decomposed Unicode). For 256 projects each, it checks that a save keeps exactly the files `git ls-files --others --exclude-standard` lists, and that the verdict on every path is the one `git check-ignore --no-index -v` gives. A third check lays a `.opalroignore` of mostly `!` lines beside the `.gitignore` files and shows Git only the `.gitignore` files: Opalro's verdict from the `.gitignore` lines alone, which the warning about files a `.opalroignore` takes back rests on, must still be Git's. - The same file checks 95 single patterns, each in its own folder's `.gitignore`, and five hand-made projects (negations across nested folders, lines tied to their folder, both personal lists) against `git check-ignore`, and holds a test of Git's two personal lists ([decision 047](decisions/047-git-personal-ignore-lists-read.md)): a user's own list, named to Git as `core.excludesFile`, and `.git/info/exclude`, with project rules that take back some of their lines, must leave a save exactly the files Git lists. The CLI tests point `HOME` and `XDG_CONFIG_HOME` at a folder of their own and remove `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_COUNT` from each `opalro` they run, so the real user's Git settings never reach them; the engine's own tests hand it the variables it reads, never setting the process's.

Git before 2.52 reads a `**` right after the literal start of a pattern with a `/` differently, and Opalro follows 2.52 and later; with an older Git such lines are left out of the random rules. The CI runners' Git is new enough that nothing is left out.

**The rest of the Git reader against Git.** The other parts that read what Git and Git LFS write are Opalro's own too, written from their documentation and from what the programs do, and each is held to the program beside its own cases: Git's config files are read by `git config` as well, each line giving the same names and values, or the same line refused, with the format versions, extensions, true-or-false values and the settings in the environment checked the same way; random ref names get the answer `git check-ref-format` gives; near-pointers built from the pieces Git LFS looks at get the answer `git lfs pointer --check` gives; and the hand-made cases for `.git` look-alike names, person lines and the tidying of `GIT_CONFIG_SYSTEM` record what `git fsck`, `git log` and Git give for each. A test whose program isn't installed says so and passes.

**Fuzz targets.** Twenty-three cover the decoders and parsers of data from outside Opalro:

**Big zlib streams.** Opalro inflates Git's objects with miniz_oxide, 16 KiB of input a call. Given no input, miniz_oxide can still write the rest of a copy and then say it made no progress, which once cost big, mostly-zero files their last bytes. A unit test in `git/odb.rs` inflates the smallest stream found to do that, 52 MiB of zeros, on every push. `big_mostly_zero_streams_inflate_whole` sweeps zeros and sparse data of 110 to 300 MiB at three compression levels, checking each byte against the data compressed; it takes a few minutes in a release build, so it is ignored in normal runs and runs nightly (§4).

## 4. CI on GitHub

- **Every push and pull request** (but a push to a `gate/` branch, which only measures a commit its own branch has already tested): formatting check, clippy with warnings denied, every test on Windows, macOS and Linux (the differential tests against Git on small repositories among them), run to the end even when one fails (`--no-fail-fast`), so one failing test file can't hide the others, a build without features, and `cargo-deny`, on the workspace and on the fuzz crate (it also checks the RustSec advisory database and that every crate comes from crates.io). Two of these guard the promise that Opalro sends nothing ([decision 142](decisions/142-bolt-sends-nothing-and-each-build-proves-it.md)): clippy refuses `std::net`'s types anywhere in the workspace, and cargo-deny refuses the crates whose purpose is the network. On Windows, one more step runs the slow tests that save a project nested 2,048 folders deep (a last path of 4,095 bytes) and refuse one a level deeper (4,097 bytes); they are marked ignored, so only that step runs them.
- **Nightly, on every push to `main`, and when started by hand:** fuzzing of every target (§3), 5 minutes each nightly and 1 minute each otherwise.
- **Nightly, and when started by hand (not on pushes):** the differential test on a fresh full clone of git/git, on Linux in a release build, within an hour; its log must show the one test passed, and shows the import's time and peak memory (§3). The sweep of big zlib streams runs beside it, also in a release build (§3), and so do the model test with 1,024 cases (§3), the write-out of a chunk list of the most chunks a list may hold (`most-chunks`, §3), the status gate (§5), which fails its job when either run takes 2 s or more, and the memory gate (`memory-gate`, §5), which fails its job above 500,000,000 bytes. Each of these jobs' logs must show its one test passed, and the memory gate's the peak it read too. The job that checked the links Git for Windows writes is gone since 2026-11-05: `a_link_git_wrote_keeps_its_target_when_saved` now runs on Windows on every push.
- **The `Bench` workflow** (`.github/workflows/bench.yml`), started by hand or by a push to a `bench/` branch, on GitHub's machines: the memory gate; Opalro, Git and Git with Git LFS through the same steps on the same data, on Linux and on Windows, with the speeds of the parts and what compressing again would save (§5); and git/git imported by `main`'s `opalro` and the branch's in turn (§3). A push to a `redteam/<name>-sizes` branch runs only the import of the red team's RT4-1 repository, which is attack code and runs nowhere else. Its results are copied into [benchmarks.md](benchmarks.md) by hand, with the runs they came from. The memory gate's job is in `.github/workflows/memory-gate.yml`, which both workflows call: it frees about 22 GiB of the runner's disk first.
- **The gate against Git** ([decision 099](decisions/099-a-third-speed-gate-within-twice-gits-time.md)): a `speed-gate` job, in `.github/workflows/speed-gate.yml`, which the `Bench` and nightly workflows both call, runs `bench/run.sh gate` on GitHub's Linux and Windows runners. It builds `opalro`, fetches Git's source at `v2.56.0`, times Opalro and Git through the code set's steps, ten runs each, and fails when the median of `status` with nothing changed or of a small save is more than twice Git's median ([decision 108](decisions/108-the-third-gate-compares-medians.md)), or the median of going back to the first version more than three and a half times Git's (decisions [128](decisions/128-v0.1-ships-without-goto-within-twice-gits-time.md) and [132](decisions/132-gotos-limit-is-three-and-a-half-times-gits-time.md); twice is its goal for v0.2, and the job says when it is over the goal); each step's mean, best and worst run are printed beside it (§5). A push to a `gate/` branch runs this job alone, to measure one change.
- **The `Release` workflow** (`.github/workflows/release.yml`, decisions [119](decisions/119-packaging-v0.1.md), [145](decisions/145-one-release-workflow-for-every-version.md) and [146](decisions/146-the-clean-machine-check-and-which-systems-each-build-needs.md)) starts only by hand, or on a pull request that changes the workflow, its scripts in `.github/release/`, `about.toml`, `about.hbs`, `USER-AGREEMENT.md`, `LICENSE` or anything under `docs/releases/`. Every name in it comes from the version in `Cargo.toml` (the `opal-vcs` package's), so a new version needs no change to it. Its jobs, in order:
  - **`prepare`** reads the version and fails when `docs/releases/v<version>.md` is missing; writes `THIRD-PARTY-LICENSES.html` with `cargo-about` (downloaded at a pinned version and checked against its SHA-256), and copies the toolchain's `share/doc/rust/COPYRIGHT-library.html` as `THIRD-PARTY-LICENSES-RUST.html` ([decision 143](decisions/143-the-notices-cover-what-is-built-in.md)); and makes the website copies, `opalro-<version>-website.zip`: the documents meant for the owner's website, the `--json` reference, the storage format and the benchmarks among them with their links into the repository made plain text, failing when any still holds an address on the owner's GitHub account (links to any of its repositories made plain text, so a renamed repository keeps its old links working), a link into the repository, or the old name Bolt ([decision 150](decisions/150-the-name-is-opalro.md), [decision 144](decisions/144-where-people-get-bolt-and-report-problems.md)). It prints the zip's SHA-256 and gives it to `release` as a job output.
  - **`build`** builds `opalro` with `--locked` for Windows (x86-64, C runtime linked in), Linux (x86-64, on the oldest Ubuntu runner, printing the newest glibc symbol it needs) and macOS (Apple silicon, and Intel on an Intel runner, printing the macOS version each declares). It checks each program with `.github/release/no-network.sh`, which must first refuse two small programs built on the spot, one that opens a connection and one that starts a program, and then must find neither in `opalro` ([decision 142](decisions/142-bolt-sends-nothing-and-each-build-proves-it.md)); runs it (`--version`, then `start --preset custom`, a save, `history` and `verify`, in a scratch folder with its own `OPALRO_CONFIG_DIR`); and packs it into an archive that must hold exactly six files, the program, `README.md`, `docs/guide.md`, `USER-AGREEMENT.md`, `THIRD-PARTY-LICENSES.html` and `THIRD-PARTY-LICENSES-RUST.html`, none of them holding the repository's address (the `.tar.gz` ones with every entry owned by 0/0, by number). It prints each archive's SHA-256 right after packing and gives it to the later jobs as a job output, which nothing after the job can change.
  - **`sums`** writes `SHA256SUMS` over the four archives, and only when each archive it downloaded has the SHA-256 its `build` job gave.
  - **`clean-machine`** takes each archive and `SHA256SUMS` (with `actions/download-artifact`, which fails on a digest mismatch, into the runner's temporary folder, outside the checkout, as `ordinary-computers` does; no step is handed the GitHub token) onto fresh runners, and into bare containers (Windows Server Core; AlmaLinux 9, whose glibc 2.34 is the oldest the Linux build claims; Ubuntu 22.04; Debian 12; each image pinned by its digest, refreshed by hand when the image is patched), as [decision 146](decisions/146-the-clean-machine-check-and-which-systems-each-build-needs.md) lists. On each runner it checks the download with the guide's own command; in each place, runner or container, it then runs `opalro --version`, `opalro start` with each preset, a save, a change, `status`, a second save, `goto`, `undo`, `redo`, `shelf`, `verify` and an import of a small Git repository made on the runner, with the project and the settings folder in paths that hold a space and letters outside ASCII. Then it rehearses the release from a folder laid out as the owner's website will be (the website copies' documents, all four archives and `SHA256SUMS` beside them, and the download page's placeholder replaced with `SHA256SUMS`' text), checking that the page's fingerprints are `SHA256SUMS` exactly and that every archive it names is there, serves that folder on 127.0.0.1 and downloads this system's archive, `SHA256SUMS`, the agreement and the two pages from it (`curl`, or `Invoke-WebRequest` on Windows). From that folder, on the runner and then as root in each bare container, the first run follows the download page and the guide inside the archive word for word: the checksum, the agreement (byte for byte the archive's), the install steps, the first five minutes, and a report written under the report form's "What to send" labels (each still in the form, `opalro verify` passing, `opalro status --json` holding `"opalro_json":1`), printed in the log. It fails when what a program declares (its newest glibc symbol, its macOS minimum) no longer matches what the guide says it needs.
  - **`release`**, only on a start by hand from `main` and only once `prepare`, `build`, `sums` and `clean-machine` have passed (`ordinary-computers` tries cases and isn't waited for), checks that no tag or release (drafts included) named `v<version>` exists and that CI's `test` on Windows, macOS and Linux and its `deny` passed on the commit (their latest attempts), checks every file it attaches against the SHA-256 the job that made it gave (and the archives against `SHA256SUMS`), writes `SHA256SUMS` again from those hashes and stops unless it is byte for byte the one `sums` made, and makes the draft release `Opalro <version>`, its notes `docs/releases/v<version>.md` with a last line naming the run that made it, tag name `v<version>`, on the commit the archives were built from, with the four archives, `SHA256SUMS` and the website copies. It is the only job that may write; nothing is published, tagged or signed.

  On a pull request, or started by hand from any branch but `main`, it stops before `release`. A pull request's run keeps its artifacts 3 days, since they are tests of the workflow, not releases; any other run keeps them the repository's default 90 days. A change is proved by that run's log, which shows the import check's list, each smoke test's commands, each archive's listing and each clean-machine step. If `release` fails halfway, a draft it already made stays, and the next start refuses because a release named `v<version>` exists: delete that draft by hand on the repository's releases page, then start again. The workflow's first start from `main`, on 2026-11-10 ([run 42951072197](https://github.com/WisHonor/Bolt/actions/runs/42951072197)), made a first draft of v0.1.0; it was deleted on 2026-11-11, stale, with its archives.

  1. On a branch from `main`, a test that fails without the fix, then the fix, through a pull request whose checks all pass, as for any change.
  2. In the same pull request or the next: `version = "0.1.1"` in `[workspace.package]` of `Cargo.toml`, with `Cargo.lock` updated in the same commit (`cargo build` once does it; the release builds with `--locked` and stops otherwise); `docs/releases/v0.1.1.md`, the notes (what was wrong, what was fixed, credit to the tester if they want it, and that nothing on disk changed); `docs/releases/known-problems.md` without the fixed problem; and the version in the archive names, commands and `opalro --version` output of `docs/guide.md` (section 2) and of `docs/releases/download-page.md`, which the clean-machine check reads word for word and stops on when they name another version. The pull request's own release run builds the archives and runs the clean-machine check on them.
  3. Merge it, then start the `Release` workflow by hand from `main`: it makes the draft `Opalro 0.1.1`.
  4. The owner downloads the draft's files, checks each one's SHA-256 (`sha256sum`, or `Get-FileHash` on Windows) against the hashes the log of the run the draft's notes name printed (each archive's in its `build` job, the website copies' in `prepare`), compares the text of `SHA256SUMS` with what that run's `sums` job printed, reads the draft (the line naming the run can go before publishing), publishes it (which makes the tag `v0.1.1`), and puts its files on the website in place of v0.1.0's, `SHA256SUMS` included. A run's log can be deleted but not edited, so a file swapped on the draft afterwards shows up here.

  A fix release never changes what is on disk or what a `--json` field means: format 1 and `opalro_json` 1 are frozen from v0.1 (decisions [121](decisions/121-format-1-freezes-at-v0.1.md) and [117](decisions/117-what-json-covers-at-v0.1.md)).
- The whole suite runs locally before a push, and pushes come at task boundaries: CI minutes counted while the repository was private (for a time from 2026-11-05; it is public again, checked 2026-11-06), and a local run finds a failure sooner.
- A `.gitattributes` file turns off Git's line-ending conversion, so test files stay byte-exact on Windows.
- Workflows run with read-only permissions, actions are pinned to exact commits, and Dependabot opens weekly update pull requests for Rust crates and actions.

## 5. Benchmarks and measurements

- **Micro:** the parts of a save, each timed alone on one thread: the cutter, run over 256 MiB of noise as one stream; BLAKE3, fed the same noise 64 KiB at a time; and zstd at levels 3, 9 and 19, on each 64 KiB piece of that noise and of 64 MiB of sound, one piece at a time. And, for compressing again, what levels 9 and 19 store against level 3, on the pieces a save stores (a small file whole, a big one's chunks) of code, of uncompressed assets and of compressed ones, and how long they take. These are the ignored tests `speeds_of_the_parts` and `what_compressing_again_would_save` in `crates/opal-vcs-core/tests/throughput.rs`, run in a release build by the `Bench` workflow and by hand; they print MB/s and bytes, with no `criterion` ([decision 088](decisions/088-benchmarks-and-the-speed-gates.md); results in [benchmarks.md](benchmarks.md) §4 and §5).
- **End to end:** `opalro` against Git and against Git with Git LFS, with the same steps on the same data (`bench/run.sh`, timed with `hyperfine`, 5 runs after a warm-up): a code project and Godot's demo projects at fixed tags, and generated sets (20 files of noise, a 1 GiB file in 10 versions, 1 GiB of one repeated block). The steps: first save, saving a small change, `status` on an unchanged project, `status` after touching one big file, going back to the first version, and the space each takes. Imports of a Git LFS repository and of a 200 MiB file in 50 versions are timed too, with their sizes against Git's. Results are published with the machines and versions they ran on ([benchmarks.md](benchmarks.md) §2 and §3).
- **Release gates for v0.1** ([decision 023](decisions/023-v0.1-speed-bar.md)): saving a 10 GB file uses at most about 500 MB of memory, and `status` on an unchanged 100,000-file project takes under 2 seconds on an SSD. Both run as automated benchmarks and fail their jobs over the limit: the memory gate always, and the status gate from v0.1 on, when either of its two runs takes 2 s or more ([decision 129](decisions/129-gotos-limit-until-v0.2-and-the-status-gate-enforced.md)). A third gate ([decision 099](decisions/099-a-third-speed-gate-within-twice-gits-time.md)) holds Opalro to Git on a code project: on Git's source at `v2.56.0`, `status` with nothing changed and a small change saved each take Opalro at most twice Git's time, on GitHub's Linux runner and on its Windows runner, and going back to the first version at most three and a half times, twice being its goal for v0.2 (decisions [128](decisions/128-v0.1-ships-without-goto-within-twice-gits-time.md) and [132](decisions/132-gotos-limit-is-three-and-a-half-times-gits-time.md)). `bench/run.sh gate` measures it as the end-to-end steps above are measured, with 10 timed runs of each step, both tools in one job on one machine, and fails when a step is over its limit; the `speed-gate` job runs it nightly (§4). Everything else is measured and published, not gated.
- **Results:** [benchmarks.md](benchmarks.md) gives the gates' numbers, Opalro against Git and Git LFS, the imports, the parts of a save and the ruling on compressing again, with the machines, the versions and the exact commands, the steps Git or Git LFS wins included.
- **The status gate, measured:** `crates/opal-vcs/tests/speed.rs` (`status_on_an_unchanged_100_000_file_project`, ignored; run by hand and nightly) builds 100,000 small files, 100 to a folder, an hour old, saves them, runs `status` twice, prints both times, and fails unless both are under 2 s ([decision 129](decisions/129-gotos-limit-until-v0.2-and-the-status-gate-enforced.md)). First run, 2026-11-05, on a Windows 11 laptop (Ryzen 7 7730U, NVMe), release build: **1.26 s, then 1.20 s**, under the 2 s gate; the first save took 26.3 s. Again on 2026-11-06, after the file cache began reading each file's change time (decision 069): **1.30 s, then 1.36 s**; the first save took 36.8 s. The test saves with `--yes`, since 100,000 new files ask the large-save question. Before `save` and `status` looked at files on several threads, the same kind of project took about 4.4 s. On Windows each file is still opened once to read its size and time, since the folder listing can hold old ones for a file open for writing; most of what is left is those opens. Runs on this laptop vary by up to about 0.7 s (Windows Defender working through new files, the power state), so the nightly Linux run is the reference figure. Measured again on 2026-11-09, after milestone 5's changes ([benchmarks.md](benchmarks.md) §1): **0.70 s, then 0.70 s** on GitHub's Linux runner (nightly run 42592855953, whose first save took 1.93 s), and **1.16 s, then 1.15 s** on the Windows laptop, whose first save took 5.10 s.
- **The memory gate, measured:** `saving_a_10_gib_file_stays_under_500_mb` (`crates/opal-vcs/tests/speed.rs`, ignored) writes 10 GiB of BLAKE3's extendable output into a temporary folder, a mebibyte at a time, runs `opalro save --yes` on it, and reads the `opalro` process's `VmHWM` from `/proc` every 20 ms. So it measures on Linux only, and says it skipped elsewhere. It fails above 500,000,000 bytes, and when it read no peak or the file wasn't stored. The nightly and `Bench` workflows run it; on Windows the same save is measured by hand, its peak working set read by PowerShell. Measured on 2026-11-09: **43.5 MB** on GitHub's Linux runner and **48.7 MB** on the Windows laptop ([benchmarks.md](benchmarks.md) §1).
- **Dedup:** how much space chunking really saves on real assets (textures, models, audio, video, engine files), so claims stay honest (design.md risk 4). Milestone 5 measured it on Godot's demo projects and generated sets ([benchmarks.md](benchmarks.md) §2): ten versions of a 1 GiB file take 1,041 MiB in Opalro against 10 GiB in Git, and Godot's demos take 3% more in Opalro than in Git. Other real assets are still to be measured (design.md §7).
