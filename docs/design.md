## 1. Vision

**In plain words.** Opalro keeps the history of a project: you save versions, go back in time, try ideas on the side, and work with other people. It is meant to be one tool for the *whole* project: the source code **and** the multi-gigabyte textures, models, datasets and videos next to it.

**Why it exists.** Opalro is a personal project, but it is designed as if it would be marketed and sold: the bar is "best on the market", and decisions are judged that way.

To the user, every save is a full **photo** of the project. How photos are stored (whole copies, differences, shared chunks) is the storage engine's private business and can change without changing what users see.

**What makes it different**
- **Own engine**: its own object model, storage format and network protocol. Not a Git wrapper, not Git with renamed commands.
- **Friendly**: clear command names, human error messages, undo for everything.
- **Great with big files**: big files are split into chunks so only changed pieces are stored and sent; big files and old versions download on demand; built-in, opt-in file locking for files that can't be merged.
- **Hybrid**: small text files handled like Git (but faster), big binaries like Perforce (but friendlier), in the same project, with one engine and one storage format.
- **Adapts to the project**: `opalro start` detects the project type and suggests a preset; presets only change defaults, and per-file rules always apply.
- **Closed source** ([decision 140](decisions/140-bolt-is-closed-source.md), the owner's): all rights reserved, downloaded from the owner's website under a user agreement, with its own hosting platform later: asset previews, a locks dashboard, cheap deduplicated storage.

**Signature experience.** The owner's target for `opalro start` (built in milestone 6 as [decision 113](decisions/113-presets-what-each-writes-and-how-start-picks-one.md) settles it, with the three presets of v0.1 and summary lines that say only what v0.1 does; what it prints exactly is in [terminal.md](terminal.md) §12):

```text
$ opalro start

Looks like a game project (found Unity files and 2.3 GB of assets).

What kind of project is this?
  1. Code (apps, websites, libraries)
  2. Game  ← suggested
  3. AI / data
  4. Design / video
  5. Custom

Using "Game" settings:
  • Big files (over 1 MB) are chunked and downloaded on demand
  • .psd .fbx .blend .png files can be locked
  • Code files are stored and merged normally

Change anytime with: opalro setup
```

What it implies for the design:
- **Presets change rules, never the engine.** They decide what's chunked, lockable and ignored, and how files merge; the storage format stays the same. That is what makes "change anytime" cheap: switching presets must not rewrite history, which requires that a file's ID never depends on how it is chunked (topic 5).
- **Settings reach teammates.** The rules go in `opalro.toml` and `.opalroignore` at the project root, so everyone who copies the project gets the same behaviour (decision 008).
- **Presets know the engine.** Unity, Unreal and Godot differ in which files must be locked (Unity: scenes and prefabs; Unreal: `.uasset`, `.umap`) and which cache folders must be ignored (Unity's `Library/`, `Temp/` and `Logs/` can hold gigabytes and must never be saved). Detection applies ignore rules before reporting sizes.
- **Detection only reads names and sizes.** It never runs anything from the project.
- **Locking and on-demand download need a server**, so they arrive in v0.3; until then the rules are recorded but not enforced.
- **Scripts need a non-interactive form**, e.g. `opalro start --preset game`.

**First audience and roadmap** ([decision 001](decisions/001-first-audience-and-v0.1.md))
- **First audience:** game developers. The engine stays general; games set the priorities, first presets and benchmarks.
- **Main platform:** Windows. macOS and Linux are supported and tested in CI from the start.
- **v0.1, solo and local-only:** `start`, `save`, `status`, `changes`, `history`, `show`, `goto`, `discard`, `undo`/`redo`, `shelf`/`unshelf`, `save --amend` ([decision 021](decisions/021-v0.1-command-scope.md)), Git import including Git LFS files whose contents are on disk (decisions [002](decisions/002-git-compatibility.md) and [020](decisions/020-lfs-import.md)), chunked big files. Big files are streamed, never loaded whole into memory. Presets: Code, Game (Unity, Unreal, Godot) and Custom ([decision 016](decisions/016-presets.md)). Lines can be created (by saving away from a line), listed and switched (decision 012).
- **v0.1 milestones:** First save → Coming from Git → Working folder → Undo everything → Big files → Presets and polish ([decision 018](decisions/018-milestone-plan.md), [milestones.md](milestones.md)).
- **v0.1 release gates** ([decision 023](decisions/023-v0.1-speed-bar.md)): saving a 10 GB file uses at most about 500 MB of memory; `status` on an unchanged 100,000-file project takes under 2 seconds on an SSD; benchmark results against Git and Git LFS are published. Both gates passed when measured on 2026-11-09: saving a 10 GiB file peaked at 43.5 MB on GitHub's Linux runner and 48.7 MB on a Windows laptop, and `status` took 0.70 s on Linux and 1.16 s on the laptop. The results against Git and Git LFS are published beside them, the steps Git or Git LFS wins included ([benchmarks.md](benchmarks.md)). A third gate holds Opalro to Git on an everyday code project ([decision 099](decisions/099-a-third-speed-gate-within-twice-gits-time.md)): on Git's own source, `status` with nothing changed, a small change saved, and going back to the first version each take at most twice Git's time, on GitHub's Linux and Windows runners. Before milestone 6's speed work it failed five of its six checks ([benchmarks.md](benchmarks.md) §1). After it, on 2026-11-10, it is not met yet: `status` and the small save pass on Linux in every run and all three steps pass on Windows in six runs of seven, but going back on Linux sits at twice Git's time or over, where it was 4.5 times, and missed in five runs of seven ([benchmarks.md](benchmarks.md) §8, which also has the first two gates measured again: 43.7 MB, and 0.20 s on GitHub's Linux runner). **For v0.1** the owner ruled ([decision 128](decisions/128-v0.1-ships-without-goto-within-twice-gits-time.md)) that `status` and the small save stay held to twice Git's time, while going back is held to three and a half times ([decision 132](decisions/132-gotos-limit-is-three-and-a-half-times-gits-time.md)) and twice is its goal for v0.2; the status gate fails its nightly job from v0.1 on.
- **v0.2:** combining lines (merging, conflicts), plus making, renaming and deleting lines, tags, moves recorded in saves, and `who`.
- **v0.2 milestones:** Lines and tags → Combine → Conflicts → `who`, and v0.2 ([decision 157](decisions/157-v0.2-in-four-milestones.md), [milestones.md](milestones.md)). Moving saves between lines (Git's rebase and cherry-pick) waits until after v0.2, with conflict algebra.
- **v0.3:** sync and locking for small teams; big files and old versions download on demand.
- **Before 1.0:** Git export ([decision 002](decisions/002-git-compatibility.md)). Live two-way Git sync is not promised, but nothing may block it.
- **Later:** conflict algebra on top of decision 007, smart locks on top of decision 014, AI/data and Design/video presets (decision 016), hosting platform, GUI and editor plugins.

**Scope of this design phase.** The brief describes several products: the engine (with a Git bridge), a sync server, and a hosting platform. This phase designs the **engine** in detail, and the server and platform only as far as the engine must respect them. Each gets its own design pass before it is built.

## 2. Principles (non-negotiable)

1. **Never lose or corrupt user data.** Atomic writes (temp file + rename), repository locking, hash verification on every read and every received object, crash safety.
2. **Security by design.** Assume projects and servers can be malicious: path traversal (`..`, absolute paths, writes into `.opalro/`), symlink attacks, case-insensitive and Windows name tricks, never auto-running code (hooks) on copy, decompression and size bombs, tampered data, server permissions and locks, safe asset previews (e.g. scripts inside SVG), secret-detection warnings, signed saves later.
3. **Testability.** Unit tests; round-trip tests (save → restore → byte-identical); property-based random action sequences; differential testing against Git (import real histories, verify every snapshot); crash/kill tests; fuzzing; a malicious-repo corpus; CI on Windows, macOS and Linux; dependency auditing.
4. **Provable claims.** Reproducible benchmarks against Git, `opalro verify` for self-checking, a documented storage format spec.
5. **Correct first, fast second.** Measure, then optimize.

## 5. Design

The current design, by area. Each part links to the decision that set it.

### 5.1 Your project folder and saves ([decision 003](decisions/003-working-copy-model.md))

**In plain words.** Your project folder is separate from history: nothing enters history until you run `opalro save`. But Opalro never destroys unsaved work without keeping a copy first, so `undo` can always bring it back. It works like an IDE's local history, built into the version control system.

- **Saving.** `opalro save "msg"` records every change in the folder; `opalro save "msg" <files, folders or patterns>` records only those, patterns matched by Opalro as Git matches them ([decision 054](decisions/054-partial-saves.md)). Paths and patterns are taken from the current folder; a folder, or a folder a pattern matches, means everything in it, and an argument holding `*`, `?` or `[` is a pattern (as Git matches globs: `*` stays within a folder, `**` crosses folders). The new save is the last one with what is named taken from the folder, deletions included; everything else stays as the last save has it and shows as unsaved in `status`. On a drive that ignores letter case (or Unicode composition), paths match whatever the case, as the drive does; patterns fold ASCII letters only, as Git folds them under `core.ignorecase` (so `[[:upper:]]` takes small letters too). A literal path holding `[`, `*` or `?` is named with a class holding the character, such as `a[[]1]` for `a[1]`: `\[` can't work, since Windows takes `\` between names. Refused, saving nothing: an argument matching nothing in the folder or the last save, a path outside the project, and a new file an ignore rule keeps out named outright (a pattern just leaves such a file out). Only the files named are read, so the file-state cache afterwards vouches only for them. Choosing parts of a file comes later. A save that adds more than 100 MB or 10,000 new files (files where the last save holds none under a name the drive takes as the same, counted from the sizes the walk saw, before anything new is read or stored) asks first, naming the three top-level folders holding the most new bytes, or stops without a terminal and names `--yes`; at a save, the new line's name is asked for before it ([decision 056](decisions/056-question-before-large-saves.md)). The two numbers are the project's own: `ask-before-saving-over` and `ask-before-saving-files-over` in `opalro.toml`, which the Game preset sets to 1 GiB and 10,000 ([decisions 113](decisions/113-presets-what-each-writes-and-how-start-picks-one.md) and [114](decisions/114-bolt-toml-keys-and-how-bolt-reads-it.md)).
- **Amending** ([decision 074](decisions/074-save-amend.md)). `opalro save --amend ["message"] [paths]` replaces the newest save of your line with one holding the folder's changes on top of it (all, or those named), and the new message or the old one (an empty message keeps it, so `opalro save --amend "" <paths>` amends only those paths). It keeps the old save's parents, author, change ID and `line`; the saver is you, now; Git's fields go, since the save no longer matches its commit. It is refused at a save rather than on a line, and when another line, a server line or a tag names the save, or another line's history holds it along first parents, since two visible saves would then share a change ID (v0.2 shows such divergence). The old save stays stored for the undo window, and `undo` puts it back.
- **Tracking.** New files are tracked automatically (there is no `add` step) unless ignore rules exclude them. Rules keep out only files that aren't saved yet: a saved file stays saved until it is deleted, as in Git ([decision 038](decisions/038-gitignore-and-saved-files.md)). A save that adds unusually much at once asks for confirmation first, at the numbers above, which a preset writes into `opalro.toml`; `--yes` skips the question for scripts.
- **Safety copies.** Before any command overwrites or removes unsaved work, Opalro keeps it. `discard` and `shelf` keep what they throw away as a save of its own on top of the current one (a kept save): the folder's version of each changed, new or deleted file and link and each new folder, and nothing else, recorded in the diary entry so `undo` can put it all back, deletions included ([decision 071](decisions/071-a-step-records-its-change-to-the-folder.md)). They leave alone an unsaved link that could only come back as a placeholder file (one leading out of the project or through a name Opalro never writes, or any link where this system can't make links), with a warning. A file holding exactly the target of a link they expect is that link to both rules, as it is to the switch, so one another program swaps in is kept before it is removed. `goto`, `undo`, `redo` and `unshelf` never overwrite unsaved work: it stops them instead. Undo and redo keep no safety copies of what they write over, since it is all in the step's own saves; known limit: with a damaged store, what they wrote over may not read back. Kept saves live in the normal object store, so content that is already stored costs nothing extra. A new file is unsaved work too: `discard` removes it, keeping it, so the folder matches the save ([decision 050](decisions/050-unsaved-work-in-goto-and-discard.md)).
- **`discard`.** `opalro discard` throws away every unsaved change, and `opalro discard <files or folders>` only those, paths taken from the folder you are in and, on a drive that ignores letter case, matched in any case (a path two saved names match is refused, naming both): changed and deleted files are put back, new ones removed, and the project stays on its save. What it throws away is kept, before anything is touched, as a kept save its diary entry names (above). It never touches what `goto` never touches (below), nor a link it couldn't write back as a link. A path outside the project, in `.opalro`, or matching nothing is refused, and so is a discard with something in the way of a file going back; nothing changes then ([decision 050](decisions/050-unsaved-work-in-goto-and-discard.md)).
- **Shelf** ([decision 073](decisions/073-shelves.md)). `opalro shelf ["message"]` sets every unsaved change aside as a kept save, listed as a shelf, and puts the folder back to the current save as `discard` does, with the same rules. Shelves are numbered: a new one takes the smallest number from 1 that no shelf has, and is the newest. `opalro unshelf [number]` brings back the newest, or the one named, onto whatever save you are on: a switch from the save it was shelved on to the shelf, carrying other unsaved work along, so it stops, changing nothing, where the folder differs from that save at a path the shelf changes (combining comes in v0.2); then the shelf leaves the list. `opalro shelf --list` shows them. Shelving, and bringing a shelf back, can be undone; otherwise shelves are the user's own, like Git's stash: undo, redo and `undo --to` leave the list as it is. Shelving only some paths, keeping a shelf while bringing it back, and dropping one wait.
- **`goto` with unsaved changes.** Changes come along when nothing collides; otherwise Opalro changes nothing and lists them, to be saved, shelved or discarded first. A change collides where the target differs from the current save at its path or a folder above or below it, unless the change already matches the target or the folder already holds what the target holds there: a deletion the target agrees with, a file changed to the target's contents, or a new file in a folder the target adds just comes along ([decision 065](decisions/065-matching-work-doesnt-collide.md)). Ignored files the save doesn't hold, entries this computer can't hold, project links and folders that are projects of their own are never touched ([decision 050](decisions/050-unsaved-work-in-goto-and-discard.md)). Where the target puts a file or link in place of a folder, anything of these left inside it is in the way: `goto` and `discard` change nothing and list it, rather than empty the folder only partly. Where the target just removes the folder, the folder stays for what is left in it, as in Git.
- **Conflicts.** A save can contain unresolved conflicts, and the save records them (topic 7).
- **`status`** only reads; it never writes to the store.

### 5.2 What a project can contain ([decision 004](decisions/004-project-contents.md))

**In plain words.** Opalro stores exactly what's in your project and never changes a file's bytes. It checks new names when you save, so a project that works on Linux won't break on Windows or a Mac, and it refuses to write anything dangerous when it puts files back on disk.

- **Entry kinds:** regular file, executable file, symlink, folder (empty folders included), and a link to another project (from Git submodules; not fetched, and kept as it is by every save: [decision 036](decisions/036-submodules-as-bare-links.md)).
- **Bytes in = bytes out:** no line-ending conversion or any other change to contents by default.
- **Not stored:** timestamps, Windows attributes, other permissions. On Windows the executable flag keeps whatever history says.
- **Names (always):** valid UTF-8, `/` between folders, no empty, `.` or `..` parts, no absolute paths, and no part that Windows or macOS would treat as `.opalro`. A name may be at most 765 bytes and a path 4,096; a new name a save adds must fit 255 bytes, which every system holds ([decision 051](decisions/051-names-this-computer-cant-write-and-length-limits.md)). A save leaves `.opalro` spellings out with a warning, as it does `.git` spellings ([decision 059](decisions/059-bolt-spellings-left-out-like-git-spellings.md)).
- **Portability check on save:** new names that would break on Windows or macOS are refused (differences only in letter case or Unicode normalization, reserved device names, trailing dots or spaces, forbidden characters), unless the project relaxes the rule. Imported histories keep their names.
- **Never saved:** Opalro's `.opalro/` and Git's `.git/` folder, skipped without a word (decision 019). A save also leaves out every other entry whose name Git treats as `.git`, the ones an import leaves out (a `.git` file, `.GIT` where letter case counts, `git~1`, spellings with a character macOS ignores), with everything in them, in every folder and on every system, even where the last save holds one. The one exception is a folder kept as it was because this computer can't hold it ("Entries this computer can't hold", below), which keeps everything the last save holds in it; writing files out (milestone 3) checks every name again. A warning names what was left out: the entries in the folder that no ignore rule keeps out, and those the last save held. A folder below the top that holds a `.git` of its own (a nested repository, a worktree, a submodule's checkout) is left out whole, as next ([decision 046](decisions/046-nested-projects-left-out.md)).
- **Safety on write-out:** never through a symlink, never outside the project, never to a name the OS would misread; such entries are reported instead. Symlinks that leave the project, or that the OS can't create, become placeholder files with a warning. A regular file holding exactly a link's stored target (the same content ID and size) is that link's placeholder: a save reads it as the link, a switch removes or replaces it as it would the link (finishing a stopped switch included), and `discard` and `shelf` keep it before removing it; one whose bytes were changed is unsaved work like any changed file. Opalro holds each folder open and works inside it, refusing a link at every step ([decision 048](decisions/048-handle-relative-file-access.md)); entries this computer can't hold, two names that are one file on this drive included, are left unwritten ([decision 051](decisions/051-names-this-computer-cant-write-and-length-limits.md)); links are made last, files get modes 0644 or 0755 exactly on macOS and Linux, and a Windows link is a folder link when its target is a folder in the save ([decision 052](decisions/052-links-and-executable-bit-on-windows.md)).
- **Link targets** are stored with `/` between their parts. On Windows each `\` read in a target becomes `/`, as Git for Windows does, and writing a link there turns `/` back into `\`; a stored target that holds a `\` is never written on Windows ([decision 045](decisions/045-link-targets-stored-with-slashes.md)).
- **Nested projects:** a folder below the top with its own `.opalro/` or `.git` is a project or repository of its own, and the outer project's saves leave it out as if an ignore rule did: what the last save holds there stays saved, nothing new is taken, and a warning names it ([decision 046](decisions/046-nested-projects-left-out.md)). A project link (a submodule) is kept as it is, whatever its folder holds.
- **Entries this computer can't hold** (names Windows can't create, names that collide here, symlinks written as placeholders) stay in history untouched: `status` lists them as not written on this computer, and saves never record them as deleted or changed (decision 019). Saves keep them from milestone 2, when imports first bring them, and also keep a symlink that Git wrote as a plain file holding its target; a save's warnings say how many entries it kept ([decision 039](decisions/039-first-save-after-import.md)). A folder gone from disk that holds one of them comes back holding only what is kept; if a file or link now has that folder's name, the save stops and says to rename or move it.

### 5.3 How data is identified ([decision 005](decisions/005-object-identity.md))

**In plain words.** Every stored object gets an ID that is a fingerprint of its contents. A file is identified by its contents, never by how it was cut into chunks, so the same bytes always have the same ID whatever the settings.

- **Algorithm:** BLAKE3, 256-bit IDs shown as lowercase hex (short prefixes in the UI); declared once per repository, never mixed.
- **Flavors:** file contents and chunks use plain BLAKE3 (`b3sum` prints the same ID). Each structured object type (folder listings, saves, chunk lists…) uses BLAKE3's key-derivation mode with its own context string.
- **Big files:** a chunk list links the file's ID to its chunks, and is stored under the file's ID, so a big file is found as a small one is ([decision 083](decisions/083-a-chunk-list-is-stored-under-its-files-id.md)); each chunk is checked as it is read, and the rebuilt file against its ID before use.
- **Folder listings:** one per folder; entries hold name, kind, ID and size, sorted by name in byte order.
- **Encoding:** hand-written binary format, one valid encoding per object, strict readers, test vectors in the storage spec. Serde only for data that is never fingerprinted.
- **Known but not downloaded:** a normal state everywhere; `opalro verify` tells it apart from real loss.

### 5.4 What's inside a save ([decision 006](decisions/006-save-object.md))

**In plain words.** A save points at the photo of your project (its top folder listing) and records who, when and why. Each save also has a short, stable change ID made of letters (`kxqmz`) that survives edits, and it can note files Opalro is sure you moved.

- **Fields:** top folder listing ID; ordered parents; author and saver (name, email, time, time zone); message; change ID; optional move notes; reserved signature slot; extra fields that older versions keep but ignore.
- **Change IDs:** 128 random bits, shown in the letters k–z (never confused with hex fingerprints) as Jujutsu writes them, `z` for 0 down to `k` for 15, so a save imported from Git shows the letters Jujutsu shows for its commit ([decision 122](decisions/122-change-ids-in-jujutsus-letters.md)), as the shortest unique prefix of at least 4 letters (each line's saves and their change IDs are kept in order in a sealed cache, `.opalro/cache/change-ids`, so that shortening one and `undo --list` needn't read the line from the store, on a line or at a save, and finding a save by the start of its change ID or by its whole ID reads only the saves from the line's newest down to it: [decision 105](decisions/105-the-change-id-cache-keeps-each-lines-saves-in-order.md); the list is never the reason a save is shown or gone to unchecked, and one that doesn't match the saves is dropped and rebuilt from the store: [decision 109](decisions/109-the-speed-sessions-follow-ups-and-format-1s-three-open-rows.md); a list is made only for a line the project is on, and when the lists outgrow the file the position's own is the one kept: [decision 111](decisions/111-rulings-after-the-first-red-team-session-on-the-speed-work.md); the check before an amend keeps what it read of the other lines in a cache of its own, `.opalro/cache/other-lines`, so a later amend doesn't read them again: [decision 112](decisions/112-rulings-after-the-second-red-team-session-on-the-speed-work.md)); kept across edits; marked "divergent" when two visible saves share one. A save imported from Git takes its change ID from its commit instead ([decision 032](decisions/032-exact-repeatable-commit-import.md)).
- **Move notes:** recorded only when Opalro is certain (same contents moved, or a Unity `.meta` file moved with its asset); used by diffs, merges and locks; they never change the snapshot.

### 5.5 Conflicts ([decision 007](decisions/007-conflicts.md))

**In plain words.** When two lines of work change the same thing differently, Opalro keeps every version in the save, like a sticky note, so you can keep working and fix it later. Nothing is lost, and it works for binary files too.

- **Record:** a folder-listing entry of kind "conflict" points to a record with the sides and the ancestors between them (any of which can be "absent"), plus your half-fixed version if you started fixing it.
- **In your folder:** text files get standard markers with the ancestor section; binary files keep your version in place, with the other versions kept inside `.opalro/`. Presets decide per file type (the Unity preset treats scenes, prefabs and `.meta` files like binaries).
- **Fixed** when the markers are gone, or when you mark the file as fixed.
- **Planned later:** conflict algebra, jj-style automatic simplification of conflicts. The record's general form allows it without a format change.

### 5.6 Settings and the `.opalro/` folder ([decision 008](decisions/008-layout-and-settings.md))

**In plain words.** The project's rules live in two normal files at the top of your project, so they travel with it and are part of its history. Your personal settings stay on your machine and can never change the project's rules.

- **Project rules:** `opalro.toml` (the `preset` label, `chunk-files-over`, the large-save question's two numbers, and `[[rule]]` tables that mark files lockable or keep conflict markers out of them; a file or key Opalro can't use is passed over with a warning and Opalro's own value applies, so nothing in it stops a command: [decision 114](decisions/114-bolt-toml-keys-and-how-bolt-reads-it.md)), purely declarative, and `.opalroignore` (the `.gitignore` syntax, read and matched exactly as Git does; [storage-format.md](storage-format.md) §12 gives the details and its limits). Opalro reads a folder's `.gitignore` too, before its `.opalroignore` ([decision 038](decisions/038-gitignore-and-saved-files.md)), and Git's two personal lists, the user's own and `.git/info/exclude`, before the top folder's, as Git does ([decision 047](decisions/047-git-personal-ignore-lists-read.md)), following plain includes in the user's own Git settings ([decision 060](decisions/060-user-git-settings-includes-and-paths.md)).
- **Personal settings:** identity, editor, merge tools, display; kept in your user config folder and never shared. v0.1 reads four things there: your name and email, `safe-folders`, `undo-window-days`, and the Git words it has already explained ([decision 116](decisions/116-gits-words-as-shortcuts.md)); `.opalro/config.toml`, the place for one project's personal settings, holds nothing Opalro uses yet, and a name or email written there is ignored with a note. Your name and email come only from you: `OPALRO_USER_NAME` and `OPALRO_USER_EMAIL`, else a `[[project]]` entry in your own settings for this exact folder (written as a full path), else `[user]`; a project's own settings are ignored, with a note ([decision 025](decisions/025-red-team-m1-rulings.md)). Opalro uses a project only when both its folder and its `.opalro/` belong to you, as Git requires ([decisions 025](decisions/025-red-team-m1-rulings.md), [026](decisions/026-ownership-check-details.md) and [027](decisions/027-project-folder-must-be-yours.md)). Every command, `opalro start` and `opalro import` included, first resolves the folder it runs in, so a project reached through a link or junction is judged by the folder its `.opalro/` is in, and the resolved path is the one Opalro shows (a mapped or `subst` drive appears as the folder it leads to); a `.opalro/` that disappears while its owner is looked up stops the command, which can simply be run again. On Windows, folders the Administrators group owns count as yours only in an elevated terminal, as in Git ([decision 030](decisions/030-administrators-only-when-elevated.md)). To trust a folder anyway (a shared folder, a drive that records no owner, or your Windows home folder itself, which Windows gives to SYSTEM), list that exact folder in the top-level `safe-folders` list of your own settings (above any `[section]`; Opalro never suggests it for a folder other accounts can write to, such as `/tmp`, or the root of a drive or share on Windows, where anyone could have planted the project: [decision 042](decisions/042-trust-hint-skips-folders-anyone-can-write-to.md)). Anything that runs a program is personal only.
- **`.opalro/`:** `format` (version + feature list), `store/` (saved data), `state/` (lines, operation log), `cache/` (rebuildable), `tmp/` (files being written), `config.toml` (personal). Hidden on Windows.
- **Format safety:** if `format` lists a feature Opalro doesn't know, it refuses to open the repository and asks to be updated. Format upgrades only happen when you ask, through `opalro setup` (format 1 has none to offer: [decision 115](decisions/115-bolt-setup.md)); the one exception is `feature chunks`, which a repository from before milestone 5 gains before a command stores anything in it ([decision 083](decisions/083-a-chunk-list-is-stored-under-its-files-id.md)). Format 1 freezes when v0.1 is released: every later Opalro reads what v0.1 wrote, anything new on disk comes as a feature or a later format, and `feature chunks` stays a line every repository carries ([decision 121](decisions/121-format-1-freezes-at-v0.1.md)).

### 5.7 How data is stored ([decision 009](decisions/009-storage-engine.md))

**In plain words.** Each command writes its new data into one or more "pack" files, each of which only appears once it's complete, so a crash can never leave half-written data in the store. Big files are cut into chunks based on their content, so an edit in the middle of a file only adds the chunks around the change (when the file format keeps edits local).

- **Packs:** written to `tmp/`, made durable, then renamed into the store; index at the end with its own checksum; a pack may hold at most 2^24 objects ([decision 028](decisions/028-red-team-m1-session-2-rulings.md)), and the writer starts a new one every 2^20, so a command that stores more writes several, and only its last holds the diary entry ([decision 041](decisions/041-several-packs-per-command.md)). From milestone 3 a pack's index has fixed-width lines searched on disk, packs open only when needed (at most 16 at once, however many hold an object; the pack that held the last object is searched first if open, then the other open ones, then the closed ones, [decision 061](decisions/061-pack-copy-order-and-lazy-opening.md)), and once more than 32 packs are small (under 64 MiB on disk, and at most 256 MiB uncompressed as their index records) a changing command, after it has committed, merges the small ones into one ([decisions 057](decisions/057-pack-index-on-disk-and-merging.md) and [062](decisions/062-when-packs-are-merged.md)); other packs wait for `tidy`, a damaged or unreadable pack is left out, and anything that goes wrong is a `pack_not_merged` warning, never a failed command.
- **Chunking** ([decision 082](decisions/082-how-big-files-are-cut-into-chunks.md)): a file of 1 MiB to 128 GiB (the 1 MiB is `opalro.toml`'s `chunk-files-over`, which a project can raise: [decision 114](decisions/114-bolt-toml-keys-and-how-bolt-reads-it.md)) is cut with Opalro's own FastCDC (its 2020 form, normalized at level 1) into chunks of 16 KiB at least, about 64 KiB on average and 256 KiB at most; the cutter's table comes from BLAKE3, so storage-format.md §6 states it exactly, and test vectors pin the cut points, so a file is cut at the same places on every computer. Each chunk is stored once, however many versions and files share it. Tuning waits for measurements on real assets.
- **Chunk lists** ([decision 083](decisions/083-a-chunk-list-is-stored-under-its-files-id.md)): a big file's chunk list is stored in a pack under the file's own ID, so a lookup of the file finds it with no cache. A whole copy and a chunk list are both copies of the file; a chunk is always content stored whole, so reading never goes deeper than one list. Merging copies chunk lists last, so a list, which it checks only by its structure, never takes the place of a checked copy under the same ID. A repository that may hold lists says so in `.opalro/format` (`feature chunks`), so that builds from before milestone 5, which can't read them safely, refuse it; it is the one format change made without `opalro setup`.
- **One read, several threads** ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)): whatever stores a file (a save, a safety copy, an import) reads it once: a small file whole, a big one cut as it is read. Worker threads (as many as the machine runs at once, at most 8) read, hash and check files and hash, check and compress chunks; one thread writes every pack in a fixed order, so a command writes the same packs whatever the timing.
- **Compression:** zstd per chunk, fast on save; incompressible data stored raw; sizes recorded so decompression bombs are caught. Merging and `tidy` copy stored bytes as they are. They would compress again at a stronger level only if a level saved at least 10% at no more than 5 times the time ([decision 088](decisions/088-benchmarks-and-the-speed-gates.md)); measured on 2026-11-09, level 9 saves 2.6%, and level 19 saves 8.8% but takes 53.5 times as long, so neither does ([benchmarks.md](benchmarks.md) §5). On a few kinds of file Git's zlib shrinks more than zstd at level 3 (Godot's demos take 3% more in Opalro, most of it six `.hdr` images), and Opalro keeps level 3 for its speed ([decision 103](decisions/103-where-git-keeps-less-zstd-level-3-and-the-chunk-sizes-stay.md)).
- **Flushing:** a pack is flushed to the disk before it is renamed into the store. One that grows past 16 MiB is also flushed as it is written, every further 16 MiB, by a helper thread, so that the disk works while Opalro still reads and hashes and the last flush has little left to do; a flush that fails on the way fails the command ([decision 102](decisions/102-big-files-are-flushed-while-they-are-written.md)).
- **Reading:** a record is found in a pack's index with a few small reads, and a copy stored in at most 1 MiB (for a file's contents, one that is at most 1 MiB unpacked too) is read whole and, when it is one ordinary zstd frame, decoded in one call; anything else goes through the streamed path. Both refuse, with the same words, whatever a zstd frame's header and its blocks' headers show format 1 refuses; what only unpacking shows is read as zstd reads it ([decision 154](decisions/154-format-1s-zstd-is-exactly-one-frame.md), [storage-format.md](storage-format.md) §11). Small reads that sit side by side are answered from the last 64 KiB block read of a pack's entries, or of its index; a block is read only at the second read in a row that falls in it, so a scattered read costs a small read ([decision 111](decisions/111-rulings-after-the-first-red-team-session-on-the-speed-work.md)), and only while the blocks read come to at most four times the bytes asked for, so no order of reads costs more than five times what it asks for ([decision 112](decisions/112-rulings-after-the-second-red-team-session-on-the-speed-work.md)). A switch reads each chunk whole and keeps the chunks it has checked while it writes one file, up to 8 MiB of them, so a chunk a list repeats is read once ([decision 109](decisions/109-the-speed-sessions-follow-ups-and-format-1s-three-open-rows.md)). At most 16 packs are open for each handle on the store ([decision 061](decisions/061-pack-copy-order-and-lazy-opening.md)).
- **Deltas:** later, as a format feature, for small text files.
- **Cleanup** ([decision 077](decisions/077-tidy-and-the-undo-window.md)): `opalro tidy` keeps everything the current state reaches (lines, the save you are at, shelves, tags, server lines, with all their history), every diary entry from `head` back (and, within the undo window, every diary end with its diary, so a diary cut off from `head` survives; [decision 079](decisions/079-red-team-m4-rulings.md)), and, for every entry within the undo window, everything an undo or redo of it (or of what it undid or redid) needs: the states before and after it and its folder change, and those of its target; it leaves packs changed in the last 24 hours untouched. It deletes unread a pack with nothing to keep, rewrites as version 2 one holding anything else, a small one or one in version 1 (each kept object checked, its stored bytes copied as they are), and removes old packs only once the new ones are on disk; it says how much it will free, and then what it freed. It follows chunk lists: every chunk a kept file's chunk list names is kept, and so is every chunk a list in a young pack names. To mark what to keep it reads only records and chunk lists, never a file's contents: one of those it can't read stops it before it removes anything, and so does a pack it can't open or whose index it can't read or check, since it could hold the only list naming chunks elsewhere ([decision 083](decisions/083-a-chunk-list-is-stored-under-its-files-id.md)). Two rules keep that from stopping it for good ([decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)): before it removes anything it writes the start of the undo window it used into `.opalro/state/tidied`, and the next `tidy` never reaches back past that time, so a window made longer doesn't ask for what it already freed; and a diary end whose diary can't be read back is passed over, keeping what could be reached from it, with a `diary_end_unreadable` warning. Cleanup on its own and the size budget for safety copies wait.
- **`opalro verify`** ([decision 118](decisions/118-bolt-verify.md)) checks everything at once, changing nothing and taking no lock: every pack opens, its index matches its checksum, and each object reads back as what the index says (records decoded, each chunked file rebuilt); then, from `head`, that everything `tidy` would keep is there. Something that looks missing is looked for again from the start, and reported only when two looks agree, so a save, merge or `tidy` running beside it can't make it report damage that isn't there. It lists every problem (counting them all, keeping the first 1,000), naming the save and path that need a missing object; it also reports what would stop a save from being written out: a chunk held only as another kind of object, a folder listing whose size for a file isn't the file's, and a save past the entry, depth or path limits every reader keeps (`save_too_big`; [decision 126](decisions/126-verify-also-finds-a-save-that-cant-be-written-out.md)). It shows a progress bar by bytes of pack read in a terminal, and ends with exit code 1 when it found a problem; `opalro fsck` runs it too. v0.1 can't repair. Its memory grows with the number of objects, as `tidy`'s does ([follow-ups](plans/2026-11-01-milestone-1-follow-ups.md)), never with what a listing repeats ([decision 127](decisions/127-what-verify-holds-is-bounded-and-two-costs-are-written-down.md)).
- **Checking:** every object is verified against its fingerprint on read, and a stored copy is read and verified before a save relies on it instead of storing its own (a stored chunk list counts once the save has cut the same file into exactly its chunks, each checked or stored in that pass: [decision 083](decisions/083-a-chunk-list-is-stored-under-its-files-id.md)); a bad copy is passed over for a good one in another pack, with a warning ([decision 028](decisions/028-red-team-m1-session-2-rulings.md)). Copies are tried smallest first, except that a first copy found of at most 1 MiB is read before the other packs are searched ([decision 061](decisions/061-pack-copy-order-and-lazy-opening.md)), and a save skips, unread, a copy whose recorded size isn't the object's, so a planted copy claiming a huge size can't slow it down ([decision 029](decisions/029-red-team-m1-final-review-rulings.md)).

### 5.8 Operation log and undo ([decision 010](decisions/010-operation-log.md))

**In plain words.** Opalro keeps a diary of every command that changed something. Each entry records the whole state of the repository afterwards, so `undo` simply goes back to an earlier entry, like Ctrl+Z in an editor. Changing commands take turns, and a crash can never leave a command half-done.

- **Entries:** objects in the store; each holds the full state (every line, where you are, shelves), what the command did to the folder (if anything: two saves holding what the folder held and what the command wrote, at exactly the paths it wrote), its parent, and metadata. Tags and server lines, which change rarely, sit in records of their own that entries point to and share while unchanged ([decision 034](decisions/034-tags-kept-and-shared.md)). What `discard` and `shelf` throw away is kept as a save of its own, which the entry's switch names ([decision 071](decisions/071-a-step-records-its-change-to-the-folder.md)).
- **Committing:** one or more packs (the new data, with the entry in the last one), then `.opalro/state/head` is replaced atomically. Folder rewrites are journaled first (`.opalro/state/journal`), so an interrupted command is finished on the next run, never rolled back ([decision 049](decisions/049-writing-files-one-at-a-time.md)). On Windows each rename, removal and new folder is written through to the disk, as macOS and Linux flush them ([decision 076](decisions/076-renames-reach-the-disk-on-windows.md)); once `head` has moved, a failure is only a warning ([decision 075](decisions/075-crash-recovery.md)).
- **Undo and redo** ([decision 070](decisions/070-undo-and-redo-step-through-the-diary.md)) work like an editor's. Each command is a step. `opalro undo` takes back the newest step not yet undone, `opalro redo` brings back the one undone last, and a new command clears what redo could bring back; `opalro undo N` and `opalro redo N` take N steps, one entry each. Undoing a step puts back the lines, position, tags and server lines from just before it and writes back what the folder held where the step wrote; redoing puts back its own and writes again what it wrote, both through `goto`'s planner, so other unsaved work comes along. Shelves stay as they are, except one the step itself added or removed. Unsaved work in the way stops them, changing nothing; `--shelve` sets it aside on a new shelf as part of the same step, since a separate save, shelf or discard would be the next step undo takes back. A step that changed no file (`save`, `save --amend`) changes none when undone: its changes show as unsaved again. Nothing is erased. The diary's first entry can't be undone, nor can a step whose saves `tidy` removed. After finishing a switch a crash or a file in use stopped, `undo`, `redo` and `unshelf` take no further step, so running them again doesn't go one too far.
- **`opalro undo --list`** ([decision 072](decisions/072-undo-list-and-undo-to.md)) shows the steps redo can bring back, then the steps undo can take, numbered from now for `undo N` and `redo N`, each with the start of its entry's ID; `--all` shows the whole diary. `opalro undo --to <entry>` makes the state the one right after that entry: through undos or redos when it is on that list, otherwise as one new step that puts its state back (all but the shelves) and switches the folder to its save.
- **A lost `head`** (missing, damaged, or naming an entry the store can't read) stops every command, saying the saves are safe. Then `opalro undo --list` lists the entries no other entry follows, newest first, and `opalro undo --to <entry>` makes one current, without touching any file ([decision 075](decisions/075-crash-recovery.md)). A switch stopped before `head` was lost is dropped then, as no command could finish it, and a `switch_dropped` warning says so ([decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)).
- **Other people:** undo changes only your repository; for sent saves and locks, Opalro offers the opposite action (v0.3).
- **Concurrency:** one changing command at a time behind an OS-held lock; read-only commands never wait.
- **Undo window:** the personal setting `undo-window-days`, 30 days unless set; `tidy` keeps what every entry in the window needs ([decision 077](decisions/077-tidy-and-the-undo-window.md)). The optional size budget for safety copies waits.

**Example** (illustrative; the wording is settled as each command is built):

```text
$ opalro save "Add double jump"
Saved ptvz  "Add double jump"  (2 files)

$ opalro discard Assets/Scripts/Player.cs
Threw away your unsaved changes in Assets/Scripts/Player.cs (+31 −4 lines).
A safety copy was kept. Changed your mind? opalro undo

$ opalro undo
Undid: discard Assets/Scripts/Player.cs
  Player.cs is back, with your +31 −4 unsaved lines.

$ opalro undo
Undid: save ptvz "Add double jump"
  ptvz is off line main; its changes are unsaved work again.

$ opalro redo
Redid: save ptvz "Add double jump"
```

Behind the scenes, `head` points at the newest diary entry, and every entry records the full state:

```text
head ─► redo     main → ptvz                       (redoes the save)
        undo     main → kxqm                       (undoes the save)
        undo     main → ptvz   + switch ptvz → wqnm (undoes the discard: Player.cs is back)
        discard  main → ptvz   + switch wqnm → ptvz (wqnm keeps the unsaved Player.cs)
        save     main → ptvz
        save     main → kxqm
```

### 5.9 Fast status and safe writing ([decision 011](decisions/011-status-and-write-out.md))

**In plain words.** `status` remembers each file's size and last-modified time, so it only re-reads files that look changed. Anything that writes files plans first, re-checks each file right before replacing it, and never overwrites work you haven't saved.

- **Cache:** kind, size, time, change time, file ID and fingerprint per file, in `.opalro/cache/files`, trusted only for the very file it saw, unchanged since (a file moved onto the path has another ID, and one overwritten in place a new change time; [decisions 067](decisions/067-the-file-cache-matches-file-identity.md) and [069](decisions/069-the-file-cache-matches-the-change-time.md)), with a keyed checksum whose key sits in the user's own settings, so a cache Opalro didn't write for this account is rebuilt; a file not at least 2 seconds older than "now", read from the drive's own clock, is read again; `save` uses it only to tell that a file is unchanged; `opalro status --full` re-reads everything ([decision 053](decisions/053-file-state-cache.md)). It is written only when it changed, and never flushed to the disk: a cache a crash tore fails its checksum and is rebuilt ([decision 100](decisions/100-caches-are-written-without-a-flush-and-only-when-they-changed.md)).
- **`opalro save`** reads only what it must: a file the cache vouches for, whose cached fingerprint is the one the save it builds on holds, is taken from that save unread; every other file is read once, and stored as it is read, on several threads ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)). After the walk each file's details come from a look at the file itself, never from the folder listing (on Windows a file still open for writing keeps its old size and time there), and those looks run on several threads. The walk lists each folder once and takes what the folder holds from that listing; it opens the two ignore files only when the listing could hold them, which a folder of plain ASCII names without them can't ([decision 101](decisions/101-the-walk-lists-a-folder-before-it-looks-inside.md)). On Windows the same goes for `.git` and `.opalro`; on Linux and macOS every folder is still asked for those two by name, since a FAT or NTFS drive there answers to a short name its listing doesn't show ([decision 106](decisions/106-on-linux-and-macos-a-folder-is-still-asked-for-git-and-bolt-by-name.md)). A file the last save holds isn't matched against the ignore rules while the folder is walked: the rules decide nothing about it until it changes, and it is matched then, by the rules as the walk read them ([decision 107](decisions/107-a-saved-files-ignore-rules-are-read-only-when-it-changed.md)). A folder whose entries all turn out equal to the last save's listing takes that listing's ID, without a new listing being built or stored. The last save's listings themselves are read just ahead of the walk by a helper thread, through a second handle on the store with its own open packs; the walk takes each through its own store's normal read, which is spared only the work the helper already did, so what a command says never depends on which thread was first ([decision 110](decisions/110-the-last-saves-listings-are-read-ahead-of-the-walk.md)). Both commands then keep in the cache what this walk met, so deleted files drop out, and write it only if that differs from what they read; a cache a save can't write is a `file_cache_not_stored` warning after the save is made.
- **`opalro status`** walks the folder as a save would, through the same code, reads only the files the cache doesn't vouch for, hashing them on several threads, and compares what it finds with the current save without storing anything; it lists the save's entries this computer can't hold as not written here. A cache it can't use only makes it slower: without the drive's "now" it reads every file and keeps nothing, and a cache it can't write (over 256 MiB, or a failed write) is a `file_cache_not_stored` warning, never a failed status. Goto's plan uses the same comparison, so both judge unsaved work alike.
- **Watcher:** later, optional, and only ever a speed-up.
- **Writing files:** plan → stop if unsaved work would be overwritten → store the safety copies and the new diary entry → write the journal → one file at a time, each entry re-checked just before it is replaced or removed, or a folder or link is put in its place ([decisions 079](decisions/079-red-team-m4-rulings.md) and [080](decisions/080-red-team-m4-session-2-rulings.md)), through a temp file and a rename, links last → move `head` → remove the journal. After a crash the next changing command finishes the switch ([decision 049](decisions/049-writing-files-one-at-a-time.md)).
  - **Finishing a stopped switch:** a command that changes the project (`save`, `goto`, `discard`, `undo`, `redo`, `shelf`, `unshelf` and `tidy`) does it right after taking the lock. A journal whose entry `head` already names is only removed. Otherwise the journal is carried out again (finished changes are skipped), `head` moves, the journal goes, and a `switch_finished` warning says so. It still can't finish when a file is in use (the error names it; the journal stays and `head` doesn't move) or when a change fails with an error it can't go past, such as a damaged stored copy or no permission (the error names the path, and the next command tries again once that is fixed; for a stored copy that is damaged or missing, the hint also says that deleting `.opalro/state/journal` goes on with the files as they are, [decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)). A journal that can't be used (damaged, made for another save than `head`'s, or naming an entry that can't be read) is never carried out and never passed over: changing commands refuse, naming `.opalro/state/journal`, and say that deleting it lets them go on with the files as they are; `status`, `history` and `show` say the same through `switch_unfinished`, which otherwise tells that a switch is unfinished. What finishing did is told even when the command then fails.
  - The journal's order is not the order of the work: folders are made top down, then files are written, then removals run deepest first (so a folder's contents go before the folder becomes a file), and links come last. Each entry must be what the plan found, or already what the switch puts there (so carrying out a journal twice changes nothing more); anything else is left and reported (`changed_since_plan`).
  - On a drive that ignores letter case, a file renamed only in case (`Readme.md` to `README.md`) is written over the old one under its new spelling and the old name's removal is skipped; a folder renamed only in case keeps its old spelling.
  - File contents stream from the store into a file in `.opalro/tmp`, which is flushed and renamed into place, so memory stays small whatever the file's size. A file past 16 MiB is flushed as it is written too, as a big pack is, and once more, whole, before the rename ([decision 102](decisions/102-big-files-are-flushed-while-they-are-written.md)).
- **Files in use (Windows):** try up to 10 times, 100 ms apart, finish the rest, say which files another program has open, or deleted while it still holds them on drives such as FAT and exFAT (`files_in_use`; [decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)), and fail, keeping the journal, then finish with one more command; naming the program comes later ([decision 049](decisions/049-writing-files-one-at-a-time.md)). Opalro's own files in `.opalro` (`format`, `state/head`, `state/lock-info`, `state/journal`, the caches) are replaced the same way, through a file in `tmp/` and a rename; `format`, `state/head` and `state/journal` are flushed to the disk first, while `state/lock-info` and the caches, which a crash may lose, aren't ([decision 100](decisions/100-caches-are-written-without-a-flush-and-only-when-they-changed.md)). Every rename of Opalro's own files, a new pack moved into the store included, is tried on that schedule while Windows refuses it as it refuses a file another program has open (a sharing violation, access denied, or a file still being deleted). If one of those files still can't be replaced, the command fails, naming it; a cache that can't be replaced is left as it was, and the command goes on.

### 5.10 Lines ([decision 012](decisions/012-lines.md))

**In plain words.** A line is a name, like `main` or `feature/double-jump`, that points at the latest save made on it and moves forward when you save. Each save also notes which line it was made on, so history keeps that information even after lines are combined or deleted.

- **Stored in the diary**, not as files: renaming or deleting a line can be undone, and filesystem case rules never interfere.
- **Names:** letters, digits, `-`, `_`, `.`, `/`; no spaces; no two names differing only by letter case; `opalro start` creates `main`. A new line's or tag's name can't start with `-`, so it never reads as an option; a stored name that does (from an import) still loads, renames, moves and deletes. Letter case is compared through Unicode's lowercase mapping (Rust's `to_lowercase`), not full case folding, so `ß` and `SS`, or `ΑΣ` and `ασ` (whose final sigma lowercases differently), count as different names. That stays the rule when format 1 freezes ([decision 121](decisions/121-format-1-freezes-at-v0.1.md)).
- **Not on a line:** after `goto` to a save, Opalro says you're looking at an older save; saving there asks for a new line name in a terminal, or takes it from `--line <name>` (without either it stops, saving nothing); the name follows the rules above, may not be a line's already in any letter case, and the new line and the save are one diary entry. On a line, v0.1 refuses `--line`; from v0.2 it starts a new line with the save, and the line the project was on stays where it was ([decision 158](decisions/158-making-renaming-and-deleting-lines.md)). `goto` to a save is at that save even when it is a line's newest, and then says how to keep saving on that line (the first by name, when several lines are there); `goto <line>` puts you on the line, but a line name that is also the start of another save's change ID or fingerprint is refused, listing both, so a line can't pose as a save ([decision 068](decisions/068-a-goto-target-that-names-both.md)); `opalro line` lists the lines, marking the current one, then the server lines as `line@server` ([decision 055](decisions/055-lines-in-v0.1.md)).
- **Tags:** fixed names for important saves; they never move, and changing one asks first. `opalro tag <name> ["message"] [--save <save>]` makes one, under the line-name rules, `opalro tag` lists them, and `opalro tag --delete <name>` deletes one; moving and deleting ask first, or take `--yes`. A tag's name is taken where a save is asked for (`goto`, `show`, `changes --save`, `tag --save`), after lines and server lines and before IDs, and `goto <tag>` puts the project at the tag's save, not on a line. A name that is a line or a server line and also a tag at another save is refused, naming both saves, as a name that is also the start of an ID is; only an import or a planted project brings such a pair, since a new tag can't take a line's name. `history` and `show` name the tags at each save. An imported tag's name can be any text: one that doesn't fit the line-name rules is shown between double quotes, with `"`, `\`, `[` and `]` marked inside, so it can't pass for a line's mark or for two tags. No hint puts text from the project inside a command unless it is plain (a line name's characters, not starting with `-`), and a save's ID in a hint is one the command will take: a fingerprint finds any save a line, a server line or a tag reaches along first parents ([decisions 159](decisions/159-tags.md), [162](decisions/162-red-team-m7-rulings.md) and [163](decisions/163-red-team-m7-session-2-rulings.md); milestone 7).
- **In v0.1:** lines can be created (by saving away from a line), listed and switched.
- **Making, renaming and deleting (v0.2, milestone 7; [decision 158](decisions/158-making-renaming-and-deleting-lines.md)):** `opalro line new <name>` makes a line at the save the project is on and moves onto it, leaving the folder alone; `opalro save --line <name>` does the same and saves, from a line too. `opalro line rename [<old>] <new>` renames a line; saves already made keep the old name as the line they were made on. `opalro line delete <name>` takes a name away, never the line the project is on, and asks first (or takes `--yes`) when no other line, tag or server line holds the line's newest save in its history, through every parent ([decision 160](decisions/160-whether-a-save-is-in-anothers-history.md)). Each is one diary step that `undo` takes back; a deleted line's saves stay stored for the undo window.
- **Combining (v0.2, milestone 8; planned, not built yet):** `opalro combine <target>` brings another line's work into the line you're on, as one diary step that `undo` takes back ([decision 165](decisions/165-combine-the-command.md)). When your line already has everything, nothing happens; when it hasn't moved since the other left it, it just moves forward; otherwise a combined save is made at once, with both saves as parents. Opalro finds where the two parted ([decision 164](decisions/164-where-two-lines-parted.md)): no common save, and the combine is refused; several (two lines that were each combined into the other), and they are combined with each other first. The two versions are merged entry by entry ([decision 166](decisions/166-merging-two-versions-of-the-project.md)): what only one side changed is taken, folders are merged one level down, and a file's executable mark and contents are merged apart. Text both sides changed is merged line by line when the changes neither overlap nor touch, with line endings compared as bytes; binaries, and files whose rule says `conflict-markers = false`, are never merged automatically ([decision 167](decisions/167-merging-text-line-by-line.md)). A save notes a move when Opalro is certain of it, and a combine follows the notes, so a change to a moved file lands where the file went ([decision 168](decisions/168-moves-in-saves-and-in-combines.md)). In milestone 8 a combine that would leave a conflict stops and changes nothing; milestone 9 keeps it. `history` stays the line's own story, marks a combined save, and a save a combine brought in is found by its ID ([decision 169](decisions/169-saves-reached-through-a-combine.md)).
- **Server lines (v0.3):** shown as `main@origin`. Until then the only ones are the server branches a Git import brought in ([decision 033](decisions/033-git-branches-to-lines.md)).

### 5.11 What's on your computer ([decision 013](decisions/013-local-data-and-offline.md))

**In plain words.** Your computer always has the whole history (every save, folder listing and small-file version) plus the current version of every big file, as real files. Older versions of big files download when you need them, and pinning keeps chosen ones available offline.

- **Always local:** saves, folder listings, diary entries, every small-file version.
- **Big files:** current versions fully downloaded (never stubs); older versions on request; offline errors name exactly what's missing.
- **Pinning:** keep chosen saves or folders available offline.
- **Freeing space:** only versions the server has confirmed it holds can be dropped.
- **Later:** partial workspaces for huge projects.

### 5.12 Locking ([decision 014](decisions/014-locking.md))

**In plain words.** Files that can't be merged (textures, models, engine scenes) can be locked: while you hold the lock, nobody else can send changes to that file on any line. Locks arrive with the server in v0.3; locks that follow a change until it reaches `main` come later.

- **Which files:** patterns in `opalro.toml`, filled in by presets.
- **Early warning:** lockable files stay read-only until you lock them (a personal setting turns this off).
- **Locking:** `opalro lock <file> "<why>"`; `opalro status` shows who holds what.
- **Release:** automatic on send, unless you ask to keep the lock.
- **Safety net:** the server refuses changes to files someone else has locked.
- **Forgotten locks:** maintainers can break them; the holder is told and keeps their work.
- **Offline:** you can edit on request, with a warning; Opalro takes the lock when you're back online.
- **Planned later:** smart locks that release once the change reaches the integration line.

### 5.13 Syncing ([decision 015](decisions/015-sync.md))

**In plain words.** Your copy and the server first compare which saves they have, then move only the missing pieces, each identified by its fingerprint. Every piece is checked on arrival, transfers resume where they stopped, and a big file that changed in one spot uploads only the changed chunks.

- **Transport:** HTTPS; browser login; tokens in the OS credential store.
- **Trust nothing:** both sides verify every piece against its fingerprint.
- **Server storage:** chunk packs in object storage (S3 / R2), everything else in PostgreSQL; chunks are shared only within a project or organization, and only after proof of possession.
- **Permissions:** roles per project and protected lines; folder-level permissions later.
- **Folder remotes:** the same layout on a USB drive or NAS, for backups (no locks).
- **Versioned protocol** from the first release.

### 5.14 Presets ([decision 016](decisions/016-presets.md))

**In plain words.** A preset is a starter set of project rules. `opalro start` detects what kind of project you have, suggests a preset and writes all of its rules into `opalro.toml` and `.opalroignore`, so everything Opalro does is visible and editable in your project.

- **Detection:** names and sizes only, never a file's contents; cache folders skipped; never through a link, and at most 128 folders down; stops early on huge folders (after 20,000 entries, then says "more than"). It only suggests: planted files can change the suggestion, never what is written without an answer. Unity, Unreal and Godot are known by their project files, and eight languages by their manifests; what Opalro prints about it is fixed words, never a name from the folder ([decision 113](decisions/113-presets-what-each-writes-and-how-start-picks-one.md)).
- **The question:** in a terminal `opalro start` asks, with its suggestion as the default; `--preset code|game|custom` answers for a script, and without a terminal or the flag nothing is started. A folder that already has an `opalro.toml` keeps it and is asked nothing.
- **Rules:** read top to bottom, later rules win; `.opalroignore` pattern syntax; settings like `lockable` and `conflict-markers`.
- **v0.1 presets:** Code (apps, websites, libraries, scripts), Game (Unity, Unreal, Godot), Custom. AI/data and Design/video later.
- **Code preset:** no locks, markers for all text, ignore lists for every detected language, `.env` ignored, asks before saving more than 100 MB or 10,000 new files at once, normal chunking for big files.
- **Game preset:** art, audio and each found engine's scenes and assets marked lockable, Unity's scenes, prefabs and `.meta` files kept free of conflict markers, the found engines' caches and generated files ignored, and the question asked from 1 GiB or 10,000 new files. Its ignore lists are a reviewed part of GitHub's templates: when in doubt, a file is saved.
- **Custom** writes no file: a project without an `opalro.toml` gets Opalro's own values.
- **Writing the files:** one diary step, `setup`, right after the start, so `opalro undo` takes the rule files away again; a `.opalroignore` that was there keeps every line, with the preset's block, between two marker lines, added at its top, so the user's own lines below it win. If the rule files can't be written, the project is still started, and the command ends with an error whose hint says to write them with `opalro setup --preset`.
- **Changing presets:** `opalro setup --preset` shows the exact line changes to both files, asks (or takes `--yes`), and applies them as that same undoable step; `opalro setup` alone shows the rules as Opalro reads them ([decision 115](decisions/115-bolt-setup.md)).

### 5.15 Commands and messages ([decision 017](decisions/017-commands-and-output.md))

**In plain words.** Opalro uses its own friendly words (`save`, `goto`, `combine`…) but quietly accepts Git's words too, so Git users aren't stuck. Every error explains what happened, why, and what to do next.

| When | Commands (Git word) |
|---|---|
| Starting | `start` (init) · `setup` · `import` · `export` (before 1.0) |
| Every day | `status` · `changes` (diff) · `save` (commit) · `save --amend` (commit --amend) · `discard` (restore) · `undo` / `redo` · `shelf` / `unshelf` (stash) |
| History | `history` (log) · `show` · `who` (blame; v0.2) · `goto` (checkout/switch) · `reverse` (revert; v0.3) |
| Lines (v0.2) | `line` (branch) · `combine` (merge) · `resolve` · `tag` |
| Team (v0.3) | `copy` (clone) · `get` (pull) · `send` (push) · `lock` / `unlock` / `locks` · `login` · `pin` |
| Upkeep | `verify` (fsck) · `tidy` (gc) |

- **Built so far** (milestones 1 to 7; milestone 5 added no command): `start` (`--preset code|game|custom`), `setup` (with `--preset` and `--yes`), `import`, `save` (with `--amend`, `--line`, `--yes` and `--accept-crlf`), `status` (`--full`), `changes` (`--save`), `goto`, `discard`, `undo [N]` and `redo [N]` (with `--shelve`), `undo --list [--all]`, `undo --to <entry>`, `shelf ["message"]`, `shelf --list`, `unshelf [number]`, `tidy`, `verify`, `line`, `history` and `show`, with `--version`, and `opalro` alone printing an overview of the commands. Milestone 7 added `line new <name>`, `line rename [<old>] <new>`, `line delete <name>` (with `--yes`), `save --line` from a line ([decision 158](decisions/158-making-renaming-and-deleting-lines.md)), and `tag`, `tag <name> ["message"]` (with `--save` and `--yes`) and `tag --delete <name>` (with `--yes`), a tag's name taken wherever a save is asked for and shown by `history` and `show` ([decision 159](decisions/159-tags.md)). The rest of the table comes with the milestone or version that builds it.
- **Git's words** are hidden shortcuts: `commit` (with `-m`), `diff`, `log`, `checkout`, `switch`, `stash` (with `pop` and `list`), `branch`, `init`, `fsck` and `gc` run the Opalro command, the first use of each in a terminal naming Opalro's word once. `checkout -b <name>` and `switch -c <name>` run `line new`, `branch -m` runs `line rename`, `branch -d` runs `line delete`, and `branch -D` runs it with `--yes`. `tag` is Opalro's own word, and `tag -d <name>` runs `tag --delete <name>`. `restore` is explained and never run, since `discard` also removes new files; so is `branch <name>`, which in Git makes a branch and stays where it is, while `line new` moves onto it, and so are `checkout -b` and `switch -c` given a starting point, words with no Opalro command yet (`add`, `merge`, `blame`, `push`…) and Git forms that would mean something else in Opalro ([decisions 116](decisions/116-gits-words-as-shortcuts.md), [124](decisions/124-restore-is-explained-and-a-shortcut-takes-nothing-for-what-it-isnt.md), [158](decisions/158-making-renaming-and-deleting-lines.md) and [159](decisions/159-tags.md)).
- **How it looks** ([decision 120](decisions/120-the-terminal-ui.md), [terminal.md](terminal.md)): the owner's design sets the look, Opalro's decisions the facts. The outcome comes first, then details, then at most one next step; the terminal's own colours mark what happened, IDs, paths and commands, on Windows too; symbols fall back to plain characters where the console can't show them; long lines wrap and long paths give way only in a terminal, so logs and scripts get one line per message; progress shows only in a terminal.
- **Output:** `--json` on every command, frozen as `opalro_json` 1 at v0.1 ([decision 117](decisions/117-what-json-covers-at-v0.1.md)); colors and progress only in a terminal; no questions without a terminal; examples first in help. When stdout can't take what a command prints (its reader has gone, or a write fails), stderr gets it as text instead: the command's error, then its warnings, then, only when a write failed, that the output couldn't be written. The exit code is the command's own when only the reader went; a failed write makes it 1 ([json.md](json.md) §5).
- **`changes`** shows unsaved changes (`opalro changes [paths]`), or what a save changed against its first parent (`opalro changes --save <save>`, so a path is never taken for a save), line by line in the unified form with 3 lines of context, with the `similar` crate; binary files (a zero byte in the first 8,000), files over 64 MiB and files of more than 1,000,000 lines on either side show as changed without lines, a file whose only change is its line endings says so, a removed and an added line that differ only in their ending are marked (`(CRLF)` after the one that ends in CRLF; `"eol_only": true` on both in `--json`), and each file gets at most 2 seconds, past which its changes show coarser and a `diff_timed_out` warning says so. Colour is used only in a terminal; on Windows Opalro first asks the console to read colour codes, through the call clap already brings, with no new `unsafe` code of Opalro's, and shows no colour when the console refuses ([decision 120](decisions/120-the-terminal-ui.md)) ([decisions 058](decisions/058-changes-line-by-line.md), [063](decisions/063-changes-takes-the-save-with-a-flag.md) and [064](decisions/064-changes-line-limit.md)).
- **`--json` formats:** every document, field and kind of warning is in [json.md](json.md).

### 5.16 Importing from Git (milestone 2)

**In plain words.** `opalro import` turns a Git repository's whole history into Opalro saves, in place next to `.git/`, without changing the Git repository. Opalro reads Git's files itself, with the same care it takes with its own: nothing in them is trusted, every read is bounded, and big files flow straight through.

- **Already decided:** every branch becomes a line and every tag a tag; each save records its Git commit in the extra field `git-commit`; paths that aren't valid UTF-8 stop the import with a list of where they occur; messages in other encodings are converted to UTF-8, keeping the original bytes; `.opalro` entries in Git trees are skipped and the summary lists them, a `.opalro` folder Git checked out below the top gets a warning, and one Git tracks at the top stops the import before anything is written, since Opalro never takes files Git wrote for its own; up to 1,024 parents ([decision 019](decisions/019-review-clarifications.md)). Submodules become project links ([decision 004](decisions/004-project-contents.md)); Git LFS files come in from `.git/lfs/objects`, which must hold every version the history names ([decisions 020](decisions/020-lfs-import.md) and [085](decisions/085-importing-git-lfs-files.md)).
- **Reading Git** ([decision 031](decisions/031-own-git-reader.md)): Opalro's own read-only reader, for loose objects, packs and their deltas, refs, and from `.git/config` only the format lines, plus two settings it reads only to refuse: `core.sparseCheckout` and `lfs.storage`. Both are read from `config.worktree` too when `extensions.worktreeConfig` is set, and from the user's own Git settings as well (`lfs.storage`: [decision 089](decisions/089-git-lfs-objects-kept-elsewhere.md); `core.sparseCheckout`: [decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)), read where Git reads them, as the user's ignore list is ([decision 094](decisions/094-red-team-m5-rulings.md)): the file `GIT_CONFIG_SYSTEM` names unless `GIT_CONFIG_NOSYSTEM` is true, then the file `GIT_CONFIG_GLOBAL` names in place of `$XDG_CONFIG_HOME/git/config` and `~/.gitconfig`, with their plain includes, and last, after the repository's own, the settings `GIT_CONFIG_COUNT` gives; a value Git refuses there stops the command, naming the variable. `~` is the home folder Git uses: `HOME`, and on Windows, where it is usually unset, `HOMEDRIVE` followed by `HOMEPATH` when that names a folder, else `USERPROFILE`; with none, no `~/` file is read, and an include whose path starts with `~/` stops the import, as it stops Git ([decision 097](decisions/097-red-team-m5-session-2-rulings.md)). A `~/` `lfs.storage` doesn't stop it: the import only compares that value and never expands it. The import doesn't read `core.excludesFile`; the commands that read the user's ignore list, such as `save` and `status`, stop at the first one that starts with `~/`, even where a later one overrides it ([storage-format.md](storage-format.md) §12). The system's own file when `GIT_CONFIG_SYSTEM` doesn't name it, `[includeIf]` sections and `-c` options stay unread. It reads SHA-1 and SHA-256 repositories.
  - No memory-mapping, and every read is bounded. Files in `.git` are opened without following links; only blobs over 64 MiB stream into Opalro's pack, read once, hashed and cut into chunks as they pass ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)), while smaller blobs and every commit, tree and tag are read whole; and every Git object's ID is checked as it is read (SHA-1 with collision detection).
  - A deltified object and its base may each be at most 512 MiB, which Git never exceeds by default; so may any object read whole into memory, and so may a delta say it holds. An object read whole is allocated only if the compressed bytes it has (a packed one's, the rest of its pack) could hold it: deflate expands at most 1,032 to 1, so a 30-byte file that says it holds 500 MiB is refused before any room is made. A delta is applied as it inflates, its instructions read in order through a small buffer, so rebuilding holds two objects whole, the base and what it builds, and never the delta. A file over 64 MiB that Git stored whole streams through at any size, and a loose object may say it holds at most 1 TiB.
  - Every zlib stream inflates in full, checked against the size its object gives. One that ends sooner stops the import: Git never writes one, so the repository was damaged or made that way, which `git fsck` doesn't always notice, or Opalro's reader is at fault, and the hint says both. An object that says it holds more than its compressed bytes can is refused as damage.
  - A delta chain may be at most 4,096 deep (Git's own cap is 4,095), and one that loops is refused. Bases rebuilt along the way, and the objects they build, are kept for the next delta built on them, at most 96 MiB of them, which is Git's own default for the same cache ([decision 104](decisions/104-an-import-keeps-96-mib-of-rebuilt-objects.md)), a base staying in the cache when used; a big file's whole family is rebuilt once (below). Asking for an object's type walks down its chain to the type at the bottom; what that walk learns of each entry it passes (the type, how deep the entry is, and what it builds once that was asked) is kept for good, since an entry never changes, for the first 524,288 entries (about 43 MB, and about 64 MB for a moment while the table grows). So no later walk passes one of those entries again, however many tags, commits or files ask. Past that many nothing more is kept, so walks through other entries repeat, though each is still counted against the allowance.
  - Rebuilding objects through deltas may take an import at most 4 GiB of work, or 500 bytes for each compressed byte of the pack entries it has inflated so far if that is more, each entry counted once. Each delta inflated, what it builds, and the object stored whole that the chain starts from count as work, before each step is taken; so does each entry header a walk down a chain reads past the first, 1 KiB each, about what reading one from disk costs in time. A few bytes of delta can build a big object again for every read through it, so past the allowance the import stops, saying which file or commit it was reading, and that the repository holds a long history of small edits to a big file or was built to make importing slow: each version is built once (below), but a small edit adds only a few hundred bytes to what is inflated, so a history of hundreds of versions of one big file, with little else, can pass the allowance too. The hint says that if the user trusts the repository, Git can store its files over 1 MiB whole and make its other deltas anew (`git -c core.bigFileThreshold=1m repack -a -d -f`), which leaves those files nothing to rebuild ([decision 091](decisions/091-the-work-stop-names-a-way-out-for-long-histories.md)). The allowance rests on data inflated, not on a pack's length, but that doesn't keep holes out: zeros a hole leaves inside an entry's compressed stream (stored blocks, or a Huffman code that spends one bit on a zero) are inflated and count like any other bytes. Each byte inflated buys 500 bytes of rebuilding, roughly 35 to 1,000 times the time inflating it took, so a hostile archive can still make an import slow, though not endless: the import can be stopped at any time, nothing is committed, and running it again reuses what was stored. A second run isn't faster at rebuilding, though: what was converted is known only in memory, so it rebuilds what it meets again and saves only the storing. Since each family of a big file is rebuilt once (below), a hostile pack can no longer buy repeated rebuilding of one chain, only one rebuild per delta, within the allowance. git/git needs 10.5 GiB, 35 bytes for each byte it inflates and at most 47 at any point of its import past the 4 GiB, a margin of about 11; of that, 0.2 GiB is 221,056 entry headers read walking down chains (measured on 2026-11-03).
  - **A big file's delta family is rebuilt once** ([decision 086](decisions/086-rebuilding-gits-deltas-once.md)). Git stores the newest version of a file whole and older ones as deltas built from newer ones, while the import asks for the oldest first, so a request used to walk the whole chain and the next one nearly all of it again: a long history of a file of roughly 80 MiB or more passed the allowance (a 200 MiB file in 50 versions, each changing 1%, needed about 251 GiB of work against about 146 GiB). Now the first time the import needs a file Git stored as a delta that builds at least 1 MiB, it rebuilds that file's whole family in its pack (the object stored whole at the bottom, and every entry built from it, directly or not), each object once, from the bottom up, depth first, storing each file of 1 MiB or more as it is built, and letting smaller ones go once nothing more is built on them ([decision 092](decisions/092-a-family-rebuild-stores-only-files-big-enough-to-cut.md), [093](decisions/093-a-family-rebuild-builds-every-member.md)); later versions are found already stored, and that history needs about 10 GiB of work. Finding a family reads the pack's entry headers once, in pack order, only for a pack where a family is rebuilt, keeping at most 8 bytes an entry. Rebuilding still holds at most two objects whole; an object with more of its family still to come stays in the base cache while it fits, else in a file in `.opalro/tmp` (at most 4 GiB of them), read back when the next one comes, and past that is built again from the bottom, within the allowance. A member whose delta fails or whose result isn't the object its index names is neither stored nor mapped, and stops the import only if a commit needs it. Versions no imported commit names (kept by reflogs, the stash, notes or `refs/original`) are built and stored too, and `tidy` removes them later. A file Git stored whole is streamed once (above).
  - Packs are read from `objects/pack`, each `pack-*.idx` with its `.pack`, which must match it. A file without its partner is a pack Git is still writing or removing, and is skipped, as Git skips it. An index's tables stay in memory: each object's name and offset, and the order of the entries in the pack with a bit for each that has been inflated, 32 to 44 bytes an object. So a repository's packs may list at most 16,777,216 objects in all (git/git has about 0.4 million, Linux about 10 million), and an index past that is refused before its tables are read. At that limit Opalro keeps at most 706 MiB of tables, and loading them peaks at about 832 MiB, under 1 GiB: the table being read grows by doubling, and an index's table of 64-bit offsets is held until its offsets are read. Once its length fits its object count, an index is read a buffer at a time, and its tables grow only as each name passes the check that it comes after the one before, so a planted index of zeros is refused at its second name. `objects/pack` may hold at most 100,000 entries, and Opalro reads at most 4,096 packs, since an object may be looked for in each: Git merges its packs once there are 50 (`gc.autoPackLimit`), so more are refused before any is read, with a hint to merge them with `git repack -a -d`. A pack that lists no objects, which Git never writes, is checked and then never searched, and each object is looked for first in the pack that held the last one found, as Git does. Between reads, at most 16 packs stay open (the ones used last), few enough for any system's limit on open files.
  - A pack or loose object that Git removes or rewrites during the import stops it as a change, not as damage: run it again once Git has finished. A pack Opalro already has open goes on being read as it was.
  - `.git/config` and `.git/config.worktree` may each be at most 1 MiB.
  - `HEAD` and each loose ref may be at most 4 KiB.
  - `.git/packed-refs` may be at most 512 MiB, room for millions of refs.
  - It reads at most 7,600,000 entries of `.git/refs` and `packed-refs` (folders, files and refs): room for every ref decision 033's limits let an import bring in, and a million more it only lists.
  - The ref names and folder paths it keeps while reading refs may take at most 512 MiB. This is separate from the limit on `packed-refs`, which is read whole, so the two limits add up to 1 GiB of memory at the peak of reading refs, before the maps that hold the refs add their own overhead.
  - It never runs Git or Git LFS and never fetches. It ignores replace refs, grafts and Git's speed-up files, and warns when the repository has a grafts file.
  - It refuses, before writing anything and saying what to do: unknown formats or extensions, reftable, refs kept outside `.git`, partial and shallow clones, alternates, sparse checkouts, pack indexes in Git's old version 1 format, a `.git` that is a file, and a `.git` another account owns.
- **Commits become saves exactly** ([decision 032](decisions/032-exact-repeatable-commit-import.md)).
  - Tree, parents (in Git's order), author, committer (as the saver) and message carry over; imported saves get no `line` note, since Git never recorded where a commit was made.
  - Whatever the save's own fields can't rebuild (a signature, a signed merge, extra or unusual header lines) stays in the extra field `git-header`. Import checks that every commit rebuilds to its own Git ID, so a later export can give back the same IDs.
  - A save's change ID comes from its commit (Jujutsu's rule, or the `change-id` header Jujutsu writes), so importing the same repository again, on any computer, gives identical saves.
  - No two imported saves share a change ID ([decision 043](decisions/043-red-team-m2-rulings.md)), so each can be picked by the ID history shows. A header's change ID goes to the first commit in the import's fixed order that has it, unless Jujutsu's rule gives that ID to some commit of the import from its own ID; every other commit with the header takes the ID its own commit ID gives, and a warning counts them. That order is a depth-first walk from the commits the imported refs point to, smallest Git ID first, which goes into each commit's parents smallest Git ID first and puts each commit after its parents. The first pass notes which header IDs some commit's own ID gives, before anything is written.
  - A commit with a message over 1 MiB or a header over 64 KiB stops the import; commits whose trees an old tool wrote in a non-standard form are counted, since export can't recreate their IDs.
  - A commit may have at most 1,024 parents, and an import may add at most 1,000,000 parents beyond each commit's first, all commits together ([decision 043](decisions/043-red-team-m2-rulings.md)). Each save keeps its parents whole, 32 bytes each, so a chain of merges of many parents, a few hundred bytes a merge in Git's pack, would otherwise fill the disk; within the limit they take at most about 35 MB. That bound is for parents only: the rest of a save is kept whole too (next point). Real histories need far fewer: git/git's has 21,699 (counted on 2026-11-03), and Linux's has about 80,000 merges. The first pass counts them as it reads each commit, before anything is written. It keeps each commit as an index into one table of IDs, and a commit's parents, as 4-byte indexes, only while that commit waits on the walk's stack; the second pass reads each commit's parents again.
  - Records are stored whole, not as deltas ([decision 044](decisions/044-red-team-m2-final-rulings.md)): each save's message, each folder's listing and each distinct file, compressed, where Git stores them as deltas on one another. So an import can need far more disk than the Git repository: 2,000 commits sharing one 1 MB message take under 1 MB in Git and about 1.5 GB in Opalro, about 1,500 times (the red team's case). Nothing but the rebuilding allowance bounds it, and that grows with the repository, so a hostile repository can fill a disk. When the disk fills, the import stops cleanly: nothing is committed, and the hint says the `.opalro` folder it began is kept, so that running the import again can finish from what was stored, or it can be deleted. Chunking ends this for file contents, since a big file's versions now share their unchanged chunks, but not for records: a message is part of its save, and a listing is one record. An import has no limit on what it writes; storing records as deltas, a later storage feature, is what would end it ([decision 087](decisions/087-what-an-import-writes-once-files-are-chunked.md)).
- **Branches become lines** ([decision 033](decisions/033-git-branches-to-lines.md)).
  - Your own branches become lines.
  - Each server's branches, as Git last saw them, become server lines (`feature-x@origin`); they move only with another import.
  - Names Opalro's rules refuse are renamed by a fixed rule, which the summary lists: each character Opalro doesn't allow becomes `-`, a name over 255 bytes is shortened, and a clash gets `-2`, `-3` and so on. Names that need no change keep them, as does the first in byte order of names that differ only by letter case, so the suffixes go to renamed names and to the later names of such a group. The same repository always gets the same names.
  - You stand where Git did: on its current branch's line, or at the save of a detached `HEAD`. At a save the summary says so, and that saving there asks for a new line's name, as any save away from a line does (§5.10).
  - The stash, notes, replace refs and other refs aren't imported; the summary lists them. A repository with no commits, or a current branch with none yet, stops the import.
- **Names Opalro can't take as they are** ([decision 035](decisions/035-git-names-bolt-cant-take.md)). Dangerous names are skipped, with everything under them, and the summary lists them: any spelling a system would treat as `.git` (Git's own list, on every system, as Git for Windows applies it: its check for macOS spellings also ends a name at a backslash), `.`, `..`, empty names and names holding `/`. Names over 765 bytes and broken folders (duplicate names, wrong order, unknown modes, contents that don't match their ID, missing objects) stop the import. A snapshot with a path over 4,096 bytes, or of more than 4,096 folder levels or 10,000,000 entries (counting every path), stops it too ([decision 051](decisions/051-names-this-computer-cant-write-and-length-limits.md)), and so does a single Git tree of more than 1,000,000 entries, which is more than an Opalro folder may hold. Commits with skipped entries are counted, since export can't recreate them exactly. Later saves leave out the same `.git` spellings wherever the folder holds them, and say so (§5.2).
- **Submodules become bare links** ([decision 036](decisions/036-submodules-as-bare-links.md)): a project link holding only the commit. `.gitmodules` comes in as an ordinary file and is never read. A later save keeps every link as it is and never looks inside its folder; moving, adding or removing a submodule is done in Git.
- **The first save after an import** ([decision 039](decisions/039-first-save-after-import.md)) stops when files differ from the imported version only by line endings Git converted, offering to have Git write them back or to save them as they are with `opalro save --accept-crlf`. Like every save, it keeps what this computer can't hold exactly as it was (§5.2). Sparse checkouts are refused by the import. Opalro doesn't follow a config's `[include]` or `[includeIf]` sections, so when `.git/config` or `config.worktree` has one, the import warns that it can't tell whether they turn sparse checkout on, and says how to check and turn it off before the first save ([decision 043](decisions/043-red-team-m2-rulings.md)). Uncommitted work in Git becomes part of the next save.
- **Import is one-time for now** ([decision 040](decisions/040-import-once-catch-up-later.md)): a second `opalro import` refuses; catching up with Git's new commits comes later.
- **An import that stops partway** commits nothing and keeps the `.opalro` folder it began, for a later run to finish from what it stored ([decision 041](decisions/041-several-packs-per-command.md)). A second run may get past the stop when Git was busy or a read or write failed, and the hint says so; any other stop comes again until its cause is fixed, and the hint says that instead. Other commands in that folder say an import or start didn't finish there, or that one is still running while it holds the lock. They offer deleting the folder only while it holds nothing (no head and no packs), and the import's own hint offers it only while the import hasn't written its head; otherwise they say to run the command again, which finishes from what is stored. A project whose diary shows saves (the head's entry has a parent or, when the head is gone too, an entry in a pack does) has lost its `format`: commands report it as damaged, and `opalro import` and `opalro start` refuse it alike, so neither writes a new first entry over its saves. `opalro start` refuses an unfinished import once it has stored files, which an empty project would leave unused.
- **Ignore rules carry over by themselves** ([decision 038](decisions/038-gitignore-and-saved-files.md)): Opalro reads `.gitignore` files as well as `.opalroignore`, so an import copies nothing, and files Git tracks despite a rule stay saved. A save that takes a change to such a file says so and names it, since Git would leave the change out unless it was added: a repository can track a placeholder `.env` that its `.gitignore` lists ([decision 043](decisions/043-red-team-m2-rulings.md)). A `.opalroignore` line may take back what a `.gitignore` keeps out, and a repository can track a `.opalroignore` too, so a save also judges each file by the `.gitignore` lines alone, as Git would: a file or link it takes, new or changed, that those lines keep out, itself or a folder it is in, is named in a warning as well. Git's personal lists, the user's own and `.git/info/exclude`, apply too ([decision 047](decisions/047-git-personal-ignore-lists-read.md)), the user's own named in the user's Git settings, read where Git reads them, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` included ([decision 094](decisions/094-red-team-m5-rulings.md)), where `/dev/null`, and `nul` on Windows, names no file ([decision 095](decisions/095-a-git-setting-naming-dev-null-names-no-file.md)) and `GIT_CONFIG_SYSTEM` is first tidied as Git tidies it ([decision 096](decisions/096-git-config-system-is-tidied-as-git-tidies-it.md)), with `~` the home folder Git uses ([decision 097](decisions/097-red-team-m5-session-2-rulings.md)), and a folder that holds a `.git` of its own, such as a worktree, is left out ([decision 046](decisions/046-nested-projects-left-out.md)), so a first save keeps out what Git keeps out.
- **Git LFS files** ([decision 085](decisions/085-importing-git-lfs-files.md), refining [020](decisions/020-lfs-import.md)) come in as ordinary files, identified by their contents.
  - A file (never a link, which Git LFS doesn't convert either) is a Git LFS pointer when Git LFS accepts its blob as one (as `git lfs pointer --check` does: the version line, `oid sha256:` and 64 hex digits, then `size`, in that order, with only extension lines between), and it is not empty and at most 1,024 bytes; where it sits doesn't matter, as for `git lfs fetch --all`. Known limit: where a commit's `.gitattributes` doesn't mark such a blob for Git LFS, Git checks out the pointer text, and Opalro brings in the file it points to.
  - Its contents are read only from `.git/lfs/objects/<oid[0..2]>/<oid[2..4]>/<oid>`, without following a link, a regular file whose length is the pointer's size, streamed into the store as any file is while its SHA-256 is computed; a SHA-256 that isn't the pointer's stops the import, naming the file, the commit and the object, with the hint to run `git lfs fsck <commit>` (which moves the bad copy aside), then `git lfs fetch --all`. A pointer of size 0 is an empty file. Opalro never fetches and never runs Git LFS. Objects kept elsewhere, through `lfs.storage` set to another place (as Git reads it: the user's own Git settings files, then `.git/config`, then `config.worktree` when `extensions.worktreeConfig` is set, then what `GIT_CONFIG_COUNT` gives) or a `.git/lfs` or `.git/lfs/objects` that is a link, stop an import that has a Git LFS file to bring in, saying where: before anything is written when the repository shows a sign of Git LFS, at the first such file otherwise. A repository with none comes in whatever the setting says ([decision 089](decisions/089-git-lfs-objects-kept-elsewhere.md)). Known limit: a repository that keeps pointer text as data, without the objects it names, can't be imported.
  - When the repository shows a sign of Git LFS (a `.git/lfs` folder, or `filter=lfs` on a line of the top `.gitattributes` of `HEAD` that isn't a comment), the first pass walks every folder of every commit the import brings in, each distinct folder once, within the import's limits, reads every blob of at most 1,024 bytes, and checks that each pointer's object is there with the right size. If any is missing, the import stops before `.opalro` is made, listing the first 20 (path, commit, size), how many are missing in all and their total size, and says to run `git lfs fetch --all` and import again. It also says that a Git setting Opalro doesn't read (the system's own settings, or an `[includeIf]` section) may keep Git LFS's files elsewhere, where fetching can't help: `git lfs env` shows where on its `LocalMediaDir` line, and if that isn't `.git/lfs/objects`, the way out is the one for objects kept elsewhere ([decision 094](decisions/094-red-team-m5-rulings.md)). Without a sign, a missing object stops the second pass at the first one, naming it, with nothing committed.
  - A blob that isn't a Git LFS file comes in as it is. Whatever its size, an `lfs_lookalikes` warning names it (the first few, and counts them all) when its first 1,024 bytes (all of a shorter one) look like a pointer (not empty, a first line starting `version https://git-lfs.github.com/spec/v1` or `version https://hawser.github.com/spec/v1`, a line that is `oid sha256:` and 64 hex digits and a line starting `size `, in any order, whatever else they hold), or Git LFS's parser accepts them, as they are or in their CRLF form: each LF not already after a CR turned into CR LF, then cut at 1,024 bytes. Git LFS's smudge filter reads only those bytes, and Git may first turn line ends into CR LF (under `eol=crlf`, or `core.autocrlf=true`, which Git for Windows' installer sets), which pushes bytes out of them. So Git LFS may check such a blob out as the file a pointer there names, whatever its size, though Git LFS never writes such a blob, and the warning says so ([decisions 094](decisions/094-red-team-m5-rulings.md), [097](decisions/097-red-team-m5-session-2-rulings.md) and [098](decisions/098-a-blob-is-also-judged-in-its-crlf-form.md)). The check looks only at those bytes, which the import holds anyway. Known limits: the other way round, a pointer of at most 1,024 bytes padded so that Git's CRLF pushes its size line out of those bytes comes in as its file, where Git LFS checks out its text; and Git's other conversions before the filter, `ident` and a working-tree encoding, aren't modelled. A pointer with extension lines (`ext-`) stops the import, since rebuilding its file needs Git LFS to run a program.
  - The import counts the pointers not in the exact form Git LFS writes, since a later export can rebuild a pointer only in that form, as it counts trees not in Git's standard form, and counts the commits that hold Git LFS files: a save keeps a file's contents, not the fact that it was a pointer, so an export can give back such a commit's Git ID only by turning those files back into pointers (decision 032 is refined so).
  - The first save after an import stops where the folder holds a pointer instead of the file the import brought in (Git LFS wasn't installed, or was told to skip, when the folder was checked out): a file that isn't the imported version, that Git LFS's parser accepts, and whose size line is the imported version's size. It names them and says to run `git lfs checkout`, then save again, or, if Git LFS can't, `opalro discard` with those paths, which puts back the files the import brought in. It comes before the line-ending stop, `--accept-crlf` doesn't skip it, and it looks at the whole folder (the small files the cache doesn't vouch for), even when the save or an amend names paths, so a partial save can't end the check while pointers stand in for files ([decision 090](decisions/090-the-first-save-looks-at-the-whole-folder-for-pointers.md)).
- **Tags come in exactly** ([decision 034](decisions/034-tags-kept-and-shared.md)). An annotated tag keeps its Git bytes, signature included, beside its Opalro message. A tag of something other than a commit (a folder snapshot, a single file) is skipped and listed. The tag list may hold at most 512 MiB; the import writes it once, a tag at a time into a buffer of the size its first pass counted, and checks it as a reader would without keeping what it reads, so it holds the list once ([decision 043](decisions/043-red-team-m2-rulings.md)).

## 6. Risks and watch-outs

Raised at kickoff. Each is either answered by a topic or tracked here until it is.

1. **Scope and motivation.** The brief describes several products; the realistic failure mode is losing steam long before Opalro is usable. *Response:* a usable v0.1 early (roadmap in §1), then grow toward the full goals; design later layers only as far as the engine must respect them.
2. **Adoption.** Every independent engine of the Git era (Mercurial, Bazaar, Fossil, Darcs, Pijul) stayed niche or faded against Git and GitHub; the newcomers gaining traction (jj, Sapling) work with Git repositories. Opalro is designed as if it would be marketed, so this matters. *Response:* a deliberate first audience (decision 001); Git import in v0.1 and export before 1.0 (decision 002).
3. **Precise claims.** Git is heavily optimized for code repositories; big files are where Opalro can clearly win. Git LFS does have locking (`git lfs lock`), and Git has partial clone (`--filter=blob:none`), which skips old file contents. The real problem is that both are add-ons: awkward, easy to bypass, unevenly supported by hosts.
4. **Dedup depends on file format.** Chunking saves a lot when edits leave most bytes untouched (WAV, uncompressed source assets, appended datasets) and little on already-compressed formats (PNG, JPEG, MP4, ZIP-based files) or a retrained model where every weight changed. *Response:* measure on a real-asset corpus before claiming savings (starting parameters in decision 009; measurement in topic 18). Milestone 5's benchmarks measure it on Godot's demo projects and on generated assets, and publish what they find ([decision 088](decisions/088-benchmarks-and-the-speed-gates.md)). Measured on 2026-11-09 ([benchmarks.md](benchmarks.md) §2): ten versions of a 1 GiB file, each with 1 MiB overwritten and 4 KiB inserted, take 1,041 MiB in Opalro against 10 GiB in Git and Git LFS; Godot's demo projects take 3% more in Opalro than in Git (226.7 MiB against 219.3 MiB), most likely since Opalro compresses each chunk of a big file on its own.
5. **Shared vs. local settings.** *Answered by decision 008:* project rules in `opalro.toml` + `.opalroignore`, declarative only; personal settings are never shared and can never change project rules.
6. **Undo has edges.** *Answered by decisions 003 and 010, and built by decisions 070 to 077 (milestone 4):* what `discard` and `shelf` throw away is kept as a save, so undo puts back every file, deleted ones included; each step records what the folder held and what it wrote at exactly the paths it wrote, so undo touches nothing else; undo and redo never overwrite unsaved work, they stop instead, and `--shelve` sets it aside within the same step; shelves are never dropped by undo; undo restores only your own repository and offers the opposite action for things others received (v0.3); a 30-day undo window, which `tidy` respects. Edges left: `discard` and `shelf` leave alone a link they couldn't write back as a link (decision 071); amending a save another line reaches only through a second parent shares its change ID until v0.2 shows divergence (decision 074); the size budget for safety copies waits.
7. **Accidental huge or secret saves.** No staging + "save everything" + big-file support means one save can swallow a 30 GB render folder or a `.env` file. *Response:* new files are tracked automatically and unusually large saves ask first (decision 003); preset ignore rules (topic 16); secret warnings (topic 18); a save that takes a change to a file an ignore rule matches says so (decision 043), and so does one that takes a file `.gitignore` keeps out but `.opalroignore` takes back; folders that hold a repository or project of their own are left out (decision 046), and Git's personal ignore lists apply (decision 047). The owner's import check (2026-11-04) showed the cost of each gap: 44 Git worktrees, about 11 GB, nearly went into a first save. A save that adds unusually much asks first since milestone 3 (decision 056), and from milestone 6 presets set the numbers and keep `.env` files and engine caches out ([decision 113](decisions/113-presets-what-each-writes-and-how-start-picks-one.md)); the warning about files that look like secrets stays for after v0.1 ([decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)).
8. **The working-copy model drives undo, conflicts and shelving.** *Answered by decision 003:* a separate folder with automatic safety copies.
9. **File-model basics** (line endings, executable bit, symlinks, empty folders, path encoding, case and Unicode collisions, nested projects). *Answered by decision 004.*
10. **Windows must be first-class.** Antivirus and editors hold files open, so temp-file-plus-rename fails intermittently and needs retries. Also: reserved names (`CON`, `NUL`, `AUX`, `COM1`…), trailing dots and spaces, 8.3 short names, alternate data streams, long paths, case-insensitivity, symlinks that need special permission. *Name rules and write-out safety: decision 004. Files held open and retries: decision 011.*
11. **Big-file identity.** *Answered by decision 005:* files are identified by their contents, never by their chunk list.
12. **Hashed objects need a hand-specified byte format.** *Answered by decision 005:* a hand-written format with exactly one valid encoding per object; serde only for data that is never fingerprinted.
13. **Renames are guessed** when changes come from comparing snapshots. *Answered by decision 006:* saves carry move notes for moves Opalro is certain about; how merges use them follows in topic 12.
14. **Change IDs.** *Answered by decision 006:* 128 random bits, shown in the letters k–z, with divergence shown explicitly.
15. **Build order.** Answered by decision 001: test infrastructure is built with the object store, a minimal Git importer follows saves and history, and chunked big files come before lines and combine. Locking waits for the server (v0.3).
16. **A data-integrity tool written mostly by an AI while the owner learns Rust.** Subtle bugs can look fine in review. *Answered by decision 022:* the rules are approved and copied into CLAUDE.md, with `unsafe` allowed only in a tiny platform crate for operating-system calls. *Decision 024* adds an attacker's view: a red-team session from an isolated sandbox at the end of every milestone.
17. **Too many open packs.** Every save adds a pack, a big import adds several at once ([decision 041](decisions/041-several-packs-per-command.md)), and the store keeps every pack open, so a long-lived project will hit the operating system's open-file limit. *Answered by [decision 057](decisions/057-pack-index-on-disk-and-merging.md):* fixed-width pack indexes searched on disk, packs opened only when needed, and small packs merged automatically (milestone 3).
18. **Our own Git reader meets hostile repositories first.** Readers of Git's formats keep having crash and memory bugs on crafted packs (gitoxide, go-git, libgit2 and dulwich all published some in 2026). *Response:* decision 031's bounds; fuzzing; malicious-repository cases drawn from Git's published vulnerabilities (reviewed 2026-11-02); differential tests against Git; milestone 2's red-team session.
19. **Code that follows another project's code.** Opalro ships closed, and code that follows Git's code (GPL version 2) can't ship in a closed program; an AI that knows Git's source can reproduce it without meaning to. *Answered by [decision 131](decisions/131-code-that-follows-another-projects-is-rewritten-clean.md):* an audit of every module, test and data file ([the code audit](releases/v0.1.0-code-audit.md)); clean-room rewrites, each compared with the old code from the outside and reviewed against the other project's source; copied test material replaced by comparisons against the real programs.
20. **A closed product built from open-source code.** Each license of the code inside Opalro asks something of whoever passes the program on, and one that asks too much (the GPL) would force Opalro's own source open. *Answered by decisions [140](decisions/140-bolt-is-closed-source.md) and [143](decisions/143-the-notices-cover-what-is-built-in.md):* cargo-deny allows only licenses a closed product can meet, and MPL-2.0 for one crate alone; the notices cover everything built in, Rust's standard library included. Code written from another project's code is the engine session's audit.
21. **Trust in a closed tool that holds people's work.** Its users can't read the code to see what it does with their projects. *Answered by [decision 142](decisions/142-bolt-sends-nothing-and-each-build-proves-it.md):* Opalro sends nothing, and each release program is checked for networking and for starting other programs; the user agreement ([decision 141](decisions/141-the-user-agreement.md)) says so.

## 8. Prior art

Learn from these; don't copy them.

| System | What to learn |
|---|---|
| Git | Snapshots + packfiles with deltas; content addressing; the index; weak with big files |
| Mercurial | Revlog: deltas with periodic full snapshots; the `requires` file for format features |
| Jujutsu (jj) | Change IDs, operation log, first-class conflicts, working copy as a commit |
| Pijul | Patch theory: changes, not snapshots, as the primitive |
| Sapling (Meta) | Scalability; the Mononoke server; lazily fetched history |
| Perforce, Unity Version Control | Big files, locking, typemaps (per-file storage rules) |
| Diversion | Cloud VCS for games; syncs with Git and Perforce |

| Anchorpoint | Git + LFS made friendly for artists, auto-configured per engine |
| Hugging Face Xet | Content-defined chunking at scale for ML files, replacing Git LFS on the Hub |
| restic, borg | Content-defined chunking for backups (FastCDC and relatives) |
| Git partial clone, sparse checkout, Scalar | Git's own answer to very large repositories |

## 9. Glossary

Working names; command names can still change (topic 17).

- **Repository**: the history database, kept in `.opalro/`.
- **Working folder**: the files you actually edit.
- **Save**: one recorded version of the whole project (Git: commit). A photo of every file at one moment.
- **Change ID**: a stable name for a save that survives edits and rewrites, written in the letters k–z (`kxqmz`). Editing a save changes its fingerprint, not its change ID.
- **Conflict**: two lines of work changed the same thing differently. Opalro keeps every version in the save so you can fix it later.
- **Divergent**: two saves that share one change ID, usually because two people edited the same save; Opalro shows both until you keep one.
- **Move note**: a record inside a save that a file moved, kept only when Opalro is certain.
- **Pack**: a file in `.opalro/store/` holding many pieces of data plus an index, written in one go so a crash can't leave half of it.
- **Undo window**: how far back `tidy` keeps what undo needs; 30 days by default.
- **Step**: one command in the diary that undo can take back and redo bring back again.
- **Cache**: remembered facts that speed Opalro up, like file sizes and times; always safe to delete.
- **Pinning**: marking saves or folders so they stay available offline.
- **Lock**: a "someone's working on this" claim on a file that can't be merged; while you hold it, nobody else can send changes to that file.
- **Remote**: another copy you sync with: a server, or a plain folder such as a USB drive.
- **Preset**: a starter set of project rules for one kind of project (Code, Game…), written into `opalro.toml` and `.opalroignore` by `opalro start`.
- **Hash**: a fingerprint of data. Change one byte and the fingerprint changes (BLAKE3).
- **Blob**: the contents of one file, stored under its hash.
- **Tree**: a folder listing: names pointing to blobs or to other trees.
- **Chunk**: a piece of a big file. Identical pieces are stored once.
- **Chunk list**: the list of pieces a big file was cut into. Stored separately, so the file's ID never depends on it.
- **Line**: a named line of work (Git: branch); a movable name that points at the latest save made on it.
- **Tag**: a fixed name for an important save, like `v1.0`; it never moves.
- **Operation log**: a diary of every command that changed the repository; it is what makes undo possible.
- **Project rules**: settings the whole team shares, kept in `opalro.toml` and `.opalroignore` and saved in history like normal files.
- **Personal settings**: your own preferences (name, editor, merge tools); never shared, and they can't change project rules.
- **Safety copy**: unsaved work that Opalro keeps automatically before a command throws it away, as a hidden save of its own (a kept save), so undo can bring it back.
- **Shelf**: a place to set unsaved changes aside and bring them back later (Git: stash).
- **Symlink**: a file that points to another file or folder, like a shortcut.
