# Opalro Security Plan — Draft

> **Status:** drafted in the design phase (2026-10-31), updated after milestone 1's two red-team sessions (2026-11-02) and for milestone 2's Git import (2026-11-03), with the owner's check of a project inside OneDrive (2026-11-04), and for milestone 3's working folder: folder handles, write-out, the caches and the journal (2026-11-06), and for milestone 4's undo, shelves, `tidy`, `save --amend` and crash recovery (2026-11-07), and after its two red-team sessions (2026-11-08), and for milestone 5's chunked files and Git LFS import as decided (2026-11-08) and as built (2026-11-09), and after its two red-team sessions, whose findings are fixed, and its whole-branch review (2026-11-09), and for milestone 6's presets, `opalro.toml`, `opalro setup`, `opalro verify`, the terminal design, Git's words and the release workflow (2026-11-10), and for milestone 7's lines, tags and the walk through every parent, and after its two red-team sessions (2026-11-14). Every defense gets a test in [testing.md](testing.md) when it is built. The Windows naming rules were checked against Microsoft's documentation on 2026-11-01 (see §6 and decision 004).

**In plain words.** Opalro assumes that any project you copy, any repository you import and any server you talk to might be trying to hurt you: overwrite files outside the project, run code on your computer, fill your disk, or trick you with tampered history. Opalro's defenses are simple rules, each applied in one place, and every rule has a test.

## 1. What we protect

1. **Your files and history:** never lost, never silently corrupted.
2. **Your computer:** nothing in a project can make Opalro run a program or write outside the project.
3. **Your secrets:** login tokens and passwords never end up in files, logs or history by accident.
4. **Private projects** (from v0.3): nobody reads a project they have no access to.
5. **Availability:** malicious input can make a command fail, but not hang it, crash it, or exhaust memory or disk without limit.

## 2. Who might attack

| Attacker | Example |
|---|---|
| A malicious project | A repository someone shares, or a Git repository you import, crafted to exploit Opalro |
| A malicious or compromised server | Sends tampered saves, oversized data or fake lines |
| A network attacker | Tries to read or change traffic |
| A teammate, within their permissions (v0.3) | Abuses locks, or sends huge files |
| Another customer of a hosting service (later) | Tries to read other projects' data through shared storage |

Out of scope: malware already running as you on your own computer.

## 3. Trust boundaries

- **Untrusted:** everything inside a project (file names, `opalro.toml`, `.opalroignore`); everything in `.opalro/store` and `.opalro/state`, since files on disk can be tampered with; everything received from a server; every imported Git repository.
- **Trusted:** your personal settings and the Opalro program itself.

## 5. Engineering rules (approved, decision 022)

- The engine forbids `unsafe` code (`#![forbid(unsafe_code)]`). Memory-mapping files is avoided in v0.1: it needs `unsafe`, and a file changed underneath can crash the process.
- The one exception is a tiny, separate platform crate, which may use `unsafe` for operating-system calls only (for example Windows' Restart Manager, hiding `.opalro/`, file IDs). The owner reviews it line by line.
- No panics in library code: errors are returned, and clippy's `unwrap_used`, `expect_used` and `panic` lints are denied outside tests.
- One place per rule: name validation, path building and write-out each live in a single module that everything else must use.
- The owner reviews anything that touches disk or network before it is merged.
- Spec before code for anything on disk, and test vectors for every format.

## 6. Security tests

See [testing.md](testing.md) §3: fuzz targets for the decoders and parsers listed there, a malicious-repository corpus with at least one case per threat above, Windows-specific tests, and crash tests.

**Hostile Git repositories** (the review of Git's published vulnerabilities, 2026-11-02): `crates/opal-vcs/tests/corpus_git.rs` holds 25 tests, one of them only on Windows, for 22 of the review's 24 kinds of case. The unusual commits a save keeps exactly are in `import_vs_git.rs`: `Craft` could write them too, but there the test also compares each with Git. A `.git` another account owns is tested in `git/mod.rs`, the only place its owner can be stubbed. A SHA-1 collision can't be built as a Git object, so `git/id.rs` feeds SHAttered's blocks to the hasher. Six fuzz targets cover the Git reader: loose objects, packs and their indexes, deltas, commits, trees and tags, refs, and config.

**Hostile saves written out** (T1 to T5, and the review's write-out cases): `crates/opal-vcs/tests/corpus_writeout.rs` plants each save, or a switch's journal, as a hostile `.opalro` could hold it, runs `opalro goto` onto it, and checks the exit code, what was written, the warnings and messages, and that nothing reached a folder beside the project or went into `.git` or `.opalro`. Its cases: `.git` spellings, `.gitmodules`' plain and hashed short names and, on Windows, the real hashed short name of `.git`; `.opalro` spellings in a save (its listing is refused) and in a journal (the journal is refused); `\`, drive letters and device names, `COM¹` included; links named like folders with files below them (CVE-2021-21300, CVE-2024-32002); links leading out (absolute, a drive letter, `\\host` and `//host`, `..` past the top), written as placeholders; a hard link at each path a switch writes, to a file outside the project holding what the save expects, which must stay as it was (Git LFS's CVE-2025-26625; one of the files is stored as chunks); modes 0644 and 0755 under a umask of 000 and of 077 (Unix; a file that was 0666 before, and the executable bit flipped on a file already there, are in `crates/opal-vcs-core/src/writeout/tests.rs`, `modes_are_exactly_0644_and_0755`); a folder a stopped switch made, swapped for a link before the switch finishes, with a file stored as chunks among those below it (`a_link_above_a_written_file_is_never_followed`); names too long for the system, paths over 4,096 bytes and a save 4,096 folders deep. - ~~Windows: whether synced folders show their placeholders to Opalro.~~ Checked 2026-11-04 in a OneDrive folder with Files On-Demand ([milestones.md](milestones.md)). Opalro refuses every reparse point inside `.opalro/`, and a save refuses a file or folder that is a reparse point but not a link, as a special file it can't read yet (a folder is never walked into; some sync and virtualisation tools make such folders, rarely). Windows hides OneDrive's placeholders from programs like Opalro: they run in its "disguise placeholders" mode by default (a small Rust program reported `PHCM_DISGUISE_PLACEHOLDER`), so Opalro sees ordinary files, even in a `.opalro` set to "Free up space", and reading an online-only file downloads it. PowerShell runs in the "expose" mode, so it shows them as reparse points. Other sync clients built on the same Windows feature (the Cloud Files API) should behave the same; untested. Two things follow. A save used to read every file, so in a folder of online-only files it downloaded them all; since milestone 3 the file-state cache leaves unchanged files unread (decision 053), and Opalro can still see which files are online-only (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`). Milestone 6 packages Opalro as plain archives, with no MSIX, so the mode doesn't change ([decision 119](decisions/119-packaging-v0.1.md)); any package format that changes it brings the check back.
