## Summary

The import's move notes held: in 270 random histories, every note was true of its save and its first parent, and was exactly what a save's own rule gives, and a second import gave the same saves byte for byte. Short names, empty folders in `status`, and `resolve --keep` held too.

The comparison's cost did not hold. Its allowance counts the bytes a Git tree holds, not what reading the tree takes. An 8 MB repository can make each commit cost 12 seconds of reading in a release build, while the allowance counts 58 bytes, so the import never stops. That is RT25-1, Medium. One Low finding: a switch that puts an empty folder where a file was removes the file and says no file needed changing.

## Findings

### RT25-1 (Medium): the comparison's allowance counts what a tree holds, not what reading it costs

Threat: T59 and T7 (security.md says a history "built cheap to convert and costly to compare" stops the import).

What happens: to find a commit's renames, the import reads both commits' Git trees again (`Converter::kept` in `convert.rs`). It counts `object.data.len()`, the bytes the tree holds, against an allowance of at least 1 GiB. But a tree stored whole is inflated from the start every time it is read. Nothing caches it (`build` in `odb.rs` returns a whole entry "read, not built"). `Inflater::read_all` caps what the input may give, but never how much input it takes to give it. So a tree of 29 bytes can carry megabytes of empty deflate blocks, which Git and Opalro both read as nothing. Each comparison inflates them all again, and the allowance counts 29 bytes.

The repository I built, `padpack.py`, holds two one-file top trees, each stored whole after 4 MB of empty fixed-Huffman blocks. Its commits switch between the two trees. The pack is 8 MB whatever the number of commits. Release builds, the same repository:

| Commits | Milestone 11 | v0.2 |
|---|---|---|
| 2 | 42.8 s | 30.0 s |
| 10 | 141.6 s | not run |
| 20 | 261.1 s | 29.8 s |
| 20, no padding | 0.2 s | not run |

Each commit adds about 12 seconds of inflating to milestone 11 and nothing to v0.2. At that rate, 1,000 commits take about 3.3 hours and 10,000 about 33 hours. The allowance is never reached: 1 GiB at 58 bytes a commit is 18 million commits. Git reads both padded trees in 0.03 s.

Padding is the strongest way in, but any cost that comes per read, not per byte, slips past the count. A file 2,000 folders deep whose contents flip in every commit makes each comparison read 4,000 one-entry trees: 200 commits took 6.5 s against v0.2's 0.2 s. The same trees stored loose beside 4,095 packs make every read search all 4,096 packs first (`Repo::find`): 50 commits took 11.4 s against 0.6 s. That is about 35 minutes before the 1 GiB allowance stops it. This is more than Task 6's Minor 4 (the path built for each entry): those costs are microseconds, these are seconds.

How it is proved: `redteam25_platforms.rs`, `an_import_reads_no_more_than_its_allowance_past_the_repository`. It writes two trees stored loose, each with 32 MiB of empty stored blocks (fast to inflate even in a debug build), and 60 commits that switch between them. It runs `opalro import` and watches the bytes it reads (`rchar` in `/proc/<pid>/io`). An import should read the repository a few times, plus its allowance at most: the test allows four times the repository plus 2 GiB, 2,304 MiB. Today it fails: `the import of a 64 MiB repository of 60 commits had read 2305 MiB, past the 2304 MiB it should need, and was still going`. With 3 commits, the same test passes, having read 287 MiB (`rt25_sanity.rs.txt`).

What it costs a person: an import of a small repository from a stranger keeps running for hours or days, with no stop and no hint why. Nothing is lost: stopping it by hand leaves nothing committed. But the allowance was added so that this exact shape stops, and it doesn't.

What I would do: don't inflate Git's trees again to compare them. The converter already keeps each tree's listing (`Converter::trees`); comparing those listings, or caching the parsed entries of the trees compared, inflates each tree once. Counting the real cost of each read is the other way: the compressed bytes taken (`Inflater::taken`, or the loose file's length), plus a fixed amount per read, as `ENTRY_HEADER_WORK` does for delta chains. Counting compressed bytes alone is not enough, though: empty fixed blocks inflate at about 0.65 MB/s in release (suspicion S1), so a full 1 GiB of them would still take about 25 minutes before the stop.

### RT25-2 (Low): a switch that puts an empty folder where a file was says no file needed changing

Threat: new. Near §4's "a command that says it changes nothing changes something", like RT24-1. Not new to milestone 11, but it is in the switch's folder-making that decision 196 changed.

What happens: `main` holds the file `p`; `side` holds `p` as an empty folder. `opalro goto side` removes the file and makes the folder, then prints `No file needed changing.`, and `--json` gives `"removed": 0`. `redo` says the same. The cause: `make_folder` (`writeout.rs`) removes the file the plan expected, then returns `Outcome::Made`, and `step` counts nothing for that. The other way round, from `side` to `main`, says `1 file written.` and leaves out the empty folder it removed, though `Applied::removed` says folders count.

How it is proved: `redteam25.rs`, `a_switch_that_puts_a_folder_in_a_files_place_counts_the_file_it_removes`. It fails today with `the file p was removed, but goto said: Switched to line side at save … No file needed changing. and --json gave removed: 0`.

What it costs a person: nothing is lost, since the file is in `main`'s save. But someone told that no file changed doesn't look for the file that left, and a script reading `removed` is told nothing was removed.

What I would do: count an entry the switch removes to put another in its place. That means a "removed, then made" outcome in `make_folder`, counted as removed, and the same in `put` for the folder it removes before writing a file.

## Suspicions without proof (not counted)

- **S1: Opalro's inflater is very slow on empty fixed-Huffman blocks.** It spends about 2 µs on each one in release, about 0.65 MB/s, where Git's zlib reads the same tree about 400 times faster. Even v0.2 takes 30 s to import the 8 MB padded repository, and by the same rate a 1 GB pack of such blocks would take about 25 minutes. That is bounded by the repository's size, so I count it only as what makes RT25-1 so costly. No test proves it apart from a clock.
- **S2: the comparison may push an honest repository past the delta allowance.** Its re-reads of trees built from deltas add delta work: 370 MB, or 2.8 %, on git/git (benchmarks.md §16). So a repository that imported in v0.2 within a few percent of the delta allowance could now stop with `TooMuchWork`. Not built.

## What was tried and held

**The import's notes** (`rt25_explore.rs.txt`, `explore.out.txt`)
- 270 random histories made by `git fast-import`: 150 with up to 4 changes a commit and 120 with up to 14. That is 8,100 saves and 1,324 notes.
  - Files were added, edited, removed, copied and renamed, and folders moved whole, on `main` and `side`, with merges both ways, so the first parent is either line.
  - The names included letter-case twins (`a`/`A`, `x.txt`/`X.TXT`, `d`/`D`), `é` composed and decomposed, `.git`, `.GIT`, `git~1` and `.opalro` below the top (names the import leaves out), a space, and a right-to-left override.
  - The modes were files, executables, links and submodules, with empty files and contents held at two places.
  - For every save, each note was true of it and its first parent, by `moves::true_of`'s rule written again. The notes were exactly what the save's own rule gives on the stored listings. And a second import of a copy gave the same saves for every line.
- Git LFS: a pointer renamed, a pointer swapped for the bytes it stands for, and an LF pointer swapped for a CRLF one to the same object. Each was noted by what it holds (`a.bin → b.bin`, `c.bin → d.bin`, `e.txt → f.txt`), all true, and a second import was identical.
- By the code: `parse_tree` refuses one name twice even when the two aren't neighbours (`a`, `a.b`, then `a/`, by a binary search), so no path reaches the pairing twice.
- The pairing's bounds can't depend on the walk's order, so this puts the known item to rest. `moves_by` sums the bytes of every file that left, and of every arrival whose contents left once. Both sums are the same in any order, and past either bound the answer is no notes. One repository can't be imported two ways.

**`who` and `combine` on imported renames** (`combine1.sh`)
- `main`'s imported rename `x.txt → y.txt` carried `side`'s edit into `y.txt` at the combine. `side`'s rename `z.txt → w.txt` carried `main`'s edit into `w.txt`, and `who w.txt` named `main`'s commit for that line.
- A chain `a → b → a` brought `who a.txt` back to the commit that added it.
- A rename with a new file put back at the old name gives no note, as `git blame` finds no rename there.
- `who y.txt` gave the edit made under the old name on `side` to the combine. That is T56's known limit.

**Short names** (`short1.sh`)
- One to three letters of a save's change ID were refused with the four-letter hint in `show`, `goto`, `who --save`, `history` and `combine`. Four letters reached the save.
- A line named `tkv`, the start of a save's ID, reached the line; once the line was deleted, `tkv` matched nothing. A tag `tk` behaved the same.
- `undo --to tkv` was refused, since it takes hex only.
- A name with an escape code came back escaped. The hint never holds project text.

**Folders and `status`** (`folders1.sh`, `status1.sh`)
- RT24-1's proof passes.
- After a combine that followed `main`'s move of `d`, so made no `d`: `mkdir d`, then `goto`, `undo`, `redo` and `undo` again. `status` listed the empty `d` as added every time it was asked, and nothing else changed.
- `resolve --keep mine` with the person's file in the folder left the file, and `status` showed it.
- With the folder replaced by a link to a folder outside, `resolve --keep` left the outside folder untouched, and the next `goto` refused, the link being in its way.
- `status` escaped empty folders named with an escape code, a right-to-left override, a newline and a tab, both in its rows and in `--json`.
- A folder holding only ignored files, only an ignored folder, or only a FIFO was listed as added, and the save recorded it: `status` was clean after.
- Folders holding a `.git` or `.opalro` of their own were left out by both `status` and `save`. Folders that can't be read stopped both alike.

## What was not reached

- The journal of a finished switch, made hostile (item 7), got a reading of `journal.rs` and of the crash tests in `recovery.rs`, and nothing more: no journal was planted.
- Imported case-only and Unicode-composition renames on Windows and macOS had no platform tests.
- The cost of the path built for each entry (Task 6's Minor 4) wasn't timed apart from the deep chain.
