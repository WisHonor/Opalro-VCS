Code attacked: a copy of `milestone-10` (version 0.2.0). Built with `--all-features` in the no-network sandbox (4 GB, 4 CPUs, user 1000, not root), debug build throughout. About ninety minutes of work, in two parts (the session was stopped once by a usage limit and resumed; the copy did not change in between). Most of the time went into reading the code against the attack-surface notes; the experiments are listed below.

Proof tests: none. No finding was proved, so neither `crates/opal-vcs/tests/redteam23.rs` nor `redteam23_platforms.rs` was written.

## Suspicions without proof (not counted)

- **A planted history can make `who` compare far more than the 256 remembered pairs allow for.** By the code (`who.rs`, the turn loop), the turns are bounded by lines × depth, because each line follows one fixed route. One comparison per parent per turn is made again once its pair is dropped. A merge with 1,024 parents, each holding another version of a 10,000-line file, over a second level of the same shape, would by my count need about a million comparisons, which is hours. I did not build it: the planted store would be about 100 MB or more, and ruling R5 / please-confirm 14 already accept "a history planted to keep `who` busy". I did not measure whether this is worse than what was ruled.
- **`opalro who` in a project whose `.opalro` cannot be written says only `error: Permission denied (os error 13)`**, with no path and no hint, as text and as `--json` (`rt23_read_only`). This is the known point "who cannot run on a project that cannot be written at all". It fails cleanly: exit 1, and nothing changed (checked byte for byte after the permissions were put back). I note it because the message does not say what could not be written or why `who`, a command that only reads, needs to write. I did not check whether other commands word the same failure better.
- **On a drive that ignores case, a save made elsewhere can hold both `a.txt` and `A.txt`.** `who A.TXT` then picks one of the two spellings through `entry_as_typed`, while the folder holds whichever one the system wrote. The saves it names hold the lines at the path it reports, so the answer is consistent, but it may describe the history of the other file. This would need a Windows or macOS run; I wrote no platform test.

## What was tried and held

**`who` changes nothing**
- A `goto` stopped at each of its 16 fault points (`OPALRO_FAULT_AT=1…16`, a project with two lines and a folder of five files), then `who a.txt`, `who a.txt --json`, `who a.txt --save main` and `blame d/f1.txt`. In every state, every path and its bytes under the folder and under `.opalro` were the same before and after (`rt23_stopped_goto`).
- A read-only `.opalro` (every folder 0555, as user 1000): four forms of `who` gave exit 1 and changed nothing (`rt23_read_only`).
- I read every path `who_command` takes for a write. `with_users_key` makes the user's key in the settings folder, not in the project. `git_words::teach` writes `git-words` in the settings folder. `Repository::open_untouched` makes `.opalro/tmp` and `.opalro/cache` only when they are missing, which `docs/terminal.md` says. `Store::open_in` only lists packs. `LineIds::read` and `resolve` store through `storing_key`, which `store_no_caches` turns off. I found no fourth write.

**A line named for a save that never held it**
- A model on the command line: 6 random histories of 24 steps on two lines, with saves, gotos and combines (5 of them with a conflict fixed by `resolve --keep mine`). The lines were drawn from 8 tokens that repeat and mix `\n`, `\r\n`, an empty line and a last line without an ending. `who --json` was checked in the folder and with `--save` at four tips, once with the normal deadline and once with `OPALRO_DIFF_DEADLINE_MS=0`. For each of the 294 lines checked, the named save holds that line (up to its ending) at the named path (`rt23_model_lines_held`).
- By the code: a line moves to a parent only through an `Equal` stretch of Myers on the real bytes, or when the two content IDs are the same. Past the deadline, `similar` turns only the unmatched middle into deletes and inserts, so a coarse answer can stop early but never at a save that lacks the line. A listing whose size claim is false can only make a comparison come back empty, which stops the line at a save that does hold it. A move is followed only where `true_of` finds the same content ID at `from` in the first parent.
- `line_count` and `lines_of` agree on every shape (`\n` count plus a last line without `\n`).

**Hangs, crashes, memory**
- A named pipe at a new path and at a saved path: `who` refused it at once ("isn't a file in your folder"): the read opens with `O_NONBLOCK` and checks for a regular file (`rt23_fifo`).
- A file of 1,000,000 short lines, through 4 saves of 1,000 changed lines each: `who --json` took 5.3 s and peaked at 130 MiB of resident memory in a debug build (`rt23_million_lines_memory`). This puts a number on the review's estimate of 100 to 160 MiB.
- The `who` walk, `ancestry::holder`, `only_in` and `through_every_parent` use a heap or a stack, so nothing recurses on the depth of the history.

**The amend check (`shown_elsewhere`, `moved_since_made`, `ancestry::holder`)**
- I reasoned through renaming a line, deleting and making it again, `undo`/`redo`, a forward by `combine`, a new line started at the save, tags and server lines. Each one changes the holder's position against the note's diary state, so the check asks about it. The fast path is wrong only when, at the note's diary step, a holder other than the line already held the save. That needs the same save made twice in one millisecond, which the code already names in a comment. Opalro has no setting that fixes the clock, so I could not make it happen.
- `holder` with clocks that lie (a parent dated after its child): the walk marks a node again when it gains a mark, and the `from` map is filled when the child is spread, so the search for the save still ends there.
- `resolve`'s choice between replacing and a new save runs `shown_elsewhere` under the change lock, on the state read under that lock.

**The switch and the file cache handed on**
- By the code: `store_giving_body` gives either the body it read (only when every entry was kept, none was added and none turns racy) or the body it just wrote. With no key, or when a handle stores no caches, it gives `None` and the switch loads from disk. The entries it hands on and their racy marks are what a load of the file would decode. I did not find a case where the in-process body trusts a file that a reload would not.

**Not reached in the time:** `combine` and `resolve` at the same time; a conflict below a folder the other line moved; three common starting points in every order of their IDs; the hoisted lookups of the folder walk on a drive that ignores case; a planted `last-made` copied from another project of the same user; the package pages beyond reading the version (0.2.0 in `Cargo.toml`) and the `who` and amend lines of `docs/releases/v0.2.0.md`.
