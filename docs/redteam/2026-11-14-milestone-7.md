## Findings

- **RT17-1 Medium (a server line's name means one save to `goto` and another to `show`, `changes --save` and `tag --save`; new, near T21; `history.rs` `resolve`, `lines.rs` `resolve_target`).**
  - **What.** Decision 159 says the order wherever a save is asked for is: a line, a server line, a tag, a change ID, a fingerprint. Only `goto` follows it (`resolve_target`). `show`, `changes --save` and `tag --save` call `resolve`, which never looks at server lines: `opalro show main@origin` with no tag of that name says `No save, line or ID matches "main@origin"`. Git allows a tag named `main@origin`, and the import keeps it. With a server line `main@origin` at commit "one" and that tag at commit "two", `opalro show main@origin` and `opalro changes --save main@origin` show "two", and `opalro goto main@origin` goes to "one". Nothing says that the name means two things.
  - **Who is hit.** Someone who imports a Git repository whose author made such a tag: what they look at with `show` is not where `goto` takes them, and `tag v2 --save main@origin` tags the other save.
  - **Proof.** `a_server_lines_name_means_the_same_save_in_goto_and_show`: `show main@origin` gave save 568b73d1…, the server line is at 04ca83e5….
  - **What I would do.** One resolver for all four: take server lines in `resolve` too (or `show`, `changes` and `tag --save` call `resolve_target`), and treat a tag named like a server line as RT17-2 says.

- **RT17-2 Medium (a name that is both a line and a tag goes to the line, silently; new, near T21; `history.rs` `resolve`).**
  - **What.** Git allows a branch and a tag with one name; a release branch and tag both named `v1` are common. The import keeps both. `opalro goto v1`, `show v1` and `tag x --save v1` take the line, with no warning, while `opalro tag` lists `v1` at the other save. Git does the opposite: `git rev-parse v1` prints `warning: refname 'v1' is ambiguous.` and takes the tag. Decision 068 refuses a line name that is also the start of a save's ID, listing both, so that "neither passes for the other"; a line and a tag of one name get no such care. New names can't collide (`line new` and `tag` refuse each other's exact names), so only imported ones and planted ones do.
  - **Proof.** `a_name_that_is_both_a_line_and_a_tag_is_not_taken_silently_for_the_line`: branch `v1` at "two", tag `v1` at "one"; `show v1 --json` gave "two", exit 0, `"warnings":[]`. The test passes if Opalro refuses, warns, or takes the tag.
  - **What I would do.** Refuse as decision 068 does (`LineOrSave` listing the tag), with a hint that names the tag's save by its ID; or at least warn. Whether the line or the tag should win is the owner's call.

- **RT17-3 Low (one tag at a save the store lacks stops `line delete`, and the error doesn't say which tag; T9, T26; `lines.rs` `delete_line`, `ancestry.rs`).**
  - **What.** `line delete` hands the walk every tag's save. A tag (or server line) naming a save that isn't in the store, or naming something that isn't a save, makes every `line delete` whose line has saves of its own stop, `--yes` included: `error: object 7777…7777 is not in the store`, with no hint, and `--json` gives `"hint":null`. With a tag at a folder listing it is `object dab7… is FolderListing, not Save`, and `goto <tag>` and `show <tag>` say the same. Nothing names the tag, so the person can't tell that `opalro tag --delete ghost --yes` is the way out (it works). A line that another line already holds is deleted fine, because the walk answers before it reads the bad holder: the same tag stops one delete and not another.
  - **Proof.** `a_tag_at_a_missing_save_is_named_when_it_stops_line_delete`.
  - **What I would do.** Report it as damage that names the holder ("tag ghost names a save that isn't in the store"), with the hint damage gets; or skip a holder that can't be read, with a warning, since a missing save can't hold anything. Only a planted `.opalro` makes such a tag: `tidy` keeps tags' saves and the import skips tags of trees and files.

- **RT17-4 Low (the hint to delete a tag prints its stored name unquoted, so pasting it runs other commands; T21; `main.rs` `tag_delete_command`).**
  - **What.** An imported tag's name can be any text. `opalro tag --delete "v1; touch pwned"` without a terminal prints `hint: To delete it: opalro tag --delete v1; touch pwned --yes`. Pasted into a shell, that deletes nothing and runs `touch pwned --yes`. `escape` stops control characters but not the shell's own characters (`;`, `|`, `$(…)`, spaces, quotes). The other hints that carry a name carry a line's, and line names can't hold these.
  - **Proof.** `the_hint_to_delete_a_tag_quotes_its_name`.
  - **What I would do.** Quote a name in a hint whenever it holds anything but the line-name characters (single quotes for POSIX shells, with `'\''`; or say "the tag's name, quoted"). The name starting with `-` (needs `--`, already deferred) is the same fix.

- **RT17-5 Low (a tag's name can put a line's mark on another save in `history`, and pose as two tags in `show`; T21; `history_output.rs`, `show_output.rs`).**
  - **What.** `history` writes `  [tag <name>]` after a row, the name escaped but not quoted. A tag named `v9]  [main` at the first save makes that row read `Start project  [tag v9]  [main]`: with colour on, the forged `[main` is painted in the same blue as a real line mark, so the row looks like line `main` is at the first save. `show`'s `Tags` row joins names with `, `, so a name `a, b` reads as two tags. Git's names can't do this (`[` and spaces are refused by Git), so only a planted `.opalro` can.
  - **Proof.** `a_tags_name_cannot_put_a_lines_mark_on_another_save`.
  - **What I would do.** Quote a tag's or line's name in marks and lists when it holds characters outside the line-name rules, as `changes` quotes odd paths.

## Suspicions (no proof; never findings)

- **The tag questions don't say what a delete or move leaves unheld.** `line delete` counts the saves only the line holds and asks only then; `tag --delete` and a tag's move always ask, but never say that the tag was the only thing holding some saves, which `tidy` frees once the undo window passes. Asked, but less informed than `line delete`'s question. A judgement for the owner, not a bug.
- **Walk cost on an old, unmerged line.** Deleting a line that forked long ago reads the other lines' saves back to the fork, and a held tip dated far in the past (or `i64::MIN`) makes the walk read every save newer than it before it answers. This is ruling 9's accepted cost; I didn't measure it on a large history.

## What held

- **The walk (`only_in`).** `rt17_walk.rs` compared it with a brute-force answer on 3,000 random histories of 2 to 41 saves with up to 3 parents, under four clocks (rising, ties among 5 values, random, and the ends of 64 bits: `i64::MIN`, `i64::MAX`, 0, ±1), 5 queries each with 0 to 3 holders, holders repeated and the tip among them. 15,000 queries, no failure: held always gave 0, unheld never 0 and never below the exact count, exact when times rise. Reading the code: a node spreads at most twice, the heap gets at most two entries per node, a one-sided waiting node keeps the walk going, and saves can't form a cycle, so a holder's mark always reaches a held tip.
- **Deleting, then tidying.** `tidy` marks every tag list of every entry in the window (`tidy.rs`), and a deleted line comes back with `undo` after `tidy` (pinned by `a_deleted_lines_saves_survive_tidy_inside_the_undo_window`). Undo replaces lines, position, tags and server lines together, so it can't bring back a line next to a tag of the same name that was never there together.
- **The question that wasn't asked.** `only_in` gives at least 1 whenever the tip isn't held, and `delete_line` asks whenever it is above 0; without a terminal, or with `--json`, it stops and names `--yes`.
- **Amending a tagged save** is refused: `tag v1 shows it too` (decision 159's consequence holds).
- **Names on screen.** `tag`, `history`, `show`, both questions and the outcome lines escape names and messages (`escape`); `--json` carries project text as data, as `docs/json.md` says. `cut_end` counts characters as `columns` does, so wide characters don't make it slice past the end.
- **Git's words.** `checkout -b`/`switch -c` run `line new` only as exactly `<flag> <name>` (`-bname`, `--create=x`, a start point, a name like an option are explained); `branch -d/-D/-m` only with names that aren't options; `tag -d` only as the first word. Nothing I tried ran an Opalro command meaning something else.
- **`save --line`** goes through the same name check as `line new`, tags included.
- **Imported tags of trees and files** are skipped at import, with a reason.

## Not done

- The faked terminal at 60, 80 and 120 columns, and 100,000 tags with 64 KiB messages: not run; the existing tests cover the escaping of the questions and a list of 100,000 tags.
- A planted diary whose `line delete` entry also carries a folder change: not built.
