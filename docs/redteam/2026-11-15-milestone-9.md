## Summary

I found no lost version and no conflict settled by a plain `save` or by an ignore rule. Every move case I built kept every version, either in an entry or in a side of a conflict. `--keep` over a folder with unsaved work kept a safety copy, and `undo` brought the work back. An ignore rule over a marked file did not settle it.

There are four findings, none High:
- `--only-if-clean` can end with 0 on a line that holds a conflict.
- The unbounded record maps in `status` and `save` (the lead the notes named) are real. 43 MB of planted store makes `status` abort at 3 GB.
- `resolve .` records a picture that a program rewrote by itself.
- `--copy before` says a file wasn't there when it was.

## Findings

- **RT21-1 Medium (`--only-if-clean` ends with 0 on a line whose save holds a conflict; new, against decision 181's promise; `combine.rs` `combine_locked`).**
  - **What happens.** Decision 181 and `docs/json.md` promise that once `opalro combine <target> --only-if-clean` succeeds, the save the line is on holds no conflict. If the line already has everything the target has, `combine_locked` returns `Combined::Nothing` before it checks anything. That happens at `only_in(repo, with, &[from])? == 0`, which comes before the `Keep::OnlyIfClean` check. The command ends with 0 and prints `Nothing to combine: main already has everything side has.` (`"result":"nothing"`, `"holds_conflicts":null`), while `status` lists `a.txt  1 marked place left to fix`. The easiest way to reach this is ordinary: run `opalro combine side` (which keeps a conflict), then a script runs `opalro combine side --only-if-clean && build`, and the build runs on a file full of markers.
  - **How to see it.** `only_if_clean_never_succeeds_on_a_line_that_holds_a_conflict`.
  - **What I would do.** With `--only-if-clean` in a project that keeps conflicts, give the "nothing" case the same check as the forward case: look through the line's own save once (`held_in`), and refuse with the existing words if it holds a conflict (`… would leave N places in conflict … <line> holds them in conflict already`). Or rule that "nothing" makes no promise, and say so in `docs/json.md` and `docs/terminal.md`. The first choice keeps the flag's one-line contract that scripts rely on.

- **RT21-2 Medium (`status` and `save` hold every conflict record they read, with no bound: 43 MB of planted store aborts `status` at 3 GB; T52 and T46; `status.rs`, `snapshot/walk.rs` `records: HashMap<Id, Record>`).**
  - **What happens.** The store's own memory of records is bounded (1,048,576 versions). But each command also keeps a map of every `Record` it read, and a `Record` holds `Vec<Option<Term>>` at about 48 bytes per version, whether the version is present or absent. A record of 255 versions with 254 absent takes about 300 bytes before compression and about 12 KB in memory. I planted saves through the library: folders of 1,000 conflict entries each, every entry naming its own record. Measured in the container (debug build, peak resident memory from `/proc`):

    | Conflict entries | Store | `status` | `goto main` | `save` |
    |---|---|---|---|---|
    | 20,000 ordinary files (no conflict) | 4 KB | 21 MB | 21 MB | 16 MB |
    | 20,000 wide records | 3.4 MB | 306 MB, 2.4 s | 66 MB | 306 MB |
    | 250,000 ordinary files | 4 KB | 86 MB | 80 MB | 16 MB |
    | 250,000 wide records | 43 MB | aborted at 3,075 MB (`memory allocation of 12288 bytes failed`), 44 s | 95 MB | 3,107 MB, finished under the 3.5 GB cap |

    So the growth is about 15 KB per record, about 70 times the store's size. `goto` (write-out) stays small, so the cost is in the status walk and the save walk's maps, not in reading. Nothing is lost: the abort happens before anything is written. But a cloned or shared project of a few tens of MB makes `status` and `save` unusable on a normal machine, and can take a 4 GB machine's memory. The notes' worry about "10,000,000 entries" is not even needed: a quarter of a million is enough.
  - **How to see it.** `status_and_save_hold_little_for_many_wide_conflict_records` (Linux; 20,000 entries; it asserts under 120 MB and sees 306 MB). The table comes from `rt21_memory.rs.txt` with `RT21_N=20000` and `RT21_N=250000`.
  - **What I would do.** Keep in each command's map only what that command uses from a record: what it stands as, its marker length, how many versions it has, and whether it has its own version. That is a fixed 50 or so bytes per record. Read the record again from the store (which is bounded) where a full one is needed. Or hold the per-command maps to the same budget as the store, and read a record again past it. Either way, add the test above, with 250,000 entries under a cap, to the corpus.

- **RT21-3 Low (`opalro resolve .`, or any folder's path, records a picture that changed by itself as decided; judgement; decision 177 §2 and its "never settled by accident" line; `resolve.rs` `choose`).**
  - **What happens.** Decision 177 says a picture or scene in conflict "stays listed until someone runs `resolve` with `--keep`, or names the path once they have put the version they want in the folder". A pattern takes only the places the folder shows fixed (`a pattern takes what is fixed among what it matches`). But a folder's path takes every place below it as the folder holds it, and that includes a conflict that is "changed in place". So: a person fixes `a.txt` by hand while a game engine re-exports `pic.png` by itself, then types `opalro resolve .` the way they would type `git add .`. Both places are recorded (`Recorded 2 fixes …`), and the engine's picture becomes the combined result without anyone choosing it. `opalro resolve "*"` in the same state records only `a.txt`. Decision 177 does say "a folder's path means every conflict below it", so this may be the rule as meant. That is why the test is ignored. But it is the one route by which the case the owner named (ruling 4 of the rulings file: "Game engines rewrite files just by opening a project") is settled by typing one ordinary command.
  - **How to see it.** `resolving_a_folder_records_no_picture_nobody_picked` (run with `--include-ignored`).
  - **What I would do.** Treat a folder's path like a pattern for places without markers: below a folder, record only places the folder shows fixed, and ask (or refuse with the `StillYours` words and hint) for places changed in place, unless each is named by its own path. Or keep the rule and say in `resolve`'s output which places were taken as changed in place, so the person sees it.

- **RT21-4 Low (`resolve --copy before` says "There was no file … where the lines parted" when there was one; what a person is shown; `resolve.rs` `no_file`, ruling R7).**
  - **What happens.** Two lines start from a save that holds `a.txt` in conflict. Each fixes it differently, and then they are combined. The new conflict's middle is "unknown". The marked file's middle label says `where the lines parted, which Opalro can't tell here`, and `combine` says `Opalro can't tell what it held where they parted`. Ruling R7 keeps "unknown" out of the record, so the record stores an absent middle version. `opalro resolve a.txt --copy before --to …` then refuses with `There was no file at a.txt where the lines parted, so there is nothing to copy.` That is false: the save where they parted held `a.txt`, in conflict. Nothing is written or lost. The words just contradict the label the person is looking at.
  - **How to see it.** `copy_before_does_not_say_a_file_that_was_there_was_not`.
  - **What I would do.** Where the middle version is absent, word the refusal so it covers both cases, for example `Opalro has no version of <path> from where the lines parted (it held nothing there, or Opalro couldn't tell what it held)`. Or check whether the place is a conflict in a save where the lines parted, if one is cheap to name.

## Suspicions without proof

None counted.
- **A move named as a change in a refusal.** A line `mover` moves folder `d` to `e` without changing anything, while `main` holds `d/a.txt` in conflict. `combine mover` stops with `d/a.txt is in conflict on main, and mover changed it too`. Stopping is right (nothing is lost, and the place moved). But "changed" is not what `mover` did, and the hint ("Fix it on the line that holds it first") is the only way forward. I did not look further at whether the conflict could be carried to `e/a.txt` instead.
- **The folder-term trick in `resolve --keep`** (`Built::keeping`). A folder version is put into the overlay as a `Symlink` entry and turned back into a `Folder` by matching IDs in `whole`. Any symlink entry in a rebuilt listing whose ID equals a kept folder's listing ID would also be turned into a folder. Opalro never makes such an entry (a link's target and a listing are hashed as different kinds), so only a planted save could hold one. I did not build that case.

## What was tried and held

- **A conflict the lines' common start held.** Lines `x` and `y` both start from a combined save holding `a.txt` in conflict. `x` fixes it, and `y` leaves it alone and adds `b.txt`: the combine takes `x`'s fix, cleanly. When both fix it differently, it becomes a new conflict with an unknown middle (as ruled), and both fixes are kept. Only the `--copy before` wording failed (RT21-4).
- **`--only-if-clean` carrying a conflict held by either line.** `main` holds a conflict, `other` adds a file, and both `combine other --only-if-clean` on `main` and `combine main --only-if-clean` on `other` were refused with the documented words. Only the "nothing to combine" route got through (RT21-1).
- **Moves against a folder that became a file** (`rt21_moves.rs.txt`, both directions each). The cases were: a file moved into a new folder `f` while the other line changed the file and made a file `f`; a file moved out of folder `f`, `f` removed and made a file, while the other line changed both files in `f`; and a file moved to two places, one inside a folder/file clash. Every version either line saved was in an entry or a side of a conflict.
- **An ignore rule over a marked file and over a saved file.** Adding `.opalroignore` naming both and saving kept the conflict (`1 place is still in conflict`) and kept the saved file. `resolve` then found nothing fixed.
- **`resolve d --keep theirs` where `d` stands as your folder holding an edited file and a new file, both unsaved.** The safety copy was kept and said so. `undo` brought both files back with their unsaved contents, and the conflict was listed again as changed in place.
- **`resolve` between its two reads, by reading the code** (`Recording::check` and `check_gone`, `Storing::seen`). The folder's entry is compared by kind and ID with what `status` saw before the question about markers. A marked file is scanned from the same bytes the save hashes. I found no gap.
- **`resolve --copy` destinations, by reading the code** (`destination`, `fsio::write_new`). `..` as the last part, a trailing `/.`, a link as the last name (create-new refuses it, since it exists), a path through a link to `.opalro` (canonicalised, then matched by identity), and a folder swapped after the check (the file is made in the opened folder handle) are all refused. A dangling link fails as "already there", because create-new does not follow it.
- **`tidy`, by reading the code** (`tidy.rs` `follow`). Every version of every record a reached listing names, its own version included, is marked. Records are reached through saves, so anything that names a save keeps them. I did not run `tidy` past the window with shelves and safety copies. That is left for a next session.
- **Marker reading, by reading the code** (`markers::scan`, `is_marker`, `marker_len`). Lines are split on `\n` in the writer, the reader and the merge alike, so a file with CR-only line endings is one line to all three and can't disagree. A line longer than the held `len + 2` bytes is judged on its start only, which is all `is_marker` needs.
