# Milestone 9 ("Conflicts"): rulings

The owner asked for v0.2 to be started while they were away, with Claude working alone. This file collects the calls made while planning and building milestone 9. It has three parts:

- **Please confirm:** the calls that most change what Opalro does. Each can be reversed.
- **Every ruling, as made:** each ruling as it was written when it was made, with its reason and what it costs if it is wrong.
- **Deferred:** what this milestone left for later.

The decisions themselves are records [174](../decisions/174-the-conflict-record.md) to [179](../decisions/179-every-command-and-a-conflict.md), made before the build, and [180](../decisions/180-a-file-that-arrived-where-the-other-line-changed-the-file.md) to [183](../decisions/183-red-team-m9-session-2-rulings.md), made while building and after the red team's two sessions. Each says "Decided by Claude, at the owner's request while the owner was away. The owner can reverse any part." The plan is [2026-11-14-milestone-9-conflicts.md](2026-11-14-milestone-9-conflicts.md).

**Branch:** `milestone-9`, from `v0.2`. Nothing is merged into `main`, which stays what v0.1 is released from.

## Please confirm

1. **A combine that has conflicts goes through and keeps them** ([175](../decisions/175-what-a-combine-keeps-as-a-conflict.md)). In milestone 8 it stopped and changed nothing. Now the combined save holds a conflict at each place that clashes, every version is kept, and you fix them when you choose. `opalro combine --only-if-clean` is the old behaviour, for scripts.
2. **Such a combine ends with 0, where Git's `merge` ends with 1** (175). Opalro has three exit codes (done, failed, a command line it couldn't use), and the combine is done. A script that must stop on conflicts uses `--only-if-clean`.
3. **In the folder, a text file in conflict gets markers; anything else keeps your line's version** ([176](../decisions/176-a-conflict-in-the-folder.md)). Markers are the well-known ones, with the part both lines started from in the middle. A picture, a scene, a file too big to compare, or a file whose rule says so, stays as your line has it, whole, and the other versions stay inside `.opalro`. If you had removed the file, nothing appears in your folder.
4. **A text file is fixed when its markers are gone; a picture or a scene only when you say so** ([177](../decisions/177-recording-a-fix-save-and-resolve.md)). Game engines rewrite files just by opening a project, so a file that changed by itself never settles which line's version is kept. `opalro resolve <file> --keep mine` or `--keep theirs` does.
5. **`opalro resolve` puts the fix into the combined save when it can** (177): the save is replaced by one with the same ID, message and parents, as `save --amend` replaces a save, so history ends with one combined save that holds the result. When something else shows that save, or other saves came in between, the fix is a new save. Say if you would rather have fixes always be a new save.
6. **`opalro save` works on a folder with conflicts and never decides one** (177): half-fixed files are saved as they are, and the conflicts stay listed.
7. **`opalro resolve <file> --copy theirs --to <somewhere>`** (177) writes one version out for you to look at. Opalro starts no other program.
8. **A project made by v0.1 needs `opalro setup --upgrade` once before it can keep conflicts** ([178](../decisions/178-the-conflicts-feature.md)), and after that v0.1 can no longer open it. That is your rule from decisions 008 and 121, kept to the letter. A project made by v0.2 can keep conflicts from the start, and v0.1 can't open it. Asking on the spot, at the combine that needs it, would save a step: say if you want that.
9. **The conflict record stores the file as it stands in your folder** ([174](../decisions/174-the-conflict-record.md)): the marked text, or your half-fixed version. It costs one more stored text for each conflict, and it means Opalro never has to work the marked text out again to tell whether you touched it. This is the one new thing on disk in v0.2.
10. **A project without conflicts pays nothing for being able to have them** ([179](../decisions/179-every-command-and-a-conflict.md)): no command looks through a save for conflicts, with one exception that only a person who asks for it pays: `opalro combine --only-if-clean`, when the line would only move forward or there is nothing to combine (decisions 181 and 182). For that reason `opalro history` doesn't yet mark a save that holds conflicts; `status`, `show` and `combine` say so.
11. **In a criss-cross history, a file the two lines' starting points disagree about becomes one whole conflict** (175), where milestone 8 refused the combine. Git would often merge such a file; Opalro never guesses there.
12. **A line that still holds a conflict can be combined, except where the other line changed the same place** (175): then the combine asks for that conflict to be fixed first. Opalro never makes a conflict inside a conflict.
13. **A conflict does not follow a rename** (ruled while building Task 7). Rename a file that still has markers and the save counts the conflict as fixed: the new name is an ordinary file with the marker lines still in it. Rename a picture that is in conflict and the conflict stays at the old name, with nothing in the folder there. And a new name that differs only in upper and lower case from a conflict still open is refused, on every system, as two such names always are. Git and Jujutsu treat a renamed conflict the same way. Say if a conflict should follow its file instead: that is a design of its own.
14. **`status` reads every file that still has markers each time it runs** (ruled while building Task 4), to say how many places are left. Pictures and other conflicts without markers cost nothing. The other way is to keep that number in the conflict's record, which changes the record's layout.
15. **A file moved onto a place whose file the other line changed** ([decision 180](../decisions/180-a-file-that-arrived-where-the-other-line-changed-the-file.md), decided while building Task 10). The combine keeps one conflict there: your file, the file the place held when the lines parted, their file; a text is shown with both files whole and the old one in the middle, never merged line by line. Milestone 8 called it "changed here, removed there" and stopped. The same decision says that a moved file is not seen at its old place, so a new file made under the old name is simply a new file, and that a file moved onto the very same file is no conflict at all.
16. **`opalro combine --only-if-clean` promises a clean result** ([decision 181](../decisions/181-what-building-milestone-9-refined.md)). After it succeeds, the save your line is on holds no conflict at all: it also stops for conflicts the lines already held, and when your line would only move forward onto a save that holds one. That is stricter than decision 175 first said ("where a conflict would be kept"). With the flag, a forward onto a save too large to check is refused as well.
17. **`opalro resolve` takes patterns, and reads what you type as a path first** ([decision 181](../decisions/181-what-building-milestone-9-refined.md)). `opalro resolve "*.png" --keep theirs` takes the other line's version of every picture in conflict. A name that is exactly a place in conflict always means that place, even if it could be read as a pattern.
18. **Where `resolve --copy` will not write** ([decision 181](../decisions/181-what-building-milestone-9-refined.md)). Never over a file that is there, never into `.opalro`, told by which folder it really is. One thing is not caught: a second route to the same disk that the system reports as a different folder, such as a share from another machine. Closing that would need new operating-system calls, which you review line by line; none were added.
19. **When a `--json` field may take a new value** ([decision 181](../decisions/181-what-building-milestone-9-refined.md)). A field whose values are a fixed list of codes gets a new one only in a project that has a feature older Opalros did not know (here `conflicts`), so a project made by 0.1 and never upgraded gives the values 0.1 gave. New fields can appear anywhere, as before.
20. **A place both lines hold alike is never a conflict**, even where a file was moved to two places ([decision 181](../decisions/181-what-building-milestone-9-refined.md); and [decision 180](../decisions/180-a-file-that-arrived-where-the-other-line-changed-the-file.md) for a file moved onto the very same file). At a moved file's old place the move rules still come first, as milestone 8 decided.
21. **`opalro resolve <folder>` records only what the folder shows fixed below it** ([decision 182](../decisions/182-red-team-m9-rulings.md)). Until the red team's session, a folder's path recorded every place below it as it stood in the folder, so `opalro resolve .` could record a picture that a game engine had rewritten by itself. By this ruling a folder's path is read as a pattern is: what is fixed is recorded, the rest is listed with what each place needs, and a place changed in place is recorded only when you name it by its own path. `--keep mine` and `--keep theirs` still take every place below a folder.

## Every ruling, as made

**Before the build: what the decisions didn't yet say** (given to the planning agent on 2026-11-14)

- **R1. One function says what a conflict stands as** in the folder: its own version if the record has one, else its first term; either may be absent. Write-out, the folder walk, the check for unsaved work, safety copies, `discard` and the shelf all go through it.
- **R2. Without the feature, nothing changes.** In a project whose `format` doesn't list `conflicts`, a conflict entry or record is treated exactly as before, and the tests for that stay. The check is in one place.
- **R3. Everything in a record is untrusted.** A term's kind is checked against the object it names when that is read. A folder among the terms can be as large as a save: commands that don't need it never read it, `tidy` and `verify` walk it without recursion, and `resolve --keep` writes it under write-out's own limits and name rules. A marked text is at most 64 MiB, a label at most 200 bytes of plain text on one line, a list of conflicts a command names at most 100 with a count of the rest.
- **R4. Only the combine writes a record** (three terms), and `save`, which rewrites one only to change its own version. Nothing writes a record in a project without the feature.
- **R5.** Withdrawn by ruling B below (it said where a count of conflicts in a save would come from).
- **R6. `resolve` reaches the save code** the way `save --amend <paths>` does; "record these places as fixed" reaches the walk for the named paths only; `--keep` writes through write-out's planned actions with its safety copies; one diary step either way; it meets every check `save` makes on the files it records.
- **R7. The starting version "unknown"** is a value of its own inside the merge, never stored and never the same as "absent".
- **R8. What milestone 9 does not do:** conflicts of more than three terms written by Opalro (read, yes); combining two conflicts into a wider one; `who`; writing a conflicted save into a Git repository; a general command that takes one file out of any save; writing a conflict out afresh from its terms; merge programs.

**Before the build: three rulings that changed the plan's shape** (2026-11-14, on the planning agent's first plan)

- **A. No walk of a save to find its conflicts.** The first plan read every folder of a save, in every command that meets the folder, to find conflicts. Every v0.2 project can hold conflicts and `status` is at its speed limit against Git, so that was ruled out. A conflict is met where a listing's entry is met; its record is read then; a listing keeps its stored ID. A test holds that a project without conflicts reads no listing and no record it didn't read before. Why: the ability must cost nothing until it is used. Cost if wrong: the walk and write-out each learn about conflicts where they meet an entry, which is more places to get right than one pass up front.
- **B. No count of conflicts in a save.** It can't be kept exact without that walk, and nothing needs it: no field in the save, no check in `verify`, no mark in `history`. `show` and `changes --save` say what a save changed; `combine` counts while it measures its result against a save's limits; `save` and `resolve` say how many they met. Why: a number that is sometimes wrong is worse than none. Cost if wrong: a save that holds conflicts looks like any other in `history`.
- **C. A combine never makes a conflict inside a conflict.** It stops where both lines changed a place and one holds it in conflict or holds one below it. A planted one is refused as damage when it is read for the folder; `tidy` and `verify` still follow everything. Why: every such case has an easy way forward (fix the inner one), and nesting doubles what every command must handle. Cost if wrong: a combine is refused where it could have gone through with two conflicts, one inside the other.

**Before the build: answers to the planning agent's 22 questions** (first round)

1. Where the starting version is unknown and both lines hold a folder, the merge goes in and decides entry by entry, everything below still unknown; elsewhere the conflict is whole.
2. A picture in conflict inside a folder the person deleted: the conflict stays, its own version absent, and its folder stays in the save, standing as an empty folder. Cost if wrong: `status` keeps showing that folder as removed until the conflict is resolved, and `goto` to the save makes an empty folder.
3. Where a save's count of conflicts would come from: gone with ruling B.
4. What finding conflicts costs: ruling A.
5. Conflicts inside conflicts: ruling C.
6. Moves: nothing a line saved is cleared before the merge; a move clash's row names the place where the file landed; milestone 8's three rows for moves are reworded.
7. `resolve <path>` on a picture whose changed copy was already saved: recorded as that copy, since the person named the path. It is refused without `--keep` only while it stands as the line's version as the combine left it.
8. A planted record of 512 MiB: a conflict record over 16 KiB is refused before it is unpacked (the store knows a record's size there).
9. What must hold of a marked text: two properties, not one. When every change of theirs overlaps one of ours, taking one side everywhere gives that side back exactly; in general, taking ours everywhere equals a merge with every clash settled by ours. And every marked text reads back with as many opening lines as marked places.
10. In a project without the feature, a criss-cross that milestone 8 refused can now combine cleanly when both lines hold the disputed file alike: intended, and nothing new is stored.
11. `resolve` at a save that no line is at: its own refusal, with the hint `opalro line new <name>`, which makes a line there.
12. A save between two conflicted saves of one place: a third kind in `show`, "still in conflict".
13. A file with only closing markers left is still being fixed.
14. `combine` says how many places its save holds in conflict; its rows name the ones this combine made; a detail says how many the lines held already.
15. `status` lists every conflict, as it lists every change, in `--json` too; `combine` and `resolve` name the first 100 and count the rest.
16. A marker's label carries the first 8 letters of the save's change ID, always, so the same conflict gives the same text whenever it is made.
17. Changes below a conflict that stands as a folder are not listed apart; the conflict's row says "changed in place".
18. `--copy` may write anywhere but inside `.opalro`; the file is made new and never written over anything; nothing is locked or recorded.
19. A file moved to two places, where the other line also put something new at your place: that line's term is whatever it holds there, so nothing is dropped.
20. Two added files with the same contents and a different executable mark: a conflict standing as yours, no markers.
21. The hint for a conflict a line holds names the line in its prose and puts no name inside a command.
22. `opalro setup --upgrade --json` asks nothing: without `--yes` it changes nothing and says so.

**Second round** (the seven questions left after the plan was revised)

1. A conflict standing as a folder that an ignore rule now matches behaves as a saved folder at that place does today; where that is "gone from the folder", the conflict stays with its own version absent. Cost if wrong: the person's folder is still on the drive but no longer the conflict's version, and going back to that save moves it to a safety copy.
2. A picture in conflict below a deleted folder, in a project already past a save's limits: the save goes ahead without it, as today for other entries kept as they were. Cost if wrong: that conflict is dropped from the next save; it is still in the save before.
3. `save <path>` inside a conflict that stands as a folder goes the way a full save goes. If that needs more than the shared rule, the answer becomes a refusal ("save the place whole, or resolve it").
4. `goto` says "The save you went to holds places in conflict" when it met one in the save it went to; never about the save it left; no number.
5. `save` counts the places it met; its words say so.
6. `resolve` can't record, from the folder, a place this computer can't hold; with `--keep` the save records the version and write-out says it wasn't written here.
7. Nothing read "as it stands" is ever stored under the ID it was read by: a constraint of the plan, with a test, and a point for the whole-branch review.

**Third round** (after a pre-flight scan of the plan and milestone 8's whole-branch review)

- **D1.** No record is ever put at a place below another conflict's place: what a line holds there is held by that conflict's folder. Putting a move clash's record back never replaces a conflict with a plain folder. The scan's case is a test: ours moves `a.txt` to `ui/a.txt` and adds `ui/b.txt`; theirs moves `a.txt` to `c.txt` and adds a file `ui`; nothing may end in no entry and no record. Why: as first planned, their `ui` and your `b.txt` would have been lost. Cost if wrong: none found.
- **D2.** While either line's `opalro.toml` can't be read whole, a text file both lines changed stops the combine, whether its changes would merge or overlap, inside the starting points' own combines too ([decision 172](../decisions/172-red-team-m8-session-2-rulings.md)). Why: Opalro can't know whether such a file may be merged, or marked. Cost if wrong: a mistake in a rules file stops a combine that could have kept an ordinary conflict.
- **The rules of both lines** ([decision 173](../decisions/173-the-rules-of-both-lines-decide-what-a-combine-merges.md)) decide markers too: a file is shown with markers only when both allow it, under every name it had.
- The scan's twelve findings that would have broken a task as written (stale names, files a task touches and didn't list, an option that couldn't be given, a test that needed a later task) are fixed in the plan. Marker labels are given for each file merged, since the middle label can differ from place to place.

**Fourth round**

- When the rules stop a combine, the refusal names only the places the rules would decide, not every clash. Cost if wrong: one more run to see the rest.
- The other line's rules file is found by the name `opalro.toml`, or, when there is none, by a name that differs only in the case of ASCII letters, on every system; several such names count as rules that can't be read whole (left over from milestone 8's last re-review).

**While building** (each as it was ruled during the build; the task it came from is in brackets)

1. [Task 1] On a conflict inside a conflict, decision 174's words bind where the plan's differed: a record never names another conflict on any of its sides, not only on the first. Why: the decision is the spec. Cost if wrong: none; it is a sentence in the storage spec.
2. [Task 2] `opalro setup --upgrade` never offers `chunks`. That feature is added by itself by any command that changes the project (decisions [083](../decisions/083-a-chunk-list-is-stored-under-its-files-id.md) and 121), so a question whose "no" changes nothing is not a question. I first accepted the other way and reversed it on review. Cost if wrong: none; a project from before milestone 5 gains `chunks` as it always did.
3. [Tasks 1 and 2] The words that refuse a record that doesn't decode stand as the code has them (plain words, in the style of the other records' refusals); the plan's table was changed to them. Cost if wrong: none.
4. [Task 3] `opalro verify` reports a conflict inside a conflict for what the record stands as (its own version if it has one, else its first version), since that is what reading the folder refuses. Cost if wrong: a planted record whose first version holds a conflict while its own version is a file is not reported; it is harmless until someone keeps "mine", when it becomes an ordinary folder holding an ordinary conflict.
5. [Task 3] In `verify`'s findings the versions of a record are named "your version", "the version where the lines parted", "their version" and "its own version"; "version N of M" only for a record of more than three. The finding's `--json` carries the record in the `object` field every other finding uses. Cost if wrong: none.
6. [Task 3] In a project that isn't set to keep conflicts, `tidy` and `verify` say what is true now: `pack <pack> holds a conflict record, and this project isn't set to keep conflicts`, with the hint `Nothing was removed, and the project works as before. opalro verify checks the project; opalro setup --upgrade lets it keep conflicts, after which tidy follows them.` The old words pointed at a future version, and this is it. Cost if wrong: none; the behaviour is unchanged.
7. [Task 4] `status` reads each file that still has markers every time it runs, to count the places left. The promise that a second `status` opens no file holds for conflicts that stand as a version (pictures, scenes) only. Why: the number of places left is in the file, and the record has no room for it without changing its layout. Cost if wrong: while conflicts are open, `status` reads every marked file on each run (a thousand such files of 10 KB is 10 MB a run).
8. [Task 4] A conflict record that can't be read is damage, with the hint every damage error gives (`Nothing was changed. Ask for help before trying to repair it.`). A read that failed for the system's reasons is not reported as damage, and a record over 16 KiB doesn't make the rest of its pack suspect. Cost if wrong: none.
9. [Task 5] `status` prints `Nothing changed since then.` only when there is no change and no conflict. A place in conflict that this computer can't hold is listed once on screen, under "In conflict"; `--json` keeps it in `not_written` as well. Cost if wrong: none.
10. [Task 5] `status` ends with one `Next:` line, the first that applies: `Next: record what you fixed with: opalro resolve`; else `Next: fix the marked places in your editor, then run: opalro resolve`; else `Next: pick a version with: opalro resolve <path> --keep mine (or theirs); to look at theirs first: opalro resolve <path> --copy theirs --to <file>`. The plan had three lines at once. Why: every command names one next step, last. Cost if wrong: a person with conflicts of several kinds sees the other steps only after the first is done.
11. [Task 6] `goto` says that the save it went to holds a conflict (`holds_conflicts` in `--json`) whenever it met one there, whatever the conflict stands as, a removed file included. Why: "you deleted it, they changed it" is the case a person most needs to be told about. Cost if wrong: none.
12. [Tasks 6 and 7] A command reads each conflict record once, whichever of its steps meets it: the project's store remembers the records met. It remembers them only within a budget (1,048,576 versions named in all); past it a record is read again when it is met again. Why: a planted project could otherwise make one command hold a great deal for every conflict. Cost if wrong: a command that meets more than about 350,000 conflicts reads some records more than once.
13. [Task 7] `save` says `N places are still in conflict: opalro status lists them.`, and for a save of some paths `N of the places you saved are still in conflict: opalro status lists every place in conflict.` The plan's "places it met" was the engine's way of speaking. Cost if wrong: none.
14. [Task 7] A conflict kept inside a folder you deleted, where a file now has that folder's name, stops the save with words of its own: `Opalro can't save <path>: the last save has a folder there holding <kept>, which is still in conflict, and a save can't hold both under one name.` The hint is `Nothing was saved. Rename or move <path>, then save again.` Cost if wrong: none.
15. [Task 7] A save never passes a conflict over because it hasn't read its record yet: it reads it there. Why: a save must not decide a conflict by not looking. Cost if wrong: one more read in a corner only a save past the limits reaches.
16. [Task 7] A rename is a removal and an addition, for a conflict as for any file: a conflict does not follow a rename (Git and Jujutsu do the same). A file with markers that you rename is fixed by its removal, and the new name is an ordinary file that still has the marker lines. A picture in conflict that you rename stays in conflict at its old name, with nothing in the folder there, and the new name is an ordinary file. Why: following a rename would be a rule about moves that nobody decided. Cost if wrong: after renaming a file with markers left, `status` shows no conflict, though every line of both versions is in the file.
17. [Task 7] A conflict that a save keeps at a place with nothing in the folder still holds its name there, and new names are judged against it as against every other name ([decision 004](../decisions/004-project-contents.md)): a new name that differs from it only in upper and lower case, or is the same name written another way, is refused with the usual words, on every system. Why: found while building. Renaming a picture in conflict from `Hero.png` to `hero.png` on Windows made a save holding both names; from then on that drive saw the two as one file, kept both as they were, and never saved a later change to `hero.png`. Cost if wrong: a person who respells a file in conflict must rename it back, or pick a version first.
18. [Task 7] `save <paths>` settles every place it names exactly as a full save would, and leaves every other place as it was; one test compares the two over every kind of conflict and every way of naming. Why: reviews found two holes of this kind in a row (a picture inside a deleted folder, then a conflict standing as a folder named directly), each of which dropped a conflict nobody had decided. Both are fixed. Cost if wrong: none.
19. [Task 8] In a marker's label, a long name is cut, never the save's letters: the name is cut between characters, the cut is shown with `…`, and ` (<8 letters>)` is always whole, so the label stays within 200 bytes. The plan cut the whole label, which lost the letters exactly where a person needs them. Cost if wrong: none.

[Task 9] When both lines hold the same place in conflict, differently, the combine stops with `<path> is in conflict on both <line> and <target>, so nothing was changed.` and the hint `Fix it on both lines first (opalro resolve on each), then run opalro combine again.` The plan's hint named one line, and fixing one of two leaves the stop standing. Cost if wrong: none.

In a project made by Opalro 0.1 that has not been upgraded, such an entry (which only a project made outside Opalro can hold) is treated as milestone 8 treated it. Why: without the feature, nothing changes. Cost if wrong: none.

Before, a rules file that couldn't be read whole stopped the combine for such a pair. Cost if wrong: none.
23. [Task 9] Before a folder becomes one side of a conflict, Opalro checks that it holds no conflict below. That check is now held to each line's limits across the whole combine, and a folder is walked once however many places name it. Before, each check started from nothing, so one large folder met at many places was walked again each time. Cost if wrong: none.

Cost if wrong: a mistake in the design of the move rules would be shared by the model and not caught by it; the test above, which uses no model, is the net for a version left out.
29. [Task 11] With three or more common starting points, what they could not agree on stays unknown through every later combine of them, and a place unknown on the side made so far is never read as that side having removed it. Why: a review found that the unknown places were forgotten each time another starting point was combined in, so a removal could be lost in silence, depending on the order of the saves' IDs. Cost if wrong: none; unknown where a place could have been told only makes a conflict where a clean result was possible.
30. [Task 11] Where the save the lines parted from holds a conflict and both lines hold a folder there, everything below is unknown: a file only one line holds below is a conflict, never an addition. Only in a project that keeps conflicts. Cost if wrong: none.
31. [Task 12] After `opalro combine --only-if-clean` succeeds, the save the line is on holds no conflict. It stops, changing nothing, for a conflict it would make, one a line already holds, or (when the line would only move forward) one the target's save holds; for a forward it looks through the target's save once, only with the flag. Why: the flag is for scripts that must not go on with a conflict in the folder, and a conflict brought in from the other line is in the folder just the same. As first built it let those through. Cost if wrong: a forward with the flag reads every folder listing of the target once; and a target past a save's limits is refused with the flag even if it holds no conflict, because it can't be checked.
32. [Task 12] A project that can't keep conflicts yet is always told so, with or without `--only-if-clean`: the flag's hint ("run it again without it") would be untrue there. Cost if wrong: none.
33. [Task 12] Words. A combine that made no conflict but carries some: `Combined <target> into <line>: save <id> "<message>", with N places in conflict.` then `The two lines held them in conflict already; the save keeps them.` Where it made some and the lines held one more: `The two lines held 1 more place in conflict already; the save keeps it.` A combine that only moved the line forward onto a save that holds a conflict says `The save your line moved to holds places in conflict: opalro status lists them.` In `combine --json`, `holds_conflicts` is `null` when there was nothing to combine: the save was not looked through. Cost if wrong: none.
34. [Task 13] `opalro resolve` records only what it looked at. It reads the folder once to see what is fixed, and again to build the save; a file that changed in between stops it with `<path> changed while Opalro was reading it.`, and `status` takes a marked file's contents and its markers from one read. Why: a review found that a text which gained markers, or a picture put back, between the two reads would have been recorded as settled without the person having settled it. Cost if wrong: a person whose editor rewrites a file during `resolve` runs it again.
35. [Task 13] The engine itself refuses to keep a side without the places to keep it at (`Keeping a side needs the places to keep it at, so nothing was recorded.`), and "where the lines parted" is not a side it can be asked to keep. Why: the engine is a library; without the guard one call would take a side at every place in conflict. Cost if wrong: none.
36. [Task 13] `resolve --copy` never writes into `.opalro`, told by which folder the destination is and not by how its path is spelled: links, `..`, another spelling, a junction, a second mount on the same machine are all caught, using the operating-system calls the platform crate already had: no new `unsafe` was added. Not caught: a second route to the same disk that the system reports as another folder (a share from another machine, a network mount of the project). The destination's folder must be readable. Cost if wrong: a person who types such a route to their own project's `.opalro` can have one new file created there.
37. [Task 13] A save that `resolve --keep` makes is held to a save's limits like any other, and the default message is `Fixed conflicts in N places` (decision 177 said "N files"; a place can be a folder). Cost if wrong: none.
38. [Task 14] `opalro resolve` takes what `save` takes: paths and patterns (`opalro resolve "*.png" --keep theirs`). A pattern stands for every place in conflict it matches. What you type is read as a path first: where it is, letter for letter, a place in conflict or a folder with places below it, it means that and nothing else. Why: a file can really be named `a[1].png`; read only as a pattern it could not be named, and with `a1.png` also in conflict `--keep` took a side there instead. Cost if wrong: someone who wanted the pattern reading of a string that is also a real path must write the pattern another way.
39. [Task 14] Words. One fix is "it": `The combined save now holds it; its ID stays the same.` `--copy` says `Wrote your version of <path> to <file>.`, `Wrote the other line's version of <path> to <file>.` or `Wrote <path> as it was where the lines parted to <file>.` What is left is listed under `N places are still in conflict:`. A refusal that comes from `save`'s own checks speaks of `resolve` ("Nothing was recorded", "run opalro resolve again", `Record them? [y/N]`). The help's example writes to `Hero-theirs.png`, since `~` is not the home folder in every Windows shell. Cost if wrong: none.
40. [Task 15] In `--json`, a field whose values are a fixed list of codes takes a value an older Opalro never gave only in a project whose format has a feature that older Opalro did not know. New fields and new kinds of warning may appear in any project, as before; a field that holds a name (a command's name in the diary, a path) is not such a list. Why: `change` gained three values, and the rule for format 1 allowed new fields, not new values. Cost if wrong: a script written for 0.1, run on a project its owner upgraded, meets a value it does not know.
41. [Task 15] In `show` and `changes --save`, a folder that became a conflict's place, or a conflict's place that became a folder again, is one row with nothing below it (the conflict holds the folder whole; listing its files as removed would be untrue), and `in_conflict` says whether the newer save holds a conflict at the place. Cost if wrong: `show` does not list what differs inside such a folder.
42. [Task 15] Git's words: the one-time note for `merge` has a second line, `A combine keeps conflicts and still ends with 0; opalro combine --only-if-clean <line> stops instead.`, and an explanation of a Git word may be one to three lines (decision 116 said two or three). Why: a script that ran `git merge x && build` would go on after a combine that kept conflicts. Cost if wrong: one more line, shown once.
43. [Task 16] The model of the whole command line now keeps and fixes conflicts by its own rules, taken from the decisions. Driven by random histories it found two faults in the engine, both fixed: a file moved to two places kept a conflict even where both lines held the very same file (a place both lines hold alike has nothing to settle and is taken once, [decision 181](../decisions/181-what-building-milestone-9-refined.md)); and under `--only-if-clean` a place whose start nobody can tell was named "only files are merged line by line". Cost if wrong: none.
44. [Task 16] The model test has two passes: one with a fixed seed, the same on every system, on which it must meet at least three cases of every kind it claims to cover (37 kinds); and one that draws new cases on every run and requires no count. Why: counts required of random cases fail by chance (they did, once, on Linux), and without random cases the two faults above would not have been found. Cost if wrong: the fixed pass catches only what its fixed cases reach.
45. [Task 16] In the comparison with `git merge`, no case is set aside without a check that nothing was lost: a case is set aside only where Git itself reports that it followed a move, and there, and wherever Git reports a conflict and Opalro does not, every line and every file that either line added must be in Opalro's result or in a side of a conflict. Why: as first written the test skipped 14 of 34 conflicted cases without looking at them. Cost if wrong: a slower test.
46. [Building as a whole] Twice a test file that nobody had run turned CI red after a change to what a command prints, and three tests turned out to depend on chance (one from milestone 8 failed about once in 650 runs). Each was fixed where it showed. The machine this was built on ran short of memory several times; whole test runs that could not finish here were left to CI, which runs everything on Windows, macOS and Linux for every commit; the milestone is not closed until CI is green on its last commit.
47. [Task 16] Where one line only changes a file's executable mark and the other line moves that file together with an edit and puts another file at the old path, the mark lands on the new file at that path. Opalro goes by the path and follows only a move saved by itself ([decision 168](../decisions/168-moves-in-saves-and-in-combines.md)); Ruled not a loss. This entry first said that Git would put the mark on the moved file and called it an accepted difference; that had not been tried. Tried since, with Git 2.50.1: its merge is clean and the new file at the old path gets the mark, exactly as in Opalro. Both go by the path there. If wrong: an executable mark ends on the wrong file in that one shape, in Git as in Opalro.
48. [Task 16] The task was closed at its limit of five fix rounds with five small points open, all in the two test files and their page in `docs/testing.md`, none in the engine: one sentence about which runs gave the listed counts; one hole in the check that nothing was lost (a new file's mark, in one shape); one test that does not hold the change it was written for; two sentences about what that check does not see. Each is ruled real, to be fixed in the one round of fixes after the whole-branch review.

## Deferred

A mark in `opalro history` for a save that holds conflicts (it needs a save to say so, or a cache); conflicts of more than three versions, and combining two conflicts into a wider one (decision 007's conflict algebra); writing a conflicted save into a Git repository; a command that takes one file out of any save; writing a conflict out again from its versions (`opalro undo` gives the first marked text back); asking on the spot to turn the `conflicts` feature on; merging line by line a file the starting points disagree about.
