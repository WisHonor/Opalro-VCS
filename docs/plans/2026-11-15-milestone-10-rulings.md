## Please confirm

1. **`opalro who <file>` reads the file as it is in your folder** ([184](../decisions/184-opalro-who-the-save-behind-each-line.md)), as `git blame` does, and marks the lines you have not saved yet. `--save <save>` reads a saved version instead. The other choice was the saved version only, as Mercurial does.
2. **A change of line endings alone does not count as changing a line** (184). A save that only turned `\r\n` into `\n` takes no line in `who`. Everything else counts, spaces too; Git counts line endings unless asked not to.
3. **`who` follows a moved file only where a save recorded the move** (184), never by likeness. One thing it cannot follow: a file moved on one line and changed, under its old name, on a line that was later combined in; the lines of those changes are named as the combine's. Nothing a save stores says where a second parent had the file.
4. **In a folder that holds a conflict's marked text, `who` names the save behind each side's lines,** and the marker lines as the combine's (184). It needed no rule of its own: a place in conflict is read as what stands there.
5. **`opalro save --amend` is refused when anything else has the save in its history, through any parent** ([185](../decisions/185-save-amend-and-a-save-something-else-holds.md)): another line that combined yours in, a tag further on, a server line. Until now only first parents were followed, and a tag or server line counted only when it named the save itself. `opalro resolve` uses the same rule to decide whether a fix replaces the combined save.
6. **The amend check asks about the save itself, not about other saves of the same change** (185). The old check matched by change ID, so it would also have refused when another line held an older copy of the save you are amending. Building it showed that this cannot be reached through Opalro's commands: a save an amend replaced is not found by its ID afterwards, so no line can be started on it. It matters only in a project made by other means.
7. **A small note replaces the cache the amend check kept** (185): the save Opalro made last and the diary entry that recorded it, in the project's cache folder. With it, an amend right after a save reads nothing of the other lines. `cache/other-lines`, which Opalro 0.1 wrote, is no longer read or written.
8. **Speed: nothing that is flushed changes** ([186](../decisions/186-speed-before-v0.2.md)). Going back (`goto`) was to come within twice Git's time in v0.2. The work done twice is taken out; the flushes, which cost more, are yours to rule on, with a table of what each costs. If `goto` is still over twice Git's time, v0.2 is packaged with that said plainly, as v0.1 was.
9. **v0.2 is packaged up to the draft and no further** ([187](../decisions/187-v0.2s-package.md)): the version is 0.2.0 on the branch `v0.2`, the release workflow has run there (every job but the draft), and nothing is tagged, drafted, merged into `main` or opened as a pull request.
10. **`USER-AGREEMENT.md` was not touched** (187). One sentence in it speaks of the version: liability is limited to what you paid, "nothing: Opalro 0.1 is free". Every archive carries the agreement, so that sentence needs your word before v0.2 is published.
11. **The cache keeps a note for each line's newest save, not one for the whole project** (185, its correction). As first built it kept one, and then working on another line and coming back made the next amend ask about every line, tag and server line: slow in a project with hundreds of old lines, each time. The review of that task caught it, and it was changed before anything shipped.
12. **A tag or server line that names a missing save stops an amend,** with the damage named, when the check has to ask about it (185, its correction), as `opalro line delete` already stops. Saving as a new save still works.

## Every ruling, as made

**Before the build** (2026-11-15, from the research of the code in `milestone-9`)

- **R1. `who` works on what stands at a path,** the file itself or, at a place in conflict, what the conflict stands as ([decision 174](../decisions/174-the-conflict-record.md)'s one rule), read through the reader every other command uses. No other handling of conflicts in `who`.
- **R2. Lines are compared without their line ending,** and by nothing else: no option to leave spaces out in this milestone.
- **R3. Every parent is followed, the first one first:** a line both parents have goes to the first parent's side.
- **R4. Versions wait on a heap, the newest save first, and lines that reach one version two ways are taken together;** the answer never depends on the order, so clocks that lie only cost time.
- **R5. No limit on how far back `who` reads.** Each comparison has `changes`' deadline; past it `who` says the answer may name a newer save than the first that had a line. The command writes nothing and can be stopped.
- **R6. The amend check asks the ancestry module** ([decision 160](../decisions/160-whether-a-save-is-in-anothers-history.md)), with one new question (which of these saves holds this one), asked again without each holder found, so that the refusal can name them.
- **R7. What is asked of:** every other line, tag and server line that is new or has moved since the diary entry the note names; all of them when there is no usable note. A line, tag or server line that has not moved since the save was made pointed at a save that already existed, and a save that existed first cannot have a later one in its history.
- **R8. The note is trusted only for which of them to ask about,** under the user's seal, for the save it names, with a diary entry that has the line at that save.
- **R9. The release workflow is started from the branch `v0.2`,** where its last job, the draft, does not run by the workflow's own rule.

**While building**

1. [Before Task 1, the scan of the plan] The storage format says `cache/other-lines` is no longer read or written in the commit that stops using it (Task 3), not one commit earlier (Task 2): the format must be true at every commit. Cost if wrong: none.
2. [Before Task 1] One test of the plan is ignored on purpose and asserts nothing on a clock: it prints the times of an amend in a project of 300 old lines, for the benchmarks. What must be fast is asserted elsewhere by counting what is read. Cost if wrong: none.
3. [Before Task 1] `opalro who` reads a project the way `show` and `history` do: no lock that a writer waits for, and nothing written. One test compares `.opalro` and the folder byte for byte before and after. Cost if wrong: none.
4. [Measured before Task 8's turn] **`status` got about 4 to 5 % slower during milestone 9, in a project with or without conflicts** (and `goto` about as much). Milestone 9's last nightly had shown `status` a millisecond above earlier runs on one processor, unexplained. Three runs on GitHub's Linux machines, each comparing builds in turns on one runner, settled it: 21.4 ms before milestone 9 and 22.5 ms after on one processor; and, with eight builds from along the milestone on another, a step of about 0.6 ms at the commit in which the folder walk learned to meet a conflict, and nothing after it. That commit's own review had named three lookups it added per file and left them as "can wait". They are the candidate; Task 8 makes that one change and keeps it only if the same kind of run shows the time back. Milestone 9's sentence that a project without conflicts pays nothing is true of what is read and not of time. Cost if wrong: one change put back.
5. [Task 3] Three things in decision 185 were wrong or missing, and are corrected in it: the case of another line holding an older copy of the same change can't be reached through commands; after a save on another line the note is that save's, so the next amend of this line asks about everything ("Please confirm" 11); a tag or server line naming a missing save stops the check ("Please confirm" 12).
6. [Task 3, its review] The note of the save made last became a note for each line's newest save. The review found no way to get an amend through that must be refused, and one thing the design had lost: with a single note, a save on another line made the next amend of this line ask about everything, about 20 seconds in the shape the red team once measured, every time. Entry 5 had first put a note per line on the follow-ups list "for when the measurements ask"; the measurement was already there (decision 112), so it was built at once. Cost if wrong: 64 bytes a line in a cache file.
7. [Found by the model test, in code milestone 9 merged] **`opalro resolve --keep` made a folder again that the person had deleted,** when it kept a place inside that folder as nothing. The model of the command line, which draws new random cases on every run, met it while another task was being fixed; the case failed the same way without that task's changes. Looked into at once, before the next task: nothing was lost, the folder matched what `goto` writes, and `undo` was exact, but a folder changed that nobody had named, against decision 177 (`resolve` touches only the places of conflicts; other unsaved changes stay unsaved). The cause was older than `resolve`: a write-out limited to some paths put every folder above a named path "in scope". Ruled and fixed in that one place, for every command that limits a write-out to paths: a folder is made only if it was named itself or something is written into it or below it. No decision record: the code was brought to a decision, not a decision changed. Cost if wrong: `opalro discard <path>` no longer makes an empty folder above a path it has nothing to write at (no test or page had promised that it would).
8. [The same] After `resolve --keep` in that case, the new save still holds the empty folder, the person's folder lacks it, and `opalro status` says nothing changed: `status` lists files, not empty folders. That was already so for any saved empty folder deleted by hand. Whether `status` should show a deleted empty folder is a question of its own, on the follow-ups list.
