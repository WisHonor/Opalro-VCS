Milestone 10 is the last of v0.2's four ([decision 157](../decisions/157-v0.2-in-four-milestones.md)). The decisions themselves are records [184](../decisions/184-opalro-who-the-save-behind-each-line.md) to [187](../decisions/187-v0.2s-package.md). ## Please confirm

1. **`opalro who <file>` reads the file as it is in your folder** ([184](../decisions/184-opalro-who-the-save-behind-each-line.md)), as `git blame` does, and marks the lines you have not saved yet. `--save <save>` reads a saved version instead. The other choice was the saved version only, as Mercurial does.
2. **A change of line endings alone does not count as changing a line** (184). A save that only turned `\r\n` into `\n` takes no line in `who`. Everything else counts, spaces too; Git counts line endings unless asked not to.
3. **`who` follows a moved file only where a save recorded the move** (184), never by likeness. One thing it cannot follow: a file moved on one line and changed, under its old name, on a line that was later combined in; the lines of those changes are named as the combine's. Nothing a save stores says where a second parent had the file.
4. **In a folder that holds a conflict's marked text, `who` names the save behind each side's lines,** and the marker lines as the combine's (184). It needed no rule of its own: a place in conflict is read as what stands there.
5. **`opalro save --amend` is refused when anything else has the save in its history, through any parent** ([185](../decisions/185-save-amend-and-a-save-something-else-holds.md)): another line that combined yours in, a tag further on, a server line. Until now only first parents were followed, and a tag or server line counted only when it named the save itself. `opalro resolve` uses the same rule to decide whether a fix replaces the combined save.
6. **The amend check asks about the save itself, not about other saves of the same change** (185). The old check matched by change ID, so it would also have refused when another line held an older copy of the save you are amending. Building it showed that this cannot be reached through Opalro's commands: a save an amend replaced is not found by its ID afterwards, so no line can be started on it. It matters only in a project made by other means.
7. **Small notes replace the cache the amend check kept** (185): for each line, the newest save Opalro made on it and the diary entry that recorded it, in the project's cache folder (first built as one note for the whole project; item 11 says why that changed). With them, an amend right after a save reads nothing of the other lines. `cache/other-lines`, which Opalro 0.1 wrote, is no longer read or written.
8. **Speed: nothing that is flushed changes** ([186](../decisions/186-speed-before-v0.2.md)). Going back (`goto`) was to come within twice Git's time in v0.2. The work done twice is taken out; the flushes, which cost more, are yours to rule on, with a table of what each costs. If `goto` is still over twice Git's time, v0.2 is packaged with that said plainly, as v0.1 was.
9. **v0.2 is packaged up to the draft and no further** ([187](../decisions/187-v0.2s-package.md)): the version is 0.2.0 on the branch `v0.2`, the release workflow has run there (every job but the draft), and nothing is tagged, drafted, merged into `main` or opened as a pull request.
10. **`USER-AGREEMENT.md` was not touched** (187). One sentence in it speaks of the version: liability is limited to what you paid, "nothing: Opalro 0.1 is free". Every archive carries the agreement, so that sentence needs your word before v0.2 is published.
11. **The cache keeps a note for each line's newest save, not one for the whole project** (185, its correction). As first built it kept one, and then working on another line and coming back made the next amend ask about every line, tag and server line: slow in a project with hundreds of old lines, each time. The review of that task caught it, and it was changed before anything shipped.
12. **A tag or server line that names a missing save stops an amend,** with the damage named, when the check has to ask about it (185, its correction), as `opalro line delete` already stops. Saving as a new save still works.
13. **`opalro who` changes nothing in the project, not even a cache** (184). `opalro show` and `opalro history` refresh the cache of change IDs when it is out of date; `who` reads the same list and stores nothing, so that "it changes nothing under `.opalro`" is a sentence a test can prove. The price: with that cache out of date, `who` reads the missing part of the line again on each run until another command refreshes it. One thing it shares with every command that is given a path: to learn how the drive compares names, an empty file is made and removed under `.opalro/tmp`, so `who` cannot run on a project that cannot be written at all; there it says which folder it could not write and why it needs to. It also opens the project as `opalro verify` does: the leftovers of interrupted commands in `.opalro/tmp` are left for the next command, and no lock is taken.
14. **`who` remembers what it compared, within two bounds** (184). When the dates of saves are out of order, lines can reach a version after `who` has dealt with it. It then answers from what it remembered instead of comparing again: at most 256 comparisons are remembered, and at most about a million stretches of lines among them, the oldest dropped first. A comparison is remembered by the two versions' contents and the sizes their listings claim, so a listing that lies about a size changes nothing. What was dropped is compared again: the time changes, and the answer does not, with one exception: a comparison that ran past its deadline may come out finer when it is made again, and then names an older save that also holds the line. A history planted to keep `who` busy can still do so; it writes nothing and can be stopped.
15. **In history imported from Git, `who` does not follow a renamed file** (184). `who` follows a move only where a save recorded it, and the import records none: every imported save has an empty list of moves. So for a file that was renamed in Git, `who` names the commit that renamed it for every line older than that, where `git blame` goes on past it. Histories made with Opalro itself are followed. Making the import record renames would close the gap; it changes what the import writes, so it is a decision of its own and was not made. It is in the release notes' known limits and on the follow-ups list.
16. **Where a combine took the other line's version of a file whole, `who` still asks your line first; `git blame` does not** (184, its correction). `git blame` then names every line of that file through the other line. `who` keeps its one rule: a line your line already had is your line's. The two name different saves only for a line both lines wrote separately, and both saves did write it. The comparison test found this, and Git's own history has it on a handful of lines. I kept the rule as decided. Git's way would agree with `git blame` there and would save a comparison at such combines (how much was not measured); it would make the rule two-part. Yours to choose.
17. **After a combine, an empty folder can appear where a conflict sits in a folder you moved away** ([188](../decisions/188-red-team-m10-rulings.md)). The red team's second session found it: your line moved a folder away, the other line changed a file in it; the combine keeps that as a conflict with nothing in your folder for it, says no file needed changing, and still leaves the old folder there, empty. Keeping your side with `opalro resolve --keep mine` leaves it too. Nothing is lost, and deleting the folder is safe. I did not change it: the folder is what the combined save holds, and changing what a switch makes touches every command, after both red-team sessions. The choices are in the decision: the switch makes a folder only when it writes into it, or a `resolve` that keeps a removal removes the folder. Yours to rule on.

## Every ruling, as made

**Before the build** (2026-11-15, from the research of the code in `milestone-9`)

- **R1. `who` works on what stands at a path,** the file itself or, at a place in conflict, what the conflict stands as ([decision 174](../decisions/174-the-conflict-record.md)'s one rule), read through the reader every other command uses. No other handling of conflicts in `who`.
- **R2. Lines are compared without their line ending,** and by nothing else: no option to leave spaces out in this milestone.
- **R3. Every parent is followed, the first one first:** a line both parents have goes to the first parent's side.
- **R4. Versions wait on a heap, the newest save first, and lines that reach one version two ways are taken together;** the answer never depends on the order, so clocks that lie only cost time.
- **R5. No limit on how far back `who` reads.** Each comparison has `changes`' deadline; past it `who` says the answer may name a newer save than the first that had a line. The command writes nothing and can be stopped.
- **R6. The amend check asks the ancestry module** ([decision 160](../decisions/160-whether-a-save-is-in-anothers-history.md)), with one new question (which of these saves holds this one), asked again without each holder found, so that the refusal can name them.
- **R7. What is asked of:** every other line, tag and server line that is new or has moved since the diary entry the note names; all of them when there is no usable note. A line, tag or server line that has not moved since the save was made pointed at a save that already existed, and a save that existed first cannot have a later one in its history.
- **R8. The note is trusted only for which of them to ask about,** under the user's seal, for the save it names, with a diary entry that has the line at that save.
- **R9. The release workflow is started from the branch `v0.2`,** where its last job, the draft, does not run by the workflow's own rule.

**While building**

1. [Before Task 1, the scan of the plan] The storage format says `cache/other-lines` is no longer read or written in the commit that stops using it (Task 3), not one commit earlier (Task 2): the format must be true at every commit. Cost if wrong: none.
2. [Before Task 1] One test of the plan is ignored on purpose and asserts nothing on a clock: it prints the times of an amend in a project of 300 old lines, for the benchmarks. What must be fast is asserted elsewhere by counting what is read. Cost if wrong: none.
3. [Before Task 1] `opalro who` reads a project the way `show` and `history` do: no lock that a writer waits for, and nothing written. One test compares `.opalro` and the folder byte for byte before and after. Cost if wrong: none.
4. [Measured before Task 8's turn] **`status` got about 4 to 5 % slower during milestone 9, in a project with or without conflicts** (and `goto` about as much). Milestone 9's last nightly had shown `status` a millisecond above earlier runs on one processor, unexplained. Three runs on GitHub's Linux machines, each comparing builds in turns on one runner, settled it: 21.4 ms before milestone 9 and 22.5 ms after on one processor; and, with eight builds from along the milestone on another, a step of about 0.6 ms at the commit in which the folder walk learned to meet a conflict, and nothing after it. That commit's own review had named three lookups it added per file and left them as "can wait". They are the candidate; Task 8 makes that one change and keeps it only if the same kind of run shows the time back. Milestone 9's sentence that a project without conflicts pays nothing is true of what is read and not of time. Cost if wrong: one change put back.
5. [Task 3] Three things in decision 185 were wrong or missing, and are corrected in it: the case of another line holding an older copy of the same change can't be reached through commands; after a save on another line the note is that save's, so the next amend of this line asks about everything ("Please confirm" 11); a tag or server line naming a missing save stops the check ("Please confirm" 12).
6. [Task 3, its review] The note of the save made last became a note for each line's newest save. The review found no way to get an amend through that must be refused, and one thing the design had lost: with a single note, a save on another line made the next amend of this line ask about everything, about 20 seconds in the shape the red team once measured, every time. Entry 5 had first put a note per line on the follow-ups list "for when the measurements ask"; the measurement was already there (decision 112), so it was built at once. Cost if wrong: 64 bytes a line in a cache file.
7. [Found by the model test, in code milestone 9 merged] **`opalro resolve --keep` made a folder again that the person had deleted,** when it kept a place inside that folder as nothing. The model of the command line, which draws new random cases on every run, met it while another task was being fixed; the case failed the same way without that task's changes. Looked into at once, before the next task: nothing was lost, the folder matched what `goto` writes, and `undo` was exact, but a folder changed that nobody had named, against decision 177 (`resolve` touches only the places of conflicts; other unsaved changes stay unsaved). The cause was older than `resolve`: a write-out limited to some paths put every folder above a named path "in scope". Ruled and fixed in that one place, for every command that limits a write-out to paths: a folder is made only if it was named itself or something is written into it or below it. No decision record: the code was brought to a decision, not a decision changed. Cost if wrong: `opalro discard <path>` no longer makes an empty folder above a path it has nothing to write at (no test or page had promised that it would).
8. [The same] After `resolve --keep` in that case, the new save still holds the empty folder, the person's folder lacks it, and `opalro status` says nothing changed: `status` lists files, not empty folders. That was already so for any saved empty folder deleted by hand. Whether `status` should show a deleted empty folder is a question of its own, on the follow-ups list.
9. [Task 5, its review] **`who` was right and did too much work.** The review worked each rule through on paper and found every line at its right save, in any order of dates. It also found two promises about cost not kept: every version on the way was read whole even when the file had not changed in that save, and lines that reached a version after its turn made it compared again. Fixed in the same task: a version is read only when a parent holds other contents (a file unchanged through 40 saves: its contents read 2 times, not 44), and what a comparison found is remembered (please-confirm item 14). The bound of 256 comparisons is my ruling; the implementer added the second bound, on stretches, because 256 comparisons of a million lines each could hold gigabytes, and the re-review found it sound. Cost if wrong: time on planted histories, never an answer.
10. [Task 5 and Task 6] **Entry 3 above said `who` reads "the way `show` and `history` do, and nothing written". That was loose:** those two refresh the cache of change IDs, and the first build of `who` did the same through the function that shortens an ID. The review of the command line caught it. Ruled: `who` keeps the stricter promise (please-confirm item 13). The first fix gave one function a way not to store, and its re-review found a second path the same cache was written on: the word after `--save`, when it is an ID. So the promise went into the project's handle: the one `who` opens reads the caches and stores none, whatever it calls. The same work ended a load of that cache for every save named. The test that proves it was made able to fail: every cache file is deleted first, the whole of `.opalro` and the folder is compared both ways, and it was broken once on purpose to see it fail. Cost if wrong: a little time when the cache is out of date.
11. [Task 5, its review] The engine asked how the drive compares names on every run, which makes and removes a file under `.opalro/tmp`; my notes for the task had told it to. Now it asks only when no entry has exactly the path as typed. The command line still asks once, as it does for every command given a path. Cost if wrong: none.
12. [Task 6] **Three small rulings on what `who` says.** In your folder, a folder or a link at the path is refused as what it is ("is a folder") when the save the project is at holds one there, and not as "isn't a file in your folder". A name the system cannot hold at all (on Windows, one with a `*`) is "isn't a file in your folder", where the first build showed the system's own error with a hint about `.opalroignore`. And "isn't saved yet" is said only when no save holds the file: a saved file rewritten from top to bottom gets its rows, each marked not saved yet. Cost if wrong: words.

Ruled: `who` opens as `verify` does; the re-review checked that it loses no check or refusal by it. Cost if wrong: leftovers wait for the next command that is not `who` or `verify`.

[Task 8] **The lookups milestone 9 added to the folder walk were hoisted, and timed: about two thirds of the lost time came back.** Four builds in turns on one of GitHub's Linux machines: `status` took 12.96 ms before milestone 9, 13.82 after it, 13.84 on milestone 10 before the change and 13.24 with it; `goto` 17.53, 18.77, 18.77 and 18.06. [Task 7] **`who` was compared with `git blame`, and the two agree on every line compared**: 4,929 lines in 64 histories made in Git and imported (branches, merges, lines changed, removed and put back), and 604 lines in 24 histories with moved files. Making that test showed what please-confirm item 15 says: the import records no moves, so the histories with moved files had to be made with Opalro's own commands and mirrored in Git. Cost if wrong: none; it is a finding, not a ruling.

They were made on a throwaway branch after milestone 6's model, compiled and run only on GitHub's machines, and never merged. They show: a `goto` makes ten flushes, 3.3 ms of its 30.6 ms on Linux (11 %); `status` makes one, 0.5 ms, for the drive clock's file; and a `goto` loads the file cache twice. That last is work done twice, the one decision 186 names, so it is the one more change made, under one rule: the switch must trust exactly what a fresh load would have given, or the change is dropped. The flushes are not touched: `docs/benchmarks.md` has what each costs and what the code and the decisions say each is for, for you to rule on. Cost if wrong: none; nothing that is flushed changed.
19. [After the nightly run] **On Git's own history `who` and `git blame` name different commits on 5 to 10 % of a file's lines** (and on a third of `README.md`, which was renamed). The test on generated histories could not say whether `who` is right on those, so it was looked into before the package, on GitHub's machines: every differing line of five files was sorted by why the two differ, and each answer was checked where that needs no diff. Of 930 differing lines, 871 hold a text that repeats in the file, 23 lie behind the rename, 6 are at combines and 30 are moved lines or lines written twice. **No line was found where `who` named a save that neither wrote nor moved the line.** By the check, `who` named the save that wrote the line more often than `git blame` did (47 of 57 against 33 of 56). Not looked at one by one: 50 lines of repeated text. Cost if wrong: on those 50, `who`'s choice was not shown to be a possible one.

No decision says this rule in words (decisions 054 and 181 can be read either way; milestone 3's ruling and the engine's test point this way), so it is written down here. Cost if wrong: none; nothing in the engine changed.
